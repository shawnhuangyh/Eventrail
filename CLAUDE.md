# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Eventrail is an iPhone/iPad SwiftUI app (app target `Eventrail`, bundle id `moe.shawn.Eventrail`, plus the `EventrailTests` unit-test bundle). [MyApp.swift](Eventrail/MyApp.swift) declares the `@main` `App` and shows [RootView.swift](Eventrail/Views/RootView.swift), a four-tab `TabView` (My Events / Following / Me / Search, the last with `role: .search`, which iOS 26 detaches into its own button beside the bar). There is no package manifest and no dependencies.

Source is grouped as:

- [Eventrail/Model/](Eventrail/Model/) — `Event`, the reader's private `Tracking` record, `LibraryArchive` (everything they own, as one value), `Feed` (one page of an Eventernote listing at a time), `Region`, `PassportStats`, and `EventStore`, an `@Observable` store passed down through `.environment`. Three things ride in that environment, and the two beside the store are both read from Eventernote rather than from the library, and both cached on the device rather than only for the launch: `FollowedDates`, the upcoming dates from each followed performer's listing, so the Following tab and the Me card share one read instead of asking twice; and `VenueRegions`, which part of the country each hall named on those rows stands in. [PreviewData.swift](Eventrail/Model/PreviewData.swift) is fixtures for `#Preview` and the playground only; the running app starts with an empty library.
- [Eventrail/Services/](Eventrail/Services/) — the Eventernote import adapter (`EventernoteClient`, `EventernotePages`, `HTMLCursor`), the three answers to "where is this hall" (`VenuePlaces`, `JapanAddresses`, `VenueBuildings`) plus `VenueRegions`, `PageReads` (which event pages this device has already read), and `CloudSync`, `CalendarSync` and `LibraryBackup`. See below.
- [Eventrail/Views/](Eventrail/Views/) — one file per screen, plus [Components/](Eventrail/Views/Components/) for the shared glass panel, the wash background, and the small repeated parts: `Typography` (`SectionLabel`, `CardHeader`, `SeeAllLabel`, `Footnote`), `Pieces` (`StatTile`, `GroupHeader`, `FlowLayout`, `VenueMap`, the favorite and followed rows), `ListControls` (the list, selection and performer toolbars and the removal confirmation they share), `SettingRow` (the icon-name-control row Settings and the Welcome screen's switches share), `BackupRestore` (the `restoringBackup(_:asking:)` and picker modifiers) and `RefreshNotices` (the notice every refresh ends in — see *The Eventernote import*). A screen that draws a row two screens already draw belongs here rather than in a third copy.

Where each screen hangs off those four tabs:

- **My Events** (`EventsView`) is the library, filtered ahead/past and grouped by month or by the billed artist, with a selection mode for removing several at once. A row whose night is still ahead counts itself down beside the chevron (`DaysAway`, off `Event.daysAway`) — whole days between written dates, so a night stays "1 day" all through the day before it rather than turning into two some time that evening, and the last week reads in the app's own tint. Only here: `LibraryRow` is the one row the reader keeps because they mean to be there, and counting down to a date nobody has kept would be the app deciding it mattered. A night still ahead is also read or unread, off the **same** `followingReads` record Following keeps — so a date read on either tab is read on both: the `UnreadTag` (New / Updated) sits above the title, opening the row or swiping it from the leading edge reads it, and a past night carries neither tag nor swipe, since its record is pruned with the night. Its selection mode marks as well as removes: `SelectionToolbar` (shared with the two screens behind the Me cards) keeps Select All top-left as Following does, and takes a `MarkReadButton` bottom-left — Following's own, same rule — on the Upcoming filter only. No envelope filter here. Every row, past or ahead, also swipes from the trailing edge to Remove — the same `EventStore.remove` as the trash, unconfirmed as a swipe to delete is everywhere on iOS.
- **Following** (`FollowingView`) is every upcoming date of every followed performer, read from their listings rather than from the library, filterable by date range, area and person. A night leaves it once its published end time has gone by (`Event.hasEnded`), not only once its day is over — **but only where its hall's clock is known** (`FollowedDates.hallZone`, wired in `RootView`): a listing row is read on Tokyo time whatever its hall, so a Taipei finish would read an hour early and a Los Angeles one as the morning before the show. The clock comes from `VenueRegions` placing the hall in Japan, from the library's own retimed copy of the night, from the clock `VenueRegions.settleClocks(for:)` settled for a hall abroad, or from any `VenuePlaces` placing of a hall of that name (`timeZone(ofHallNamed:)` — opening the night places it; a name two placings put on different clocks answers nothing, since the row could mean either); a row whose clock is known is re-read on it (`Event.published(in:)`) before it is shown or judged, which also puts My Time right for it, and the cache keeps the row as the listing printed it. A row whose clock is not known stays until its day is over everywhere (`Event.isUpcomingAnywhere`, the day's end at GMT−12): read on Tokyo time, Tokyo's midnight is the morning of the same day in Los Angeles, and a night there would go before its doors opened. Doors, start and end are read in the order a night runs, each moved to the next morning wherever it is earlier than the one before it (`Event.inOrder`: 開場 23:30 開演 00:30 終演 05:00) — `EventernotePages` stores them so, and `hasEnded` reads older copies the same way. It is taken out of the cache (`FollowedDates.dropFinished()`) at the top of every pull and every stale check, before anything is asked of Eventernote, since the end time is already cached; left out of a listing as it is read; and checked again as `events(for:)` is read, for the redraws in between — which it makes happen, since nothing else changes as a night ends: each read sets a wake for the soonest shown date to go over, and the wake bumps a tick `events(for:)` reads. A night with no end published stays until midnight, since nothing says it is over sooner. It is read like a mailbox: a date carries a tag after the names in its billing caption (as `Eventrail v3.dc.html` draws it) — New, or Updated where the listing changed after it was read; a tag rather than a dot because the billing caption already leads with one — until the reader opens it, swipes it from the leading edge, or marks it in a batch from the pencil's selection mode, and the envelope in the bar shows only the unread ones. `LibraryArchive.followingReads` keeps, per event, a fingerprint of the row *as it was read* (`Event.listingFingerprint`: title, hall, day, times and bill — the day once and each time as the clock the page printed, so a night abroad retimed in the library agrees with Following's Tokyo-time copy and an after-midnight time read as the next morning (`Event.inOrder`) changes nothing; not the head count, not the flyer), so a refresh that brings the row back changed makes it unread again without anything watching for the change; a first launch finds every date unread. It is the reader's own record, so it is stamped and synced like a favourite, settled per event; marking a date unread writes a `FollowingRead` with no fingerprint rather than dropping the key, and so does Delete All, for the reason a removal is a tombstone. Records are pruned by their night, not their stamp. Clear Cache leaves it alone — it is not a copy of anything Eventernote holds. A `List` rather than a scroll view of panels, for the swipe and the selection — which is also why the billing caption pushes through the stack's `path` rather than a `NavigationLink`, which would take the whole row over.
- **Me** (`MeView`) is four cards — the linked account, the Event Passport, favourites and followed performers — each sampling five rows and sending the rest to a screen of its own (`FavoriteEventsView`, `FollowedPerformersView`). Everything that *configures* the app is behind the gear: `SettingsView`: General (Language, which pushes `LanguageSettingsView`: App Language — iOS's per-app setting, so a link to the system's page — and the language an event's 概要 is translated into; then Appearance, Time Zone, iCloud Sync, Calendar Sync), Backup (Export, Restore), Advanced (Venue Locations, which pushes `VenueLocationsView` holding the Refine with OpenStreetMap switch, the refresh, and Refresh All Venues — a per-device `@AppStorage` switch, off by default, without which the refresh skips halls Apple Maps already placed, and Clear Cache) and About (About Eventrail, the Welcome screen), with Delete All alone under Danger Zone below them. `Appearance` (System/Light/Dark) is a per-device `@AppStorage` preference applied by setting `overrideUserInterfaceStyle` on every window and every controller presented over it (`Appearance.apply()`) — by `MyApp` at launch and by the Settings row as it changes, so a change shows at once. Not `preferredColorScheme`: going from Light back to nil there left the window and the Settings sheet light on a dark phone. And not an `onChange` in `MyApp`: on the app's own `@AppStorage` it fired for the first change only. A Settings row is an icon in a gutter, a name and a control; it grows a second line only for a status the reader has to act on or is waiting on (a failure, a refresh in progress, the last sync). Don't put explanations back under the switches, a footnote at the bottom, or a how-it-works card in About; the Welcome screen's feature panels are the one place the switches are explained. The exception is `VenueLocationsView`, which opens on why the switch exists (outside mainland China Apple Maps places nearly every hall and nothing there needs changing; inside it Maps finds few halls in Japan), then the three answers a hall is placed by (Apple Maps, the 国土地理院 register, OpenStreetMap), in the order they are asked, each with how many of the reader's halls it placed (`VenuePlaces.breakdown(for:)`) — with its switch and the refresh under them: the switch governs only the third answer — every request to OpenStreetMap, the narrowing and the mainland-provider search abroad alike — and it means nothing without the other two.
- **Search** (`SearchView`) runs Eventernote's two searches, events and performers.
- Opened from several of them: `EventDetailView` (as a sheet), `PerformerView`, `VenueView`, and `ListingHalfView` behind the See All on either of those last two.
- `WelcomeView` is shown over everything on the first launch, once per device, and asks only the three things the app cannot work out for itself: where the reader's records come in from (an account or a backup), whether they sync, and whether the calendar is written. Every answer is optional and both switches start off; each is the same row Settings already carries, so nothing there is a one-way door.

## The Eventernote import

**The linked account's record on Eventernote is the source of truth for what the reader has been to and who they care about.** That is the premise the whole app is built on: the library is the account's attendance history as the site publishes it, and `follows` is the account's favourites. So an import is always allowed to restore what the site still lists, and it never needs the reader's permission to do it — asking Eventernote again is how the reader gets back something they took out and then wanted.

What the reader owns is the layer on top: tracking, notes, favourites, and which of their own devices hold what. A removal in the app settles *that* layer and syncs across their devices; it does not reach the account and has never claimed to. Dropping something for good means dropping it on Eventernote. The exception is what the account never carried — an event saved from Search, a performer followed in Eventrail alone — where a removal is final because nothing will import it back.

Eventernote publishes no API, so [EventernoteClient.swift](Eventrail/Services/EventernoteClient.swift) GETs the site's public pages and [EventernotePages.swift](Eventrail/Services/EventernotePages.swift) reads them with [HTMLCursor.swift](Eventrail/Services/HTMLCursor.swift), a marker-based scanner (no HTML parser, no dependency). Things worth knowing before changing any of it:

- **The User-Agent must contain `iPhone`.** The site serves a desktop template otherwise, and every selector here is from the smartphone template. This is the single most breakable assumption in the adapter.
- Pages read: `/events/search`, `/actors/search`, `/actors/{slug}/{id}/events`, `/events/{id}`, `/places/search`, `/places/{id}`, `/places/{id}/events`, and — only once the reader has named a handle — `/users/{handle}` and `/users/{handle}/events`. `robots.txt` disallows only `/users/notice` and `/users/timeline`. Everything is a GET: nothing is ever written back to Eventernote, no password or cookie is collected, and naming a handle reads that member's public pages rather than signing in as them.
- Performer slugs come back already percent-encoded and are passed through `percentEncodedPath`; re-encoding them breaks names containing `!`, `(` or spaces.
- A performer's own listing (`/actors/{slug}/{id}/events`) is ordered from the furthest published date backwards, so every upcoming appearance sits at the front of it. `PerformerView` relies on that: it pages until the first past row appears, which is what makes its Upcoming section — and the count over it — the whole of it rather than whatever landed on page one.
- A hall's own listing (`/places/{id}/events`) is the same block in the same order, read the same way by `VenueView`. The hall's page itself carries ten of those rows and says "→全てのイベントを見る(372件)" about the rest, so the listing is read from `/places/{id}/events`, which pages and prints its total like every other listing on the site. The two pages are what `ListingHalfView` is shared between — one screen behind both See Alls, titled for whichever subject it was handed.
- **A venue page publishes no photograph of the hall** — only an address and a `map_canvas` the site fills in with Google's script, which this app does not run. So `VenueView` draws its own map from the published address through `VenuePlaces`, the same lookup and the same kept answers an event's sheet uses; the hall is never shown with a picture, for the reason a performer is not.
- **Eventernote publishes no performer portrait.** The `gb_blur_title` cover block in the shared template is only ever filled on a member's own page; every actor page sampled across the id range leaves it out, and the actor listing and search rows carry no image either. So no performer is ever shown with a picture — not on `PerformerView`, not in an event's Performers card, not in a Search result row. An event flyer is artwork for the event rather than a likeness of the performer, so it is not stood in for one either, and an empty placeholder circle is just furniture. Don't go looking for a portrait endpoint again. (The avatar on the Me tab is a different thing: a *member* page really does publish one.)
- An event's billing publishes names only, with no link to a profile, so opening a performer from there searches for the name and takes an exact match. The search matches on the kana reading too, so a near miss is a different person.
- **An event's times are a wall clock with no zone on it.** 開演 18:00 means 18:00 at the hall, and the site's members write a night abroad in the hall's clock like any other — the Taipei dome dates print the same 18:00 their Chinese-language 概要 does. So an import reads every page on `Event.publishedZone` (Asia/Tokyo, one zone for all 47 prefectures) because that is all a page says, and a hall the placing later puts outside Japan sends its events back through `Event.published(in:)`, which re-reads the same published clock in the hall's zone. Nothing on a screen moves — every line is formatted in the event's own zone — but the instant behind it does, and that instant is what the calendar entry, its door alert and the library's order are made of. A hall nothing has placed stays on Tokyo time, which is right for every hall in Japan and is the old behaviour everywhere else. **Settings › Time Zone** (`TimeDisplay`, a per-device `@AppStorage`, Venue Time by default) can print every day and time on the reader's own clock instead: `Event.shown(on:)` is a copy for *formatting only* — the zone set to the device's and the day taken from the first published time, since a day with no time cannot be converted and keeps its hall's — and the instants, the month groups, `daysAway` and the date filter stay as they are, because a night belongs to the day its hall says it falls on. Every view that prints a day or a time reads the setting itself (`@AppStorage`) rather than through the environment. On My Time the badge reads "My time · GMT+8", the device's offset on the night, which is always known. Otherwise `EventDetailView` says under the date which clock its times are on — "Venue time · GMT+9" — on **every** sheet rather than only on the nights abroad: the times are the hall's wherever the hall is, and a reader in Shanghai reading a Tokyo date is owed that as much as a reader in Tokyo reading a Taipei one. Two rules keep it honest, and both were learned the hard way:

  - **The offset, never a place name.** A zone identifier is the map provider's reading of where the hall stands, and the provider is chosen by where the *reader* stands: a phone served from mainland China files a Taipei hall under `Asia/Shanghai`, which Foundation names "China mainland Time" — printed under a Taipei address on the same screen. Seoul is GMT+9 and is not "Japan Time". The offset is the part the app is sure of and the part that moves the times; the hall is named on the same sheet already. Don't reinstate `TimeZone.localizedName` or `.genericLocation` here.
  - **Only a clock that has been established.** `EventDetailView.venueZone` takes it from the placing, or from an event a placing already retimed, or from a published address opening with a Japanese prefecture (Japan being one clock end to end, no map service needed). Otherwise the badge stays but the offset goes: an unplaced hall abroad is read on Tokyo time because that is where every import starts, and printing GMT+9 under a Seoul date would be claiming an answer rather than having one. "Venue time" alone is still the whole truth — the times *are* the hall's, as its members wrote them — and the sheet asks for its own hall as it opens, so the offset usually arrives a second later.
- Search rows carry only day, title, venue, billing and a thumbnail. Times, head count and the venue address come from the event's own page, so `Event` marks that with `isDetailed` and its time fields are optional. **Do not make them non-optional** — Eventernote routinely announces an event months before it publishes a start time.
- An event's own page publishes more than the times: 概要 (the one free-written field, and so where ticket prices, on-sale dates and stage splits all end up — kept with its line breaks), 関連リンク, Twitterハッシュタグ, and the edit history's who-and-when, which is how a reader tells an upcoming date nobody has checked in two years from a fresh one. **Reading more of that page means bumping `Event.currentDetailFormat`.** `isDetailed` answers the older question — was the page read at all — so a library imported before a field existed carries it true and the field empty; `isFullyDetailed` compares the stored `detailFormat` and is what sends one sheet back for the rest. Deliberately one sheet at a time: a bulk re-read would be nine hundred requests for pages nobody is looking at.
- **概要 can be read in the app's own language** through Apple's Translation framework (`translationTask` on `EventDetailView.summaryCard`), on the reader's tap and never by itself. The target is `TranslationTarget`: a per-device `@AppStorage` choice made under Settings › Language, empty by default for the app's own language (`Bundle.main.preferredLocalizations.first` — the per-app language, not the system's). Its list is `LanguageAvailability.supportedLanguages`, so it is only the default row in the Simulator. The button is not offered when the target is Japanese or when `LanguageAvailability` calls the pair unsupported. The source is named as Japanese rather than detected, since kanji and hall names read as Chinese to a detector. It is translated line by line so the ticket lists keep their shape, and a line that is only an address is carried over untouched. The result lives in the sheet's `@State` and is **never written to the archive**: it is a way of reading the page, not the reader's record, and storing it would mean syncing it and noticing when the page under it changed. The models run on the device and are downloaded by the system, so this adds no host to the list under *Sandbox capabilities*. Translation does not work in the Simulator — try it on a device.
- **A listing row publishes the hall's name and nothing else** — no address, no place id — so nothing on the page the Following tab reads says what part of the country a date is in. `VenueRegions` gets there in two GETs per hall: `/places/search` finds it by the exact name the row printed (an exact match, for the reason a performer's name takes one), and the hall's own page publishes the address, which opens with its prefecture. The answers are cached per device, since a hall does not move — the address as well as the area, so a hall is read once for good (an address abroad is never asked again; only "the site files no such hall" is retried, after a month). The Following tab and the Me card look up a ration of halls (20) as they load, the filter sheet keeps going while it is open, and `learn(from:)` takes every address the library already holds for nothing. A hall whose address is abroad then has its clock settled by `settleClocks(for:)`: `VenuePlaces.placeUnplaced` first (only halls it has no answer for, never narrowed), and where that settles no clock, the country `VenueCountries` reads off the address. The clock is cached with the hall. `Region` is the site's own `area_id` grouping minus 海外 — abroad is the *absence* of a Japanese prefecture in an address, so an overseas hall is left unplaced rather than filed somewhere it might not be. The whole facet, as the `<select name="area_id">` on `/events` spells it, is 1 関東, 2 関西, 3 東海, 4 北海道・東北・甲信・北陸, 5 中国・四国・九州・沖縄, 6 海外 — it is written out in [Region.swift](Eventrail/Model/Region.swift) so nobody has to fetch the page to check, and the five cases cover all 47 prefectures exactly once. **Don't add a sixth area or split one.** The grouping is coarse on purpose: matching is done here from the prefecture at the head of the address, so a finer split would cost nothing to build and would stop the app answering the way the site answers.
- The count beside a name in performer search is the site's *fan* count, not an event count.
- A venue's own page prints 所在地, 電話番号, 公式サイト, 収容人数, 座席情報 and 会場TIPS as `gb_subtitle` sections, and members write them, so most halls leave several empty. The last two are a *link* rather than words — the label in them is "座席情報" and "ウェブサイト", and the answer is the href — and 会場TIPS is a list of exits and walking times whose `<br>`s become newlines before the tags are dropped, or it reads as one run-on sentence.
- **The app reads on its own only what has gone stale; the reader asking always reads.** Eventernote publishes no API and does stop answering an app that asks too fast, and this one was asking for the same unchanged pages over and over — every followed performer's listing on every launch. So what has been read is cached per device with the time it was read, and six hours — `Freshness.window`, one constant for every cache below — is where a copy goes stale: `FollowedDates` for the listings (a JSON file in Caches), `PageReads` for event pages, and `ListingCache` for performer and venue pages (one file per page in Caches, keyed by `PerformerLink.cacheKey`/`VenueLink.cacheKey`: who or what the page is about, and the listing up to its first past row plus whatever the reader scrolled on to). A performer or venue page opens on its cached copy at once and reads again only when that is stale; its own `.refreshable` always reads, and overrides the Following tab's, which is otherwise carried down the navigation stack onto it. A venue's refresh re-reads the hall's own page too, since members edit its address and tips; a billed name's search is never repeated once it has found someone. Opening the Following tab (and the Me card, which shows the same counts) reads only the stale listings; opening an event's sheet re-reads its page only when `EventStore.isStale` says so or it is not `isFullyDetailed`. A manual refresh is never held to the window — Following's pull-to-refresh (`FollowedDates.reload`) reads everybody, pulling on an event's sheet re-reads that one page (the sheet carries its own `.refreshable`, because a presenting screen's would otherwise be inherited through the environment and a pull there would re-read the whole Following list), and Refresh on the Me card reads every upcoming page as it always has (`needsReading` does **not** consult `PageReads`). Two rules hold throughout: **a failed read never costs what was held** — `reload` writes over the cache rather than emptying it first, and the Following tab and the sheet put a `RefreshFailureNote` under the cached copy instead of replacing it — and **a refusal stops the run** (`EventernoteClient.Failure.isRateLimited`, HTTP 429 or 503), because the next request would be refused too. Only a read that *landed* is stamped, so a page that failed stays stale. **A refresh the reader asked for always ends in a notice; one the app started by itself ends in one only when it failed.** A pull, the Me card's Refresh, Settings' venue refresh and a Try Again are the reader asking; opening a page for the first time, opening a stale one, coming back to the app and the Welcome screen's first import are the app keeping itself current, and an "Updated" over every page opened would be noise. Every caller goes through `RefreshNotices.report(_:byHand:)` — `RefreshNotices` is one `@Observable` in the environment, and the `RefreshNotice` constructors cover Following, an event sheet, the library, a performer's or hall's page and Settings' venue refresh. A pull that joins a read already running says what that read came to as a pull would (the performer and venue pages keep the read's notice as its task's result, so each caller decides). It says "Updated" or "Update failed" and the reason, nothing more — what arrived is on the screen behind it. It is a Liquid Glass pill along the bottom, drawn by `.refreshNotices()` on each tab's own content (whose safe area already stops above the floating tab bar, so no bar height is hard-coded) and again inside every sheet that can start a refresh (the event sheet through `eventSheet`, and Settings), because a sheet covers the tab; `sheetsShowing` keeps the tabs quiet meanwhile so one notice is not drawn twice. Pull-to-refresh exists only where the reader is looking at something read from the site — Following, an event's sheet, and a performer's or a hall's page. The Event Passport deliberately has none: it is the reader's own record read back. A pull on Following that lands while a read is already going joins that read and reports it (`FollowedDates.running`) rather than returning with nothing to say. A screen opened on a fresh copy reads nothing and posts nothing. **A read started from `.refreshable` runs in a `Task` of its own** (`FollowedDates.run`, `EventStore.reloadDetail`, `ListingCache.read`): SwiftUI cancels a refresh action when the screen under it changes mid-refresh, and a cancellation that reached URLSession ended the event sheet's pull in neither an answer nor an error — no notice at all. A new refresh anywhere should post one too. Images go through `ImageCache` (an actor; decoded copies in memory, bytes in Caches with the host's `ETag` beside them). The host files a flyer under the event's id, so a replaced flyer keeps its URL: a copy is drawn with no request for `Freshness.window` and then revalidated with `If-None-Match`. **A stale copy is still drawn at once** (`ImageCache.storedImage(for:)`) and revalidated behind it; the picture changes only when the host sends different bytes, and an unchanged answer hands back the very object already in memory so `CachedImage` leaves it alone. Waiting on the host first left every flyer a placeholder each time the window ran out, and for a whole timeout when offline. A screen refreshed by hand sets `EnvironmentValues.imagesCheckedSince`, and every `CachedImage` under it whose host was last asked before then asks again as it draws — so a pull resets the window on the flyers as well as the rows, once per flyer rather than once per scroll. **Stale is checked on the way back to the foreground as well as on the way in**: the Following tab, the Me card, an event sheet and a performer's or hall's page each re-run their stale check when `scenePhase` returns to `.active`, so a screen left open while the reader was away does not sit past the window. Settings' Clear Cache empties the listings, the page stamps, `ListingCache`, `ImageCache` and `VenueRegions`; `VenuePlaces` deliberately answers to it not at all — a hall's pin comes from Maps and two donated services rather than from Eventernote, a hall does not move, and rebuilding it is a run of hundreds of searches, which is what its own Refresh row under Location is for.
- Every accessor is failable by design: a changed template yields a missing field or a dropped row, never wrong data. The one place "missing" is not allowed to mean "none" is a listing's own block: the site prints no list at all where nothing matches, so `EventernotePages.events`/`performers` read a missing block as empty only on a page that closes with the smartphone template's `gb_foot_menu`, and throw `.unreadable` otherwise — a maintenance page, a captcha or the desktop template would otherwise read as a performer with no dates and be cached that way for the whole window. The footer is not enough on its own where the page also counts what it found (a positive total over no list is a renamed block), and a list that printed rows but gave up none of them throws too: one dropped row is a changed field, every row dropped is changed row markup.

## What the reader records

`Tracking` is the reader's private record for one event: whether the ticket is in hand, where they sat (`seat`, one free line — a hall prints 1階 L列 23番, an arena a block and a number, a live house an entry number and no seat at all), what it cost (`cost`, whole yen; nil is "not written down", which is not the same as free), how many entries they put into the lottery for the night (`lotteryEntries`; nil is "not written down", and so is 0 — a night applied for no times is a night with no lottery on it, unlike a free ticket, which is an answer), and a note.

- **Interest and attendance were dropped on purpose.** Both asked the library a question it already answers: an event is in the library because the reader means to go, and an event in the library whose date has passed is one they went to. `EventStore.status(for:)` works the badge out from where the event stands — in the library or not, past or ahead, ticket or no ticket — and `attendedEvents` is simply `library.filter { !$0.isUpcoming }`. Don't re-add a field for either; an event they did not go to is one they take out of My Events.
- **Every field is merged on its own**, so `Tracking` carries `edits`, a date per field — see *Persistence and sync*. A field added here has to be named in `Tracking.Field` too; the switches in `sameAnswer(for:as:)` and `take(_:from:)` will not compile until it is.
- **`Tracking` decodes every key as optional, by hand.** The synthesized decoder treats a key an older record lacks as an error, and an error thrown there is not one record lost but the whole archive — `LibraryFile` has nothing to read and the library comes up empty. That is what the lottery count did before the hand-written `init(from:)` in the extension existed. Encoding stays synthesized, and the init lives in an extension so the memberwise one survives. **Any field added here must be decoded with `decodeIfPresent`.** `LibraryArchive` says the same thing about its own new keys and answers it by making them optional.
- `YenAmount` and `EntryCount` are `ParseableFormatStyle`s because no built-in style takes an optional and an emptied field has to read back as nil rather than 0. Both read the digits out of whatever was typed, so the ¥ and the separators the style itself wrote survive an edit, and a full-width １２３４ from a Japanese keyboard is the same number as 1234.

## Where a hall is

Eventernote publishes a hall's name and its address and no coordinate, and this app does not run the Google script behind the site's own `map_canvas`. So a placing is worked out here, in three tiers, all behind [VenuePlaces.swift](Eventrail/Services/VenuePlaces.swift) and keyed by the hall rather than the event — two events at the same hall are one question. The answers are kept per device, because a hall does not move.

1. **Apple Maps**, asked for the hall by name and judged by the address: a place is the hall when the address Maps publishes for it is the address Eventernote published. Nothing judges an answer by reading its name back, which is hopeless — Kアリーナ横浜 is "K-Arena Yokohama" on an English phone, and a search for メルセデス・ベンツアリーナ returns a Mercedes dealer in Nara. This is the only tier that yields an `MKMapItem.identifier`, so it is the only one that can open the hall's own card in Maps.
2. **[JapanAddresses.swift](Eventrail/Services/JapanAddresses.swift)** — the address search 国土地理院 publishes — where Maps answers nothing. That case is commoner than it sounds and often has nothing to do with the hall: MapKit's search is served by whichever provider covers wherever the *device* stands, and the one serving mainland China carries no Japanese venues, so a reader in Shanghai would otherwise have every hall in their library go unplaced. The register answers the same from anywhere, and grades its own match — only 7 and up (the block, the building number) is believed.
3. **[VenueBuildings.swift](Eventrail/Services/VenueBuildings.swift)** — OpenStreetMap, asked which building at the block the register placed carries the hall's name — is an upgrade rather than a rescue, and every candidate is held against a coordinate the register already vouched for (800 m). It is governed by the per-device `preciseVenuesEnabled` switch in Settings.

**On a phone whose Maps is the mainland-China provider, Maps is asked only about the mainland.** That provider has no Japanese venues and, asked about a hall in Seoul, offered a mainland place that merely shared the number 145 with the address — the address check compares numbers, and one shared number is all it takes. So `VenuePlaces` first asks Maps once per launch whether it can see Japan (`mapsSeesJapan()`: a search for 東京駅 that lands in Japan or does not), and where it cannot: a hall in Japan skips Maps and goes to the register (then OpenStreetMap under the switch, as ever); a hall whose address `VenueCountries.isMainlandChina` reads as the mainland is asked of Maps with no hint; every other hall abroad — Korea, Hong Kong, Macau, Taiwan and beyond — is asked of OpenStreetMap directly (`VenueBuildings.place(named:at:country:)`: the address as the anchor, then the named building within 2 km of it, or the name alone only inside a country the address plainly names). That search is governed by `preciseVenuesEnabled` like every other OpenStreetMap request — **the switch off means OpenStreetMap is never asked anything**, so on that phone a hall in Japan stays at the register's block and one abroad stays unplaced — and it keeps the rest of the OpenStreetMap rules: only from a sheet or the Settings refresh, never from an import. Both refusals are `Deferred`, which writes nothing down, so the first sheet or refresh after the switch goes on asks again. OpenStreetMap carries no zone, so such a hall is dated by its country where the country keeps one clock (`VenueCountries.timeZone(forCountry:)`) and left on its written clock otherwise. The mainland and country readings are text heuristics over the published address, and no API can replace them: the addresses that need them are the ones members wrote in Japanese kanji and katakana, which is exactly what OpenStreetMap fails to find. They cover every province-level division of Korea, Taiwan and the mainland and the districts of Hong Kong and Macau, in local script, kanji, katakana and English; a name Japan shares (台東, 大田, 桃園) is listed only with its suffix. A miss costs a fallback, never a wrong country. The mainland reading — a province or city *with* its 省/市 suffix, since Taipei's streets are named for mainland cities — and leans towards "not the mainland", which costs a slower answer rather than a wrong country. On any other provider nothing here changed. OpenStreetMap files Hong Kong and Macau under `cn`, so `countrycodes=hk` finds nothing: those two are searched inside a bounding box instead (`VenueCountries.searchScope(for:)`). **The one name-only search** is a fallback for a hall whose page published no address at all (歷山酒店-宴會廳): where the *event's title* names a city `VenueCountries.country(of:)` knows (香港, ソウル, 台北…), OpenStreetMap is asked for the name — then its shorter forms (`VenueBuildings.shortenings(of:)`) — inside that country or box only, on every provider, under the same switch and the same sheet-or-refresh rule. A title naming nowhere leaves the hall unplaced, as before. **That provider draws its tiles in GCJ-02**, and its own search answers come in GCJ-02 too, but an OpenStreetMap coordinate is WGS-84 and MapKit does not shift a pin it is handed. So `Answer.placing` shifts an OpenStreetMap answer through `MainlandOffset` wherever the answer came back in `cn` (the mainland, Hong Kong and Macau, as OpenStreetMap files them), `hk`, `mo` or `tw` — by the country the answer carries (`Answer.country`), not by the address reading, so a mainland hall the lists missed is shifted too; answers written before there was a country fall back to boxes round Hong Kong, Macau and Taiwan — while `VenuePlaces.mapsIsMainland` (the last probe, kept across launches) says the phone is on that provider — as it is drawn, never as it is stored, so the same answer lands right on another provider. All three were checked on a phone in Shanghai, and so were Korea and Japan — which that provider does **not** shift: don't add them. Korea once looked off, and it was a name, not a coordinate system — see the shortenings below. A name is shortened by what its break means: after a **space** the part after it is tried first (高麗大学校 化汀 体育館 → 化汀 体育館, since 高麗大学校 alone is the whole campus, 800 m from the arena), after a **dash** only the part before it (歷山酒店-宴會廳 → 歷山酒店, since 宴會廳 alone is any banquet hall in the city). A Korean address is often written in kanji and katakana rather than Hangul (畿道高陽市一山西区キンテックス路 is KINTEX), so `VenueCountries.country(of:)` also reads Korea's provinces and the suffixes only its cities carry (広域市, 特別市) — never a bare city name Japan shares, like 大田. Rulesets 9 to 12 re-ask only answers outside Japan (`japanRuleset`).

**Who is allowed to ask, and when, is the load-bearing part.** A hall is looked up when the reader opens an event at it — one question, asked because somebody is waiting. The calendar mirror reads what has been found and searches for nothing itself: a run of hundreds of searches is what got this app throttled into placing nothing at all. An import places the halls it brings in (`EventStore.placeArrivedVenues`), an event added by hand from Search is placed on the same terms through a one-at-a-time queue (`placeAdded`, which reads the event's own page first wherever the search row carried no address), and `VenuePlaces.refresh(_:)` from Settings is the one way to ask about everything — paced at 500 ms, and mirroring the calendar once at the end rather than per hall. Tier 3 is reached only when the reader asks: the sheet in front of them, and the Settings refresh they started. OpenStreetMap's policy allows one request a second across all of an app's users, discourages bulk geocoding, and tolerates a small one-off run from one device made one request at a time with the results kept — so `VenueBuildings` paces itself at 1.1 s, each hall is asked once for good (`Answer.triedBuilding`, carried across refreshes by `VenuePlaces.carrying(_:from:)`), a refusal stops the rest of the run's narrowing, and an import (`placeUnplaced`) **never** narrows. A block settled while narrowing was not allowed is narrowed the first time a sheet opens it (`VenuePlaces.narrowed(_:for:)`). Crediting 国土地理院 and OpenStreetMap is a condition of use and is done in [AboutView.swift](Eventrail/Views/AboutView.swift) — don't drop that footnote.

**A placing also settles which clock the hall keeps**, because Maps carries a zone with the place and the search is already being made. `VenuePlaces.timeZones(for:)` reads those back for the whole library without asking anything, the same way the calendar mirror reads placings, and `EventStore.retimeEvents()` applies them wherever a placing lands — an import, an event added by hand, a sheet, a refresh, a merge, a restore, and once at launch. Only a hall *outside* Japan is ever asked about: Japan is one zone, so a placed Japanese hall answers itself from its own coordinate, and the handful of halls a reader has abroad are re-asked exactly once (`Answer.needsZone`) rather than the whole cache being re-read. Maps answering with no zone at all leaves the hall on Tokyo time rather than guessing.

`VenueRegions` is a different question with a similar name: not where a hall is, but which of the site's five areas it is in, for the Following tab's filter. It reads Eventernote's own pages rather than any map service.

## The Event Passport

[EventPassportView.swift](Eventrail/Views/EventPassportView.swift), reached from the Me tab, is the reader's own record of where they have been: a map of the country with every hall they have stood in, and what the library adds up to around it. [PassportStats.swift](Eventrail/Model/PassportStats.swift) is one pass over one slice of it.

- **Everything on it is read off `EventStore.attendedEvents`.** Nothing here asks Eventernote anything, and nothing here is a second record the reader has to maintain — the same argument that removed the attendance field.
- Computed on the screen rather than stored, and cheap enough to be: a handful of passes over a few hundred events. Storing it would mean keeping it in step with every note, every import and every merge; a `let` cannot go stale.
- `PassportScope` is all-time or one year, and a year the reader has nothing in is never offered. It is deliberately not remembered between visits — a filter left on from a fortnight ago would have somebody reading one year and believing it was all of them.
- Every total says what it was counted over rather than implying it read every night: `timedEvents` beside `totalDuration`, because Eventernote publishes a finish time for a minority of dates, and the lottery total beside the count of nights it was written on.
- **A night is not always at a hall.** Eventernote files streams, undisclosed rooms and "somewhere abroad" under placeholder venues whose names open with `!_` (`!_国内外各所 (ライブビューイング等)`, `!_東京都内某所`). `Event.isAtHall` is false for those and for an empty venue: the night still counts, but adds no hall, no prefecture and no pin, and `VenuePlaces.Venue` refuses to look one up by the same test (`Event.namesHall`), save that a hall with no name and a published address is still asked about.
- `PassportStats` takes `tracking` as a closure rather than the store, which is what keeps the whole type `nonisolated` and testable with no `EventStore` behind it.

## Persistence and sync

`LibraryArchive` is the single value holding everything the reader owns. It is written to a plain JSON file in Application Support, deliberately *not* SwiftData — that schema is still unsettled, and this keeps what the reader adds across launches without committing to a store. `EventStore` holds one `archive` and derives `library` from it, so a merge from another device is one reviewable operation.

iCloud sync goes through [CloudSync.swift](Eventrail/Services/CloudSync.swift) on `CKSyncEngine`, in a `Library` zone of the reader's **private** CloudKit database (container `iCloud.moe.shawn.Eventrail`). Things that matter:

- **Every record the reader owns is a `Stamped<Value>`** — the value plus when it changed. Merges are last-writer-wins *per record*, never per file, because a whole-blob overwrite would silently erase a note typed on the other device. `LibraryArchive.merging(_:)` is where this lives; the merge is symmetric.
- **A tracking record is settled one answer at a time**, because it is the only record that holds more than one. The same argument, one level down: a cost typed on the iPad after a note was typed on the phone would carry the iPad's whole record — its older copy of the note included — over the newer note. So `Tracking.edits` keeps a date per field and `Stamped<Tracking>.merging(_:)` settles each of the five against the other device's copy of that one. A field missing from `edits` is exactly as old as the record holding it, which is what an archive written before this existed says about all five and what an answer written in the same breath as its record says about itself — so only an answer *older* than its record is written down, and a record edited once carries nothing there. Two devices editing the **same** answer between syncs is still the later write: nothing can know which the reader meant, and a conflict copy of a note is a second record to reconcile by hand. `EventStore.setTracking` writes through `edited(to:)` so the answers the reader left alone keep their age, and a restore raises a backup's record with `restamped(at:)` rather than carrying the file's own dates into a merge against this device.
- Following a performer is the reader's record too, so `follows` is stamped and tombstoned like the rest. It is keyed by Eventernote's actor id and is still *not* the favourite list the reader's Eventernote account holds — that one stays read-only here. An import brings the second in line with the first (`EventStore.adoptFollows`) and only ever adds: anyone the account still favourites is followed here, tombstone or not — asking Eventernote again is the reader's way back to somebody they unfollowed and then wanted again, and unfollowing for good means unfavouriting them on the site too. A performer *dropped* from the favourites on the site is still never unfollowed here, because that would also reach everyone followed in Eventrail alone. The key is optional on `LibraryArchive` because the synthesized decoder does not fall back to a property's default, so a new non-optional key would read every existing file as corrupt.
- `followedPerformers` sits beside `follows`, keyed the same way: who each followed actor id *is*. Eventernote's facts rather than the reader's, so it carries no timestamp and merges like `events`; it is pruned once the follow is gone. Without it the Following tab could neither name a performer nor address their listing. A follow recorded before this existed has no profile and is skipped rather than shown as a nameless row — an import backfills it if the account favourites them.
- **Removals are tombstones** (`membership[id] = Stamped(false)`), not deletions, and **they are never pruned** — nor are the favourite, follow and cleared-tracking ones. Dropping the key would let the next merge resurrect the event; dropping it after a while (the old 180 days) let a device that slept through that while resurrect it anyway, since it still held the old yes and found no no to lose to, and nothing a timestamp says can tell a pruned key from one that never existed. A tombstone is an id and a date. `pruned()` still drops event facts nothing points at, the profile of anyone no longer followed, and Following reads whose night has gone.
- **A tombstone answers for the reader's devices, not for Eventernote** — the premise at the top of *The Eventernote import*. It stops a *merge* from handing a removed record back; it does not stop an *import*. `EventStore.adopt` re-adds an event the linked account still lists and `adoptFollows` re-follows a performer it still favourites, and re-adding by hand (`toggleLibraryMembership`, following from a performer's page) has always worked the same way.
- Event facts are not the reader's, so they need no stamp of their own — but the page changes under them, so two copies are settled by `Event.readAt`, when that copy's page was read (`LibraryArchive.settle`): the later read's answers stand, gaps included — a start time or a 概要 missing from a read of the page (at a `detailFormat` no older than the copy it lands on) was taken off the page, and `Event.merging` clears it; only a listing row, or a read by a build that looked for fewer fields, has its gaps filled from the other copy. The hall's address and capacity always fill gaps, since they come from a second page whose failure an import shrugs off. Without it the merge took whichever copy it was handed, and a device that had just read a moved start time took the other's older one back. An undated copy counts as the earlier; between two copies neither of which read the page, the more complete import (`isDetailed`) wins as before.
- **One record per thing** ([CloudRecords.swift](Eventrail/Model/CloudRecords.swift)): `event.<id>` carries that event's membership, tracking, favourite, Following read and facts; `performer.<actor id>` the follow and the profile; `settings` the linked account, recent searches and import dates. Each record is a *slice* — an ordinary `LibraryArchive` holding only that one thing, zlib-compressed JSON in `encryptedValues["payload"]` beside a plain `format` — so an arriving record is folded in by `LibraryArchive.merging(contentsOf:)`, the same merge a whole archive always had, and every rule above holds record by record without being written twice. **A new field on a slice that an older build would mis-read means bumping `CloudRecord.currentFormat`**; a record in a newer format is held verbatim (`Memory.held`), never overwritten, retried after an update, and Settings says to update the app meanwhile.
- **Saves are merged, never overwritten.** What changed is found by fingerprint (`CloudRecord.digests`: SHA-256 of each slice as sorted-key JSON, against what was last sent or received), so an edit sends the one record it touched. A save that lands on a record another device changed first comes back as `serverRecordChanged` with the server's copy; that copy is merged in and the merge is sent in its place. A write only ever speaks for the record it names, and a fresh install names nothing, so there is no whole library for a write to replace. A first sync still fetches before it sends (`CloudSync.sync(for:)`), so a second device updates the records it finds rather than colliding with all of them. **A deleted record says nothing about the library**: a removal is a save of a tombstone, a record is deleted only once its slice prunes to nothing, and an arriving deletion is ignored beyond its system fields, since every device prunes the same way on its own.
- **An account change or a deleted zone turns sync off on this device** (`EventStore.cloudStopped(_:)`). A `signOut` or `switchAccounts` from the engine means the library here was gathered under an account that has left, and merging it into the next one would put one reader's records in another's iCloud; the zone deleted or purged means the reader deleted Eventrail's data from iCloud, and sending it all straight back would undo that. `encryptedDataReset` is the exception — the keys went, the data here is whole — and re-sends everything. Turning the switch off (`CloudSync.stop()`) forgets the engine state, system fields and fingerprints, so turning it back on reads the store afresh.
- What the engine needs between launches — its state serialization, each record's system fields, the fingerprints and held records — is `CloudSync.Memory`, one JSON file (`cloudkit.json`) beside the library, written a second after the last change.
- `iCloudSyncEnabled` is a **per-device** preference in `UserDefaults` and deliberately does not sync — turning it off on a phone must not turn it off on the iPad. It is **off until the reader turns it on**, like `calendarSyncEnabled`: copying what they have written into their iCloud is theirs to say yes to, and a switch found already on is not an answer anybody gave. So a fresh install reaches iCloud for the first time when the Welcome screen's switch or Settings' says to.
- **An unreadable library file is set aside, never saved over.** `LibraryFile.load()` moves a file it cannot decode to `library.unreadable-<stamp>.json` beside it and starts empty; every launch tries those again and merges back any this build can now read, deleting it only then. Settings' Restore row says so while one is still unread (`EventStore.unreadableLibraryFiles`). Before this, one field decoded wrongly emptied the library and the next save made it permanent. A recovered copy is deleted only after the merged library has been saved (`LibraryFile.discard(_:)`), not as it is read. And a file that will not *open* — a device not unlocked since it started — or that will not decode and cannot be moved aside is left where it is and blocks every save (`EventStore.libraryFileIsBlocked`): each save reads it again first and folds it in once it opens, and Settings says so meanwhile. The empty library that comes up beside it is not the reader's.
- `LibraryFile.load()` falls back to `LegacyArchive` for files written before records carried timestamps. Don't remove that until you're sure no device holds a pre-sync file.

`LibraryBackup` is the other copy: one file the reader exports and keeps themselves, with no size ceiling. Sync and backup are deliberately different answers — sync keeps devices agreeing, so a removal travels; a file is the one copy nothing done in the app afterwards can reach.

The file is the app's own format, `.eventrail`: the eight bytes `EVNTRAIL`, a version byte, then the archive as zlib-compressed JSON. The signature makes a wrong file wrong before anything is decoded, and the extension keeps a backup from looking like a document any app may open and edit. It is a container, not encryption. The type is declared in [Info.plist](Info.plist) and reached in code as `UTType.eventrailBackup`; the importer also accepts `.json` so the app's own `library.json`, lifted off a device, can still be read. Three things follow:

- **A new field means a new version byte.** `LibraryBackup.currentFormat` is 7 today. It guards only the container; `LibraryArchive` still decodes its own older files, and a file whose version byte is higher than this build's is refused rather than read with its unknown fields dropped.
- **Opening a backup from Files is a second entry point, not a second implementation.** `CFBundleDocumentTypes` in [Info.plist](Info.plist) claims the type (`LSHandlerRank` `Owner`), `INFOPLIST_KEY_LSSupportsOpeningDocumentsInPlace` has it read where it sits rather than copied into an Inbox folder the app would then have to tidy up after, `RootView` receives it with `onOpenURL`, and both it and Settings hand the file to the same `restoringBackup(_:asking:)` modifier — which asks first only for a file that arrived from outside the app. The type conforms to `public.data` **and not `public.archive`**: conforming to the latter handed the file to the Files app's own archive handling, which failed to unpack it and refused with "inappropriate file type or format" instead of passing it on.
- **Export goes through the share sheet, not `fileExporter`.** `ENABLE_USER_SELECTED_FILES = readonly`, so the app may read a file the reader picks and may not write one. Settings writes the backup into the temporary directory and hands `ShareLink` that URL, rewriting it whenever `EventStore.revision` changes. A `Transferable` would write it more lazily, but handing the share sheet a file that exists is what makes the system compose its own preview — name, kind and icon — instead of leaving a screen to draw a picture of a file.
- **Restoring is `LibraryArchive.restoring(_:)`, not `merging(_:)`.** A plain merge would lose to a tombstone, so a backup restored after "Delete All Events" would bring back nothing. A restore raises the backup's *positive* records over this device's no — the same licence an import has — and only those: a note this device still holds keeps whichever copy was typed later, and nothing the file lacks is dropped. A restore adds; it never erases.

`EventStore.removeAllEvents` empties tracking as well as membership and favorites, and turns every Following date back to unread, writing an empty `Stamped(Tracking())` rather than dropping the key, for the same reason a removal is a tombstone. A single removal still keeps the note — the two are different promises.

**Capability:** sync needs the iCloud (CloudKit) and Push Notifications entitlements in [Eventrail.entitlements](Eventrail.entitlements) at the repo root (outside the synchronized group, so it is not bundled as a resource), wired via `CODE_SIGN_ENTITLEMENTS` in both configurations: `icloud-services` CloudKit, the container `iCloud.moe.shawn.Eventrail`, and `aps-environment` for the silent pushes the engine relies on — with `UIBackgroundModes` `remote-notification` in [Info.plist](Info.plist), since it has no build setting. Simulator builds sign locally and work as-is; a **device build needs iCloud (with the container) and Push Notifications enabled on the App ID in the developer portal**, otherwise signing fails. **The schema is created in the Development environment by the first save and must be deployed to Production in the CloudKit Console before a TestFlight build can sync** — TestFlight and the App Store talk to Production only.

## The calendar mirror

[CalendarSync.swift](Eventrail/Services/CalendarSync.swift) writes the library into one calendar Eventrail creates and owns. A calendar the reader made is never touched, so turning the mirror off is a single deletion rather than a hunt through a diary the app does not own. Past events are mirrored as well as upcoming ones — a calendar is a diary as much as a plan.

- **Off by default, and off is quiet.** Until `calendarSyncEnabled` is on, the app never reaches EventKit at all: only `mirror(_:)` and `stop()` ask for permission, and the second returns before asking unless a calendar of the app's own was actually made. So the system's permission sheet is the answer to that one switch and to nothing else. It is a per-device preference, like `iCloudSyncEnabled`, and so is the calendar identifier it remembers — an identifier belongs to this device's calendar database and means nothing on another one, so it is deliberately not part of the synced archive.
- **The identifier is a cache, not the answer, and `calendar()` adopts before it makes.** The calendar usually lands on the reader's iCloud account, which *does* sync: a device with nothing in `UserDefaults` that goes straight to making one produces a second "Eventrail" beside the one already synced to it, each device mirroring the whole library into its own — every night twice, under one name. The same gap opens on a single device whenever the identifier stops resolving (a restore, iCloud handing the calendar back under a new one), and there the entries already written are not even reachable to be corrected, because every search is scoped to the calendar it was handed. So `adoptableCalendar()` takes an existing one when it is named as this app names its own, is writable, and holds **nothing but entries whose URL points at Eventernote**. That last test is load-bearing: the mirror removes whatever no longer answers to an event in the library, so adopting a calendar of the reader's own that happened to share the name would empty it. Don't relax it to a title match. Adopting stops a second one from being made; `discardDuplicates(of:)` removes the ones already made, by that same test, so a pair written before this existed converges — the other device's identifier stops resolving and its next mirror adopts the survivor.
- One consequence, accepted on purpose: an iCloud calendar is one object rather than one per device, so turning the mirror off on the phone takes it off the iPad until that device's next mirror makes it again. A flap that settles itself beats two calendars of one name.
- The entry carries the event's own zone, which is the hall's — see *The Eventernote import* on why a night abroad is re-read rather than re-imported. So a Taipei date sits at the Taipei hour in the reader's diary wherever they are reading it from.
- Entries are matched by the Eventernote page URL rather than by title: a title can be re-published, and an entry the reader dragged elsewhere is still the same event.
- **The sweep for entries is fixed (30 years back, 10 ahead), not measured from the library.** The entries worth finding are the ones whose events have *left* it, and nothing in the library can point at those: a range starting at the earliest night still held would never reach the night just removed from in front of it, and emptying the library would collapse the range to ±4 years and strand everything older in the reader's diary forever. The library's own span still widens the sweep where it falls outside. EventKit refuses a window longer than four years, so it is read in chunks of that size — ten predicates against one calendar the app owns.
- **Every entry carries one alert, at the door time**, wherever Eventernote published one — past nights included, so the diary records the hour the reader had to be there. No switch governs it: the door time is the event's own fact rather than a preference, and Calendar's per-entry alert remains the reader's to change. (There is no travel-time field in EventKit to write instead.)
- **A night with no published start is an all-day entry, written floating** (`CalendarSync.floatingDay(of:in:)`): its hall's day at this device's midnight, no zone, and compared by the day rather than the instant. Handed `Event.date` as it stands — midnight on the hall's clock — it would land on the evening before on a phone west of the hall, and an all-day entry reads its zone back as nil, so the old comparison found it moved on every mirror.
- Where a start time was published and a finish was not, the entry is given `assumedLength` (3 h) so it has a length at all; the detail sheet still shows nothing where the site published nothing. EventKit refuses a search window longer than four years, so a wider range is read in chunks of that size.
- A placing is read from `VenuePlaces`, never searched for here — see *Where a hall is*. An entry gets a structured location where the hall has been placed and the hall's name as text where it has not, and `EventStore` re-mirrors once after a run of placings rather than once per hall.

## The look

The UI comes from the Claude Design canvas "Eventernote Mobile App Design" (`Eventrail.dc.html`), which specifies a Liquid Glass treatment in light and dark. All glass goes through `glassBackground(in:interactive:)` in [WashBackground.swift](Eventrail/Views/Components/WashBackground.swift) — that one helper also holds a `#if os(visionOS)` material fallback, kept from when the target still built for visionOS. Palette colours are colorsets in `Assets.xcassets` generated from the design's oklch values, with light and dark variants.

Every screen sits on `washBackground()` — most as a `ScrollView` of glass cards, the library and the half-lists as a plain `List` with `scrollContentBackground(.hidden)` so the same wash shows through. The app icon is an Icon Composer document at `Eventrail/AppIcon.icon`. `AppIconBadge` in [AboutView.swift](Eventrail/Views/AboutView.swift) draws it from a separate `AppIconArt` image set, because the catalog holds an Icon Composer icon as a layer stack rather than a picture — `UIImage(named: "AppIcon")` throws on one, and the flattened PNGs iOS writes beside it top out at 120 pt. A changed icon means re-exporting that image set and `Design/AppIcon.png` too.

## Build and run

```bash
# Build for the simulator
xcodebuild -scheme Eventrail -destination 'platform=iOS Simulator,name=iPhone 18 Pro' build

# Clean build folder when the project file or build settings change
xcodebuild -scheme Eventrail clean
```

**Xcode 27 ships no `Simulator.app`.** The bundled simulator UI is now
`DeviceHub.app` (bundle id `com.apple.dt.Devices`), and the whole
`Xcode.app/Contents/Developer/Applications/` directory is gone — Instruments,
Create ML, FileMerge and the rest moved up to `Xcode.app/Contents/Applications/`.
So `open -a Simulator` fails with "Unable to find application named 'Simulator'";
launch the UI as `open -b com.apple.dt.Devices` instead. Any tool that hardcodes
the old name breaks here — SweetPad's "Launch" task was the one this repo hit, and
a shell script under `.vscode/` stood in for it until SweetPad was fixed. SweetPad's
own build and launch tasks work now, so [.vscode/](.vscode/) holds nothing but its
settings; don't re-add a launch task or a runner script without a reason.

`xcrun simctl` is **unchanged** — boot, install, launch and `--console-pty` all
still work exactly as before. Only the app that draws the window was renamed, so
prefer `simctl` for anything scriptable and treat DeviceHub as just the window.

Don't hardcode a device name without checking `xcodebuild -scheme Eventrail
-showdestinations` first. The installed runtime is iOS 27.0 and the simulators
are iPhone 18 Pro, iPhone Air and the iPads; the `iPhone 17` this file used to
name no longer resolves, and a missing name fails the build rather than falling
back to another device.

```bash
# Run the unit tests
xcodebuild test -scheme Eventrail -destination 'platform=iOS Simulator,name=iPhone 18 Pro'

# Run one suite or one test
xcodebuild test -scheme Eventrail -destination '<dest>' -only-testing:EventrailTests/TrackingTests
xcodebuild test -scheme Eventrail -destination '<dest>' -only-testing:EventrailTests/TrackingTests/twoDevicesEditingDifferentAnswersKeepBoth
```

[EventrailTests/](EventrailTests/) is a Swift Testing bundle hosted by the app (`TEST_HOST`), so it reaches internals through `@testable import Eventrail`. Like the app's own folder it is a synchronized group: a new test file dropped in is picked up with no project-file edit. The shared `Eventrail` scheme in `xcshareddata/xcschemes/` is what puts it under the Test action. The tests cover the pure logic — the Eventernote page readers (against hand-written pages carrying the template's markers, never a fetched page), `HTMLCursor`, `Event`'s merge and re-timing, `Tracking`'s decoding and per-answer merge, `LibraryArchive`'s merge, prune and restore, the backup container, `Region` and `PassportStats` — and nothing that touches the network, iCloud, EventKit or MapKit. `Fixtures.event(...)` builds an `Event` naming only the fields a test is about. `#expect` cannot wrap a mutating call (an `HTMLCursor` advance, say); take the result into a `let` first.

## Branches and releases

**Every change goes on `main`. `release` is what testers run, and it is only ever advanced by a pull request, on Shawn's word.** Work and commit on `main` directly — a fix does not need a branch of its own. Xcode Cloud starts on branch changes to **`release`**, so nothing reaches TestFlight until that pull request is merged:

```bash
# ordinary work — this is all of it
git switch main
# edit, build, commit
git push

# only when Shawn says a build should go out
gh pr create --base release --head main --title "release: <what is in this build>"
# merged on his word; Xcode Cloud builds and distributes from release
```

**Don't open that pull request unasked, and never push to `release` directly.** Deciding that a batch of work is ready for testers is his call, not something to infer from the work looking finished; the PR is where he sees what the build would contain before it goes.

- **Keep `main` buildable anyway.** Nothing else watches it, so a broken `main` is only found when a release PR is opened. Build before pushing.
- **A hotfix branches off `release`**, not `main`, whenever `main` is carrying unfinished work: `git switch -c fix/<summary> release`, open its PR against `release` to ship, and merge it into `main` too so the fix is not lost at the next release.
- **A pull request into `main` is still welcome for anything worth reviewing** — a large feature, or a change whose diff wants reading. It is not required for ordinary work. Where one is opened, name the branch for the commit type it carries (`feat/`, `fix/`, `docs/`, `test/`, `refactor/`, `chore/`).
- **Pull requests are written in English** — title and description alike, whichever language the conversation that opened them was in, the same as commit messages.
- **Xcode Cloud builds what the repository holds**, so a change that only exists in local Xcode state — a scheme, a build setting, a file Xcode has not written into the project — fails there while it builds here. Its own record of what to build is `Eventrail.xcodeproj/xcshareddata/xcodecloud/manifest.json`, and `xcshareddata/` is tracked for that reason; `xcuserdata/` is the ignored one.

## Commit messages

Every commit message subject must follow:

```text
<type>: <concise imperative summary>
```

Examples:

```text
feat: add provider-based custom filters
fix: audit Google Drive restore downloads
docs: document production deployment
test: cover stale provider cache fallback
refactor: isolate subscription metadata handling
chore: update development dependencies
```

## Project structure conventions

- The `Eventrail` group is a **PBXFileSystemSynchronizedRootGroup** (`objectVersion = 90`). New `.swift` files dropped anywhere under [Eventrail/](Eventrail/) are picked up automatically — do **not** hand-edit `project.pbxproj` to register sources. Only build settings, targets, and capabilities need project-file edits.
- `Eventrail.xcodeproj/xcuserdata/` is user state and is checked in here by accident of the initial commit; avoid touching it.
- [Info.plist](Info.plist) at the repo root holds the two keys that cannot be expressed as build settings: `UTExportedTypeDeclarations` and `CFBundleDocumentTypes`, both for the `.eventrail` backup type. `GENERATE_INFOPLIST_FILE` stays `YES` and `INFOPLIST_FILE` points at it — Xcode merges every `INFOPLIST_KEY_*` setting into that file rather than replacing it, so the usage strings, the scene manifest and `LSSupportsOpeningDocumentsInPlace` still come from build settings. Anything that *can* be a build setting should be one: opening the target's Info.plist in Xcode rewrites the file in its own canonical form and **strips every XML comment**, so a reason written in there does not survive the next editor visit — it belongs in this file. It sits at the root beside the entitlements, outside the synchronized group, so it is not also bundled as a resource.
- `INFOPLIST_KEY_ITSAppUsesNonExemptEncryption = NO` answers App Store Connect's export-compliance question for every upload ("None of the algorithms mentioned above"). It is true because the only encryption is the system's own HTTPS through `URLSession`; `CryptoKit` is used for SHA-256 cache file names, which is hashing, and a backup is compressed rather than encrypted. **Adding encryption of the app's own — encrypting a backup, say — means revisiting this.**

## Platform and language constraints

- `SUPPORTED_PLATFORMS = iphoneos iphonesimulator` with `SDKROOT = auto`, `SUPPORTS_MACCATALYST = NO`, and `TARGETED_DEVICE_FAMILY = 1,2` (iPhone, iPad). macOS and visionOS were dropped deliberately; `platform=macOS` and visionOS destinations will not resolve.
- Deployment target is iOS **26.0** at both the project and target level, so recent SwiftUI APIs are available without availability checks.
- Some `#if os(visionOS)` branches survive from when the target built for visionOS (`glassBackground` in [WashBackground.swift](Eventrail/Views/Components/WashBackground.swift), `tabViewSearchActivation` in [RootView.swift](Eventrail/Views/RootView.swift)). They are unreachable now but make re-adding the platform cheap — remove them only on purpose.
- `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` — types are `@MainActor` by default. Mark work that must leave the main actor explicitly (`nonisolated`, `@concurrent`, actors). `SWIFT_APPROACHABLE_CONCURRENCY = YES`, Swift language mode 5.
- `LOCALIZATION_PREFERS_STRING_CATALOGS` / `SWIFT_EMIT_LOC_STRINGS` are on and known regions are en, ja, zh-Hans, zh-Hant — user-facing strings should be localizable `LocalizedStringKey`s, not raw `String`s.

## Sandbox capabilities

App Sandbox is enabled; the entitlements the target already grants are the practical limit on what features can be built without a project-file change:

- Allowed: calendars (`ENABLE_RESOURCE_ACCESS_CALENDARS`), location, outgoing network, read-only user-selected files, app groups.
- Denied: incoming network, camera, microphone, contacts, Bluetooth, USB, printing.

Of those, calendars, outgoing network and read-only user-selected files are the ones anything reaches: the mirror, the adapter and geocoders, and opening a backup. **Nothing asks for the reader's location** — there is no `CLLocationManager` in the app and no `NSLocationWhenInUseUsageDescription` — the maps draw halls, not the reader, and `ENABLE_RESOURCE_ACCESS_LOCATION` is granted without being used. Adding a feature that shows where the reader is standing means adding that usage string too.

The app fetches from four places and no others: `www.eventernote.com`, the flyer host its pages point at (`eventernote.s3.amazonaws.com`, loaded through `ImageCache` by `CachedImage` — never `AsyncImage`, whose shared URL cache the host's missing `Cache-Control` defeats), `msearch.gsi.go.jp` and `nominatim.openstreetmap.org`. Apple Maps goes through MapKit. Everything else — the source repository, a hall's official site, a hashtag, directions — is handed to the system as a link and opened outside the app. Another host means a new dependency on somebody else's service, and should be argued for first.

If a feature needs a capability not on the allowed list, flag it — it requires flipping the corresponding `ENABLE_*` build setting in both Debug and Release configurations.

## Playgrounds

[RootView.swift](Eventrail/Views/RootView.swift) imports `Playgrounds` and defines a `#Playground` block alongside the `#Preview`. These are inline-execution scratch areas for Xcode; they are not tests and are not run by `xcodebuild`.
