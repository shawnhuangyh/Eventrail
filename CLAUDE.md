# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Eventrail is an iPhone/iPad SwiftUI app (app target `Eventrail`, bundle id `moe.shawn.Eventrail`, plus the `EventrailTests` unit-test bundle, the `EventrailWidgets` widget extension, `moe.shawn.Eventrail.Widgets`, which draws the Live Activity and the home and Lock Screen widgets, and `EventrailWatch`, the companion Apple Watch app, `moe.shawn.Eventrail.watchkitapp`, embedded in the app's `Watch` folder — see *The watch app*). [MyApp.swift](Eventrail/MyApp.swift) declares the `@main` `App` and shows [RootView.swift](Eventrail/Views/RootView.swift), a four-tab `TabView` (My Events / Following / Me / Search, the last with `role: .search`, which iOS 26 detaches into its own button beside the bar). There is no package manifest and no dependencies.

Source is grouped as:

- [Eventrail/Model/](Eventrail/Model/) — `Event`, the reader's private `Tracking` record (with its `LotteryEntry` list, in `Lottery`, and `LotteryList`, every round of it entered for an event still ahead), the SwiftData models the library is kept in (`LibraryEntry`, `LibraryEvent`, `LibraryLottery`, `FollowingReadMark`, `FollowedPerformer`, `LibrarySettings`, the read-once `LibraryMembership`, and the `@Query` descriptors in `LibraryQueries`), `LibraryArchive` (everything they own as one value — the backup's form, and the merge), `Feed` (one page of an Eventernote listing at a time), `Region`, `PassportStats`, `OnThisDay` (the events gone to on today's date in earlier years), `Money` (what a ticket cost and in what, `Currencies` — the codes offered, how each is printed and the hall's own — and `CurrencyRates`, one table of rates), and `EventStore`, the `@Observable` every write to the library goes through, passed down through `.environment` beside the SwiftData container (`.library(store)`). Three things ride in that environment, and the two beside the store are both read from Eventernote rather than from the library, and both cached on the device rather than only for the launch: `FollowedDates`, the upcoming dates from each followed performer's listing, so the Following tab and the Me card share one read instead of asking twice; and `VenueRegions`, which part of the country each hall named on those rows stands in. [PreviewData.swift](Eventrail/Model/PreviewData.swift) is fixtures for `#Preview` and the playground only; the running app starts with an empty library.
- [Eventrail/Services/](Eventrail/Services/) — the Eventernote import adapter (`EventernoteClient`, `EventernotePages`, `HTMLCursor`), the three answers to "where is this hall" (`VenuePlaces`, `JapanAddresses`, `VenueBuildings`) plus `VenueRegions`, `PageReads` (which event pages this device has already read), `KeptFile` (the file each of `VenuePlaces`, `VenueRegions` and `PageReads` keeps its answers in), and `LibraryDatabase` (the store, and its sync) with `LegacyCloudZone` (what the sync before it left in iCloud), `CalendarSync`, `LibraryBackup`, `EventActivities` (the Live Activities), `WatchLink` (what the watch app is sent), `WidgetLink` (what the widgets are left, and the lottery results given on them — see *The widgets*), `LotteryReminders` (the results-day notifications — see *The results-day reminder*), `SpotlightIndex` (what Spotlight finds — see *Spotlight, Siri and Shortcuts*) and `ExchangeRates` (what one currency is worth in another — see *The Event Passport*). See below.
- [Eventrail/Intents/](Eventrail/Intents/) — the App Intents: `EventEntity`, `PerformerEntity` and `VenueEntity` (what Spotlight, Siri and Shortcuts know an event, a followed performer and a hall by), the intents that open them, the next event and Eventernote's search (`OpenIntents`), and `IntentOpens`, where an intent leaves what it asked for — see *Spotlight, Siri and Shortcuts*.
- [Eventrail/Views/](Eventrail/Views/) — one file per screen, plus [Components/](Eventrail/Views/Components/) for the shared panel, the wash background, and the small repeated parts: `Typography` (`SectionLabel`, `CardHeader`, `SeeAllLabel`, `Footnote`), `Pieces` (`StatTile`, `GroupHeader`, `FlowLayout`, `VenueMap`, the favorite and followed rows), `ListControls` (`ListMenu`, the capsule over the foot of a list that every list's filter and sort live in; `LibraryHalfPicker`, the Upcoming/Past control at the head of an event list; `PencilToolbar`, the one control a list keeps in its navigation bar; and the selection bar and removal confirmation they share), `SettingRow` (the icon-name-control row Settings and the Welcome screen's switches share), `CurrencyChoices` (the contents of every currency menu — the ticket sheet's, the Passport's and Settings'), `PhotoSaving` (adding a picture to Photos, add-only, and the alert when it cannot — the flyer's and the ticket stub's), `BackupRestore` (the `restoringBackup(_:asking:)` and picker modifiers), `RefreshNotices` (the notice every refresh ends in — see *The Eventernote import* — which also says, with an ✕, when a tap was turned down), and `Fold` and `EventPane` (where an open iPhone Duo's fold — or the middle of an iPad held on its side — crosses a screen, and the event opened beside a list there — see *The iPhone Duo*). A screen that draws a row two screens already draw belongs here rather than in a third copy.
- [EventrailWidgets/](EventrailWidgets/) — the widget extension: the Live Activity's Lock Screen, Dynamic Island and Apple Watch Smart Stack views (`EventLiveActivity`), the three widgets (`NextEventWidget`, `LotteriesWidget`, `OnThisDayWidget`, with `WidgetParts` and `WidgetSamples` — see *The widgets*), and a string catalog and an asset catalog of its own, since the extension is its own bundle.
- [EventrailWatch/](EventrailWatch/) — the watch app: `MyEventsView` (the list), `EventPagesView` (the three pages), `EventMoment` (where one event stands at one moment, and what each page prints for it), `WatchLibraryStore` (the copy the phone sent), `Flyer`, a string catalog and a copy of the app icon of its own.
- [Shared/](Shared/) — compiled into the app, the extension and the watch app: `EventActivityAttributes`, what a Live Activity is made of; `EventActivityStage`, the rules all three read the event by, and its colours; `WatchLibrary`, what the phone sends the watch; `WidgetLibrary`, what the app leaves its widgets; `CalendarDay`, a day with no clock — a results day, the day a memory fell on; and `Gregorian`, the calendar every day is counted on (see *Platform and language constraints*). Like the others it is a synchronized group, listed in all three targets — save `EventActivity.swift`, which imports ActivityKit and is excepted from the watch target, since watchOS has none (that is why the stage is a file of its own), and `WidgetLibrary.swift`, excepted the same way, since the watch has no widgets.

Where each screen hangs off those four tabs:

- **My Events** (`EventsView`) is the library, filtered ahead/past and grouped by month or by the billed artist, with a selection mode for removing several at once. Ahead or past is a segmented control at the head of the list (`LibraryHalfPicker`, the list's first row as Following's chips are) rather than in the capsule, because it is a choice between two lists — each read in its own order, only the first counting down and carrying a read state — and is always one or the other, with no All to set apart; the head of a list is where every screen keeps the choice of which list it is. The grouping is in the capsule over the tab bar (`EventListMenu`, a `ListMenu` holding a Sort section and nothing else yet), and the navigation bar keeps only the pencil. While picking, the capsule is put away and the halves held still. The full Favorite Events list behind the Me card is built the same way from the same parts. A row whose event is still ahead counts itself down beside the chevron (`DaysAway`, off `Event.daysAway`) — whole days between written dates, so an event stays "1 day" all through the day before it rather than turning into two some time that evening, and the last week reads in the app's own tint. Only here: `LibraryRow` is the one row the reader keeps because they mean to be there, and counting down to a date nobody has kept would be the app deciding it mattered. An event still ahead is also read or unread, off the **same** read record Following keeps (`FollowingReadMark`) — so a date read on either tab is read on both: the `UnreadTag` (New / Updated) sits above the title, opening the row or swiping it from the leading edge reads it, and a past event carries neither tag nor swipe, since its record is pruned with the event. Its selection mode marks as well as removes: `SelectionToolbar` (shared with the two screens behind the Me cards) keeps Select All top-left as Following does, and takes a `MarkReadButton` bottom-left — Following's own, same rule — on the Upcoming filter, and in the same place on Past a `MarkAttendedButton`, which gives every picked event without a ticket one (`EventStore.recordTickets(for:)`) — one way only; a ticket is taken back on the event's own Ticket Details. No envelope filter here. Past also opens, under the picker and not while picking, on a row offering `TicketReviewView` (`TicketReviewPrompt`) whenever past events have arrived with no ticket since the reader last went through them (`EventStore.awaitingTickets(_:since:)`: kept, past, nothing at all written on its Ticket Details (`awaitsTicket`, `Tracking.isEmpty` — so a lottery written down, lost included, or a seat, cost or note, takes it out: the reader has already said how the event went), and added — or its day ended — after the per-device `ticketsReviewed` date), which is how an imported history gets its tickets: a sheet of those events by month, nothing picked to begin with (a pick is the reader saying they were there) and Select All in the bottom bar, whose checkmark records a ticket for each picked and counts the whole list as gone through, as the row's ✕ does without writing anything. Handed its list by `sheet(item:)` (`TicketReviewList`): with `sheet(isPresented:)` it opened on a stale empty copy of the screen's state. Every row, past or ahead, also swipes from the trailing edge to Remove — the same `EventStore.remove` as the trash, and asked about first like it (the swipe's button carries no destructive role, which would send the row off the screen before the answer is in).
- **Following** (`FollowingView`) is every upcoming date of every followed performer, read from their listings rather than from the library, filterable by person (the chips along the top) and by how far ahead and where — from a capsule centered over the tab bar, a menu built as the Search tab's is (a Filter section holding a Date submenu and an Area submenu) without the Sort section, since these dates run one way. Date is All or a rolling window from today — the next 7 days, 30 days, 3 months or 6 months (`FollowingFilter.Window`), counted in written dates as `daysAway` counts them — rather than a range picked on a calendar, which went with the sheet it needed, and rather than "this week" or "this month", which near their end hold almost nothing. Area takes several areas and Not Placed at once with the menu kept open, each with its count inside the window. While the list is held to any area, halls go on being placed for as long as each run gets somewhere, since the tab's own ration can leave dates under Not Placed that are only waiting to be read. An event leaves it once its published end time has gone by (`Event.hasEnded`), not only once its day is over — **but only where its hall's clock is known** (`FollowedDates.hallZone`, wired in `RootView`): a listing row is read on Tokyo time whatever its hall, so a Taipei finish would read an hour early and a Los Angeles one as the morning before the show. The clock comes from `VenueRegions` placing the hall in Japan, from the library's own retimed copy of the event, from the clock `VenueRegions.settleClocks(for:)` settled for a hall abroad, or from any `VenuePlaces` placing of a hall of that name (`timeZone(ofHallNamed:)` — opening the event places it; a name two placings put on different clocks answers nothing, since the row could mean either); a row whose clock is known is re-read on it (`Event.published(in:)`) before it is shown or judged, which also puts Local Time right for it, and the cache keeps the row as the listing printed it. A row whose clock is not known stays until its day is over everywhere (`Event.isUpcomingAnywhere`, the day's end at GMT−12): read on Tokyo time, Tokyo's midnight is the morning of the same day in Los Angeles, and an event there would go before its doors opened. Doors, start and end are read in the order an event runs, each moved to the next morning wherever it is earlier than the one before it (`Event.inOrder`: 開場 23:30 開演 00:30 終演 05:00) — `EventernotePages` stores them so, and `hasEnded` reads older copies the same way. It is taken out of the cache (`FollowedDates.dropFinished()`) at the top of every pull and every stale check, before anything is asked of Eventernote, since the end time is already cached; left out of a listing as it is read; and checked again as `events(for:)` is read, for the redraws in between — which it makes happen, since nothing else changes as an event ends: each read sets a wake for the soonest shown date to go over, and the wake bumps a tick `events(for:)` reads. An event with no end published stays until midnight, since nothing says it is over sooner. It is read like a mailbox: a date carries a tag after the names in its billing caption (as `Eventrail v3.dc.html` draws it) — New, or Updated where the listing changed after it was read; a tag rather than a dot because the billing caption already leads with one — until the reader opens it, swipes it from the leading edge, or marks it in a batch from the pencil's selection mode, and the envelope in the bar shows only the unread ones. Each date's `FollowingReadMark` keeps (`followingReads` in an archive) a fingerprint of the row *as it was read* (`Event.listingFingerprint`: title, hall, day, times and bill — the day once and each time as the clock the page printed, so an event abroad retimed in the library agrees with Following's Tokyo-time copy and an after-midnight time read as the next morning (`Event.inOrder`) changes nothing; not the head count, not the flyer), so a refresh that brings the row back changed makes it unread again without anything watching for the change; a first launch finds every date unread. It is the reader's own record, so it is dated and synced like a favourite — **in a record of its own, never on the event's entry or its facts**: CloudKit settles a record whole, and a mark is written as a row is opened, on whichever device is in the reader's hand, so a mark on the event's row once carried whether the event was in the library and a device that had not yet heard of a removal put the event back everywhere just by opening it (see *Persistence and sync*). Marking a date unread writes a `FollowingRead` with no fingerprint rather than dropping the key, and so does Delete All, for the reason a removal is a tombstone. Records are pruned by their event, not their stamp. Clear Cache leaves it alone — it is not a copy of anything Eventernote holds. A `List` rather than a scroll view of panels, for the swipe and the selection — which is also why the billing caption pushes through the stack's `path` rather than a `NavigationLink`, which would take the whole row over.
- **Me** (`MeView`) is six cards — the linked account, On This Day (on a day that has one), the Event Passport, lotteries, favourites and followed performers — each sampling five rows (the lotteries three) and sending the rest to a screen of its own (`OnThisDayView`, `LotteriesView`, `FavoriteEventsView`, `FollowedPerformersView`). Everything that *configures* the app is behind the gear: `SettingsView`: General (Locale, which pushes `LocaleSettingsView`: under Language, App Language — iOS's per-app setting, so a link to the system's page — and the language an event's 概要 is translated into; under Currency, Default Currency — a per-device `@AppStorage` (`Currencies.storageKey`), yen until the reader picks another, which the Passport adds tickets up in and a cost typed on a ticket starts in; then Appearance, Time Zone, iCloud Sync, Calendar Sync, Lottery Reminders), Backup (Export, Restore), Advanced (Venue Locations, which pushes `VenueLocationsView` holding the Refine with OpenStreetMap switch, the refresh, and Refresh All Venues — a per-device `@AppStorage` switch, off by default, without which the refresh skips halls Apple Maps already placed, and Clear Cache) and About (About Eventrail, the Welcome screen), with Delete All alone under Danger Zone below them. `Appearance` (System/Light/Dark) is a per-device `@AppStorage` preference applied by setting `overrideUserInterfaceStyle` on every window and every controller presented over it (`Appearance.apply()`) — by `MyApp` at launch and by the Settings row as it changes, so a change shows at once. Not `preferredColorScheme`: going from Light back to nil there left the window and the Settings sheet light on a dark phone. And not an `onChange` in `MyApp`: on the app's own `@AppStorage` it fired for the first change only. A Settings row is an icon in a gutter, a name and a control; it grows a second line only for a status the reader has to act on or is waiting on (a failure, a refresh in progress, the last sync). Don't put explanations back under the switches, a footnote at the bottom, or a how-it-works card in About; the Welcome screen's feature panels are the one place the switches are explained. Two exceptions: Default Currency on `LocaleSettingsView` carries one line under it, on Shawn's word, because "default" reads as the currency every ticket is in, when each ticket keeps its own and the setting only decides what the Passport adds up in (and what a new cost starts in); and `VenueLocationsView`, which opens on why the switch exists (outside mainland China Apple Maps places nearly every hall and nothing there needs changing; inside it Maps finds few halls in Japan), then the three answers a hall is placed by (Apple Maps, the 国土地理院 register, OpenStreetMap), in the order they are asked, each with how many of the reader's halls it placed (`VenuePlaces.breakdown(for:)`) — with its switch and the refresh under them: the switch governs only the third answer — every request to OpenStreetMap, the narrowing and the mainland-provider search abroad alike — and it means nothing without the other two.
- **On This Day** (`OnThisDayView`, the `OnThisDay.dc.html` board of the Eventrail design canvas, and its card on `Me.dc.html`) is every event the reader went to on today's date in an earlier year (`OnThisDay`): an event in the library whose written day — on its hall's clock, as `Event.localDay` reads it — has today's month and day and an earlier year, with a ticket held (`Tracking.hasTicket`; in an earlier year that is `EventStore.hasAttended`). A leap day comes round on the 28th in a year without one. Counted on the Gregorian calendar whatever the reader's is set to, since on the Japanese one Heisei 31 is not before Reiwa 8. Read off the library alone, as the Passport is, with nothing kept and nothing asked of Eventernote. Most recent year first. The card sits between the account and the Passport and **is left out on a day with nothing to show** rather than standing there empty — there is nothing the reader could do to fill it today. It draws each memory as a row — "1 year ago · 2025" in green, the title, the hall — with Favorite Events' flyer, padding and divider, and the whole card pushes the screen, as the design links every part of it there. Not the design's first memory drawn large (a 76-point poster with the seat and the note): among cards whose rows carry a 38-point flyer or none, it read out of step with the rest of the tab, so the seat and the note are left to the screen. The screen puts each memory under two pills (how long ago, in green, and the day) in a card: the flyer and title (opening the event's sheet), the hall (pushing the hall's page), doors, start and how long it ran on Settings' clock, a ticket tile (how it was had — Won for a lottery, Got Tickets for a first-come seat or a ticket recorded with no round — then the price, the round and its entries) and a seat tile, the note, and Ticket Stub and Open Event.
- **Lotteries** (`LotteriesView`, `Eventrail v4.dc.html` §8a) is every lottery round entered for a kept event still ahead — and, on Decided with Show Past on, for one that is over (below) — (`LotteryList`: `LotteryEntry.isLottery` only — not a first-come round, which is a seat got, and not the ticket an older record held), read off the same `Tracking.lotteries` the ticket sheet writes, so nothing is kept for it. Each round's results day is a calendar tile (`LotteryDayTile`, the month over the day): filled in the app's tint once that day has come and nothing is written down (`LotteryRow.isResultsOut`, today included), green once won, grey once lost, and a dashed outline reading DAY ? where no day was announced. The Me card sits under the Passport and shows the next **three** rounds awaiting a result by results day (`LotteryList.next`, no day last) — fewer than the other cards' five, as the design draws it — each with the round and its entries under the title and, on the right, Results out, how far off the day is, or Not Set. Its See All stands wherever there is a round at all, the rounds of events that are over included (`LotteryList(includingPast: true)`): counted over the events ahead alone, a library whose lotteries were all behind it had no way into Show Past. The screen is a `List` (for the swipes) with two halves at its head as My Events has, Awaiting · N and Decided · N, since a result given moves a round from one to the other; a subtitle of the half on screen ("4 rounds awaiting results · 2 out now", "2 rounds decided · 1 won"); a sort capsule at its foot (Results Day, Event Date); and a card per round — the tile, with how the round went on its corner (`Eventrail v4.dc.html` §8a's style B, "On the date": an hourglass on blue while it waits, a tick on green once won, a cross on grey once lost), then the round on one line, the title in up to three lines across the card's whole width (no pill beside it any more) and the event's day and hall on one, then under a hairline three readings headed in small capitals: Entries (the applications, large, or a dash where none are written down), Results ("In 5 days", "Out — record it", "3 days ago", "Not announced") and Seats (the choices as small chips, left out where a round names none). Awaiting by results day leads with Results Out, then the months the results come out, then No Results Day; by event date it goes by the event's month. Decided is Won then Not Won in either order. Every order runs earliest first, save where Decided shows the past. **On Decided alone the capsule also holds one switch, Show Past** (as Reminders' Show Completed) — off as the screen opens, not remembered between visits — and nothing more: a Date submenu of All / Upcoming / Past was tried and taken out, on Shawn's word, as more than the job needs. On, it brings in the rounds of events that are over (`LotteryList(includingPast:)`, `LotteryRow.isOver`), and Decided reads latest first (`LotteryRow.latestFirst(by:)`, a round with no day still last), as My Events' Past is; one still pending there is No Result — the ticket sheet's word — under a group of its own after Not Won, with a grey dash on its tile. **Those rounds are only looked back on, never answered here**, on Shawn's word: their tile is drawn in the card with no menu, the card has no swipe, and a tap anywhere opens the event. Awaiting never holds them. **A result is given from the list itself**, from the menu the tile opens (Pending, Won — a choice each where there are several — and Lost, then Edit Entry) or by a swipe (one Won from the leading edge, which asks which choice was won where the round applied with several — a button per choice in the swipe was too narrow to read — and Lost from the trailing), written at once through `Tracking.givingResult(_:toLottery:)`, which settles the ticket's class as the sheet's save does — unlike the ticket sheet, which holds a copy until its checkmark. Both keep the sheet's rules: Won and Lost are not offered while the results day is still ahead (`LotteryEntry.canBeDrawn`, a rule the design's prototype leaves out), and a result that takes the ticket away with a seat or cost written asks first whether to clear them (`Tracking.leavesSeatOrCostBehind(since:)`, shared with the sheet). Edit Entry opens `TicketDetailsView` with that round's page already pushed (`opening:`); the rest of the card opens the event's sheet. A round awaiting its result with a results day written down is also a notification at 20:00 that day, which opens the same page — see *The results-day reminder*. The tile is that menu, laid over the card's button rather than inside it — over a clear frame that holds its room, found through an anchor preference (`TileSpot`), since the tile is centred against the text beside it — so a tap on it opens the menu and not the event. **The design file is over the 256 KiB the design tool returns**, so its script — the labels, captions and rules §8a computes — is cut off there. It was read whole from the design page in Chrome, through the page's own `GetFile` call; reading it any other way means guessing at the words.
- **Search** (`SearchView`) runs Eventernote's two searches, events and performers. On an iPad the bar keeps its title while a search is up (`searchPresentationToolbarBehavior(.avoidHidingContent)`): left to hide it, the bar took the large title's leading margin away (the large-title view's `directionalLayoutMargins` went from 20 to 0, the bar's own staying 20) and left it standing half off the edge of the screen (iPadOS 27.1), whether or not the screen was parted. Not an inline title while searching, which took the title away altogether — on Shawn's word. Event results carry a capsule centered over the search field (a `.safeAreaInset` on the results — a `.bottomBar` item is not drawn while the tab bar is), and the capsule is one menu, as the system's own lists hold theirs: a Filter section of two submenus, each a row with its icon and what it is set to — Date (All/Upcoming/Past) and Area (Anywhere or one of the site's areas) — and a Sort section, newest or oldest first by date (`SearchOrder`), checked as a menu checks a choice. The filter's choices sit a level down rather than in the section itself, so that every row at the top level is an icon and a name, and **every filter submenu, here and on Following, puts the choice that holds nothing back (All, Anywhere) alone above a divider** and the rest below it. Its face says what the results are held to ("All" while nothing), then the sort arrows. No date range: it was tried and taken out. `SearchFilter` says which of that the site answers: an area is asked of Eventernote (`area_id`, one at a time, so the total stays the site's — and 海外 is offered here, since the site files a hall abroad itself and nothing reads it off an address), and so is the order; ahead/past is held in the app over the pages read, the site having no idea of "upcoming". **The order goes as `sort=event_date&order=ASC|DESC`, not as the `sort_by` the site's menu is named**: its page script splits the menu's value into those two, and `sort_by` sent as it is is ignored. What the app holds back is one unbroken run of a listing in date order, on one side of today, so the pages wholly in front of it are skipped by halving (`SearchView.firstPage` — four requests for 349 results rather than eleven; this is what makes Upcoming, oldest first, possible at all, since every past event stands in front of it), and the reading stops at the first row past it (`SearchFilter.comesBeforeMatches`/`comesAfterMatches`). From there the rows read on as the last of the shown ones come into view; five pages in a row that add nothing (which takes a skip that failed) stop it on Keep Looking, since a site asked too fast stops answering the app altogether. Any change to the filter or the order starts the search again. Both are kept across searches until the reader changes them.
- Before anything is typed, **Search opens on two of the site's own lists** — the tabs over Eventernote's own event search — above the recent searches: **Today** and **Just Added** (`SiteListing`, pushed on the tab's stack as `SiteListingView`; the site's third tab is the Following tab, and its fourth, the past, is Search's own Date filter). Today is not the site's 今日開催 tab, which prints the whole day on one page and ignores `area_id`, but its search given the day as 開催日 (`EventernoteClient.events(on:areaID:page:)`): the same events, counted, paged, sorted `start_time` ASC (no start first), and narrowed by the Area submenu as the results are. The day is the site's (`Event.siteDay`), so a reader in the Americas sees the date Japan is already on — the row and the screen's subtitle name it. Just Added is the 新着 tab itself (`/events/?type=2`): the hundred events most recently added, in the order they were added, one page with no count and no second page (`EventernoteClient.newestCount`) and no area either — so its capsule holds the Date submenu instead, held in the app over the hundred rows, since a past date filed late is among them. Each list keeps its half of a `SearchFilter` in `SearchView` for as long as the app runs, as the search keeps its own. Both are read as a performer's page is: from `ListingCache` at once (`site/today/<area_id>`, carrying the site's day it was read for, so yesterday's copy is never shown; `site/new`), the first page only, read again once stale or the site's day has moved on, and from Refresh in a ⋯ menu — in the navigation bar, since the foot is the capsule's — with no pull. Neither carries a read state: New/Updated is Following's mailbox, for the reader's own people, and on a hundred strangers' dates it would be noise.
- Opened from several of them: `EventDetailView` (as a sheet), `PerformerView`, `VenueView`, and `ListingHalfView` behind the See All on either of those last two. A performer's and a hall's page carry their actions as the event sheet does, in one capsule at the leading edge of a bottom bar — Follow, Share and a ⋯ menu for a performer, Directions, Share and a ⋯ menu for a hall, each menu holding the bar's own actions again with Open in Eventernote and Refresh, in the event sheet's menu's groups a divider apart (Follow; Share; Open in Eventernote and Refresh — Directions and Share; Open in Eventernote and Refresh) (see *The Eventernote import*) — shown once the page behind the name is found; the tab bar stands down while either is up, and stays down on the See All pushed from them rather than coming back for one screen. The event sheet is drawn as `Eventrail v3.dc.html` draws it: the flyer small beside the title, date and hall — a tap opens it whole in Quick Look (`quickLookPreview`, the system's viewer, whose share button saves and sends it) and a long press offers Share and Save to Photos over a larger copy, both handed a file `ImageCache.file(for:named:checkedSince:)` writes into the temporary directory, the host's bytes under the event's title, since both go by a file's name and kind and the cached copy has neither; a timeline card (how many days off — or, once the day is over, Attended with a ticket and Ended without — then, as `Eventrail v4.dc.html` draws it, the offset of the clock the times are on and a Venue / Local switch between the two clocks, Doors, Start and End on one line, how long it runs and the head count; on the day itself it redraws every second through `TimelineView` and `EventProgress`, which says where the event has got to — "Doors in 1h 12m", "Doors open · Show in 23m", "On now · 1h 10m left" — and how far the bars have filled, an event with no end published running for `Event.assumedLength`). Its actions are a bottom-bar group at the leading edge — add/remove, share, and a `.menuOrder(.fixed)` menu in groups a divider apart — what the reader keeps (the heart), where it is and passing it on (Directions, Share), the page it was read from (Open in Eventernote, Refresh) and, last, Remove Event with its trash drawn red (a menu tints every icon, so the image carries its own colour) — or Add Event with a plus where the event is not kept. - `WelcomeView` is shown over everything on the first launch, once per device, and asks only the three things the app cannot work out for itself: where the reader's records come in from (an account or a backup), whether they sync, and whether the calendar is written. ## The Eventernote import

**The linked account's record on Eventernote is the source of truth for what the reader has been to and who they care about.** That is the premise the whole app is built on: the library is the account's attendance history as the site publishes it, and `follows` is the account's favourites. So an import is always allowed to restore what the site still lists, and it never needs the reader's permission to do it — asking Eventernote again is how the reader gets back something they took out and then wanted.

What the reader owns is the layer on top: tracking, notes, favourites, and which of their own devices hold what. A removal in the app settles *that* layer and syncs across their devices; it does not reach the account and has never claimed to. Dropping something for good means dropping it on Eventernote. The exception is what the account never carried — an event saved from Search, a performer followed in Eventrail alone — where a removal is final because nothing will import it back.

Eventernote publishes no API, so [EventernoteClient.swift](Eventrail/Services/EventernoteClient.swift) GETs the site's public pages and [EventernotePages.swift](Eventrail/Services/EventernotePages.swift) reads them with [HTMLCursor.swift](Eventrail/Services/HTMLCursor.swift), a marker-based scanner (no HTML parser, no dependency). Things worth knowing before changing any of it:

- **The User-Agent must contain `iPhone`.** The site serves a desktop template otherwise, and every selector here is from the smartphone template. This is the single most breakable assumption in the adapter.
- Pages read: `/events/search` (with `sort` and `order`, and the `area_id` of its own form where the Search tab's filter asks for one; with its `year`/`month`/`day` and `sort=start_time` for Today), `/events/?type=2` (Just Added), `/actors/search`, `/actors/{slug}/{id}/events`, `/events/{id}`, `/places/search`, `/places/{id}`, `/places/{id}/events`, and — only once the reader has named a handle — `/users/{handle}` and `/users/{handle}/events`. `robots.txt` disallows only `/users/notice` and `/users/timeline`. Everything is a GET: nothing is ever written back to Eventernote, no password or cookie is collected, and naming a handle reads that member's public pages rather than signing in as them.
- Performer slugs come back already percent-encoded and are passed through `percentEncodedPath`; re-encoding them breaks names containing `!`, `(` or spaces.
- **A `+` in a query goes as `%2B`** (`URLComponents.setQuery`, used for every host): `queryItems` leaves it as it is, being allowed in a query, and a server reads it as a space — a billed name like +α/あるふぁきゅん。 was searched for as another, and its exact match found nobody.
- A performer's own listing (`/actors/{slug}/{id}/events`) is ordered from the furthest published date backwards, so every upcoming appearance sits at the front of it. `PerformerView` relies on that: it pages until the first past row appears, which is what makes its Upcoming section — and the count over it — the whole of it rather than whatever landed on page one.
- A hall's own listing (`/places/{id}/events`) is the same block in the same order, read the same way by `VenueView`. The hall's page itself carries ten of those rows and says "→全てのイベントを見る(372件)" about the rest, so the listing is read from `/places/{id}/events`, which pages and prints its total like every other listing on the site. The two pages are what `ListingHalfView` is shared between — one screen behind both See Alls, titled for whichever subject it was handed.
- **A venue page publishes no photograph of the hall** — only an address and a `map_canvas` the site fills in with Google's script, which this app does not run. So `VenueView` draws its own map from the published address through `VenuePlaces`, the same lookup and the same kept answers an event's sheet uses; the hall is never shown with a picture, for the reason a performer is not.
- **Eventernote publishes no performer portrait.** The `gb_blur_title` cover block in the shared template is only ever filled on a member's own page; every actor page sampled across the id range leaves it out, and the actor listing and search rows carry no image either. So no performer is ever shown with a picture — not on `PerformerView`, not in an event's Performers card, not in a Search result row. An event flyer is artwork for the event rather than a likeness of the performer, so it is not stood in for one either, and an empty placeholder circle is just furniture. Don't go looking for a portrait endpoint again. (The avatar on the Me tab is a different thing: a *member* page really does publish one.)
- An event's billing publishes names only, with no link to a profile, so opening a performer from there searches for the name and takes an exact match. The search matches on the kana reading too, so a near miss is a different person.
- **An event's times are a wall clock with no zone on it.** 開演 18:00 means 18:00 at the hall, and the site's members write an event abroad in the hall's clock like any other — the Taipei dome dates print the same 18:00 their Chinese-language 概要 does. So an import reads every page on `Event.publishedZone` (Asia/Tokyo, one zone for all 47 prefectures) because that is all a page says, and a hall the placing later puts outside Japan sends its events back through `Event.published(in:)`, which re-reads the same published clock in the hall's zone. Nothing on a screen moves — every line is formatted in the event's own zone — but the instant behind it does, and that instant is what the calendar entry, its door alert and the library's order are made of. A hall nothing has placed stays on Tokyo time, which is right for every hall in Japan and is the old behaviour everywhere else. **Settings › Time Zone** (`TimeDisplay`, a per-device `@AppStorage`, Venue Time by default) can print every day and time on the reader's own clock instead: `Event.shown(on:)` is a copy for *formatting only* — the zone set to the device's and the day taken from the first published time, since a day with no time cannot be converted and keeps its hall's — and the instants, the month groups, `daysAway` and the date filter stay as they are, because an event belongs to the day its hall says it falls on. Every view that prints a day or a time reads the setting itself (`@AppStorage`) rather than through the environment. The event sheet starts from it too, and carries a switch of its own in its timeline card — Venue / Local (`EventDetailView.clockSwitch`, `TimeDisplay.shortLabel`) — that prints that one sheet on the other clock until it closes: a way of reading one event, not a preference, so it is the sheet's `@State`, never written back to Settings, and moves no other screen and not the Live Activity; picking the clock Settings names goes back to following Settings. It is left out where the hall keeps this device's own time zone (`offersClockSwitch`), since both clocks would print the same times — compared by zone, not by offset, on Shawn's word (October 2026), so a reader in Seoul still has it on a Tokyo date — and kept where the hall's clock is not yet established, since whether the two are one is not known either. It is a small capsule rather than the segmented picker Settings uses, which is too tall and too wide beside the headline, and VoiceOver is handed that picker (`accessibilityRepresentation`). Beside the switch is the offset of the clock chosen — on Local the device's on the day of the event, which is always known; on Venue the hall's — on **every** sheet rather than only on the events abroad: the times are the hall's wherever the hall is, and a reader in Shanghai reading a Tokyo date is owed that as much as a reader in Tokyo reading a Taipei one. Two rules keep it honest, and both were learned the hard way:

  - **The offset, never a place name.** A zone identifier is the map provider's reading of where the hall stands, and the provider is chosen by where the *reader* stands: a phone served from mainland China files a Taipei hall under `Asia/Shanghai`, which Foundation names "China mainland Time" — printed under a Taipei address on the same screen. Seoul is GMT+9 and is not "Japan Time". The offset is the part the app is sure of and the part that moves the times; the hall is named on the same sheet already. Don't reinstate `TimeZone.localizedName` or `.genericLocation` here.
  - **Only a clock that has been established.** `EventDetailView.venueZone` takes it from the placing, or from an event a placing already retimed, or from a published address opening with a Japanese prefecture (Japan being one clock end to end, no map service needed). Otherwise the switch stays but the offset goes: an unplaced hall abroad is read on Tokyo time because that is where every import starts, and printing GMT+9 under a Seoul date would be claiming an answer rather than having one. Venue alone is still the whole truth — the times *are* the hall's, as its members wrote them — and the sheet asks for its own hall as it opens, so the offset usually arrives a second later.
- Search rows carry only day, title, venue, billing and a thumbnail. Times, head count and the venue address come from the event's own page, so `Event` marks that with `isDetailed` and its time fields are optional. **Do not make them non-optional** — Eventernote routinely announces an event months before it publishes a start time.
- An event's own page publishes more than the times: 概要 (the one free-written field, and so where ticket prices, on-sale dates and stage splits all end up — kept with its line breaks), 関連リンク, Twitterハッシュタグ, and the edit history's who-and-when, which is how a reader tells an upcoming date nobody has checked in two years from a fresh one. **Reading more of that page means bumping `Event.currentDetailFormat`.** `isDetailed` answers the older question — was the page read at all — so a library imported before a field existed carries it true and the field empty; `isFullyDetailed` compares the stored `detailFormat` and is what sends one sheet back for the rest. Deliberately one sheet at a time: a bulk re-read would be nine hundred requests for pages nobody is looking at.
- **概要 can be read in the app's own language** through Apple's Translation framework (`translationTask` on `EventDetailView.summaryCard`), on the reader's tap and never by itself. The target is `TranslationTarget`: a per-device `@AppStorage` choice made under Settings › Language, empty by default for the app's own language (`Bundle.main.preferredLocalizations.first` — the per-app language, not the system's). Its list is `LanguageAvailability.supportedLanguages`, so it is only the default row in the Simulator. The button is not offered when the target is Japanese or when `LanguageAvailability` calls the pair unsupported. The source is named as Japanese rather than detected, since kanji and hall names read as Chinese to a detector. It is translated line by line so the ticket lists keep their shape, and a line that is only an address is carried over untouched. The result lives in the sheet's `@State` and is **never written to the archive**: it is a way of reading the page, not the reader's record, and storing it would mean syncing it and noticing when the page under it changed. The models run on the device and are downloaded by the system, so this adds no host to the list under *Permissions and hosts*. Translation does not work in the Simulator — try it on a device.
- **A listing row publishes the hall's name and nothing else** — no address, no place id — so nothing on the page the Following tab reads says what part of the country a date is in. `VenueRegions` gets there in two GETs per hall: `/places/search` finds it by the exact name the row printed (an exact match, for the reason a performer's name takes one), and the hall's own page publishes the address, which opens with its prefecture. The answers are cached per device, since a hall does not move — the address as well as the area, so a hall is read once for good (an address abroad is never asked again; only "the site files no such hall" is retried, after a month). The Following tab and the Me card look up a ration of halls (20) as they load, the tab keeps going while its list is held to an area, and `learn(from:)` takes every address the library already holds for nothing. A hall whose address is abroad then has its clock settled by `settleClocks(for:)`: `VenuePlaces.placeUnplaced` first (only halls it has no answer for, never narrowed), and where that settles no clock, the country `VenueCountries` reads off the address. The clock is cached with the hall. `Region` is the site's own `area_id` grouping minus 海外 — abroad is the *absence* of a Japanese prefecture in an address, so an overseas hall is left unplaced rather than filed somewhere it might not be. The whole facet, as the `<select name="area_id">` on `/events` spells it, is 1 関東, 2 関西, 3 東海, 4 北海道・東北・甲信・北陸, 5 中国・四国・九州・沖縄, 6 海外 — it is written out in [Region.swift](Eventrail/Model/Region.swift) so nobody has to fetch the page to check, and the five cases cover all 47 prefectures exactly once. **Don't add a sixth area or split one.** The grouping is coarse on purpose: matching is done here from the prefecture at the head of the address, so a finer split would cost nothing to build and would stop the app answering the way the site answers.
- The count beside a name in performer search is the site's *fan* count, not an event count.
- A venue's own page prints 所在地, 電話番号, 公式サイト, 収容人数, 座席情報 and 会場TIPS as `gb_subtitle` sections, and members write them, so most halls leave several empty. The last two are a *link* rather than words — the label in them is "座席情報" and "ウェブサイト", and the answer is the href — and 会場TIPS is a list of exits and walking times whose `<br>`s become newlines before the tags are dropped, or it reads as one run-on sentence.
- **The app reads on its own only what has gone stale; the reader asking always reads.** Eventernote publishes no API and does stop answering an app that asks too fast, and this one was asking for the same unchanged pages over and over — every followed performer's listing on every launch. So what has been read is cached per device with the time it was read, and six hours — `Freshness.window`, one constant for every cache below — is where a copy goes stale: `FollowedDates` for the listings (a JSON file in Caches), `PageReads` for event pages (a `KeptFile` in Caches), and `ListingCache` for performer and venue pages (one file per page in Caches, keyed by `PerformerLink.cacheKey`/`VenueLink.cacheKey`: who or what the page is about, and the listing up to its first past row plus whatever the reader scrolled on to) and for the site's own lists behind Search (`SiteListingView`: the first page, plus whatever the reader scrolled on to). A performer or venue page opens on its cached copy at once and reads again only when that is stale; Refresh in its ⋯ menu always reads. A venue's refresh re-reads the hall's own page too, since members edit its address and tips; a billed name's search is never repeated once it has found someone. Opening the Following tab (and the Me card, which shows the same counts) reads only the stale listings; opening an event's sheet re-reads its page only when `EventStore.isStale` says so or it is not `isFullyDetailed`. A manual refresh is never held to the window — Following's pull-to-refresh (`FollowedDates.reload`) reads everybody, Refresh in an event sheet's menu re-reads that one page, and Refresh on the Me card reads every upcoming page as it always has (`needsReading` does **not** consult `PageReads`). Two rules hold throughout: **a failed read never costs what was held** — `reload` writes over the cache rather than emptying it first, and the Following tab and the sheet put a `RefreshFailureNote` under the cached copy instead of replacing it — and **a refusal stops the run** (`EventernoteClient.Failure.isRateLimited`, HTTP 429 or 503), because the next request would be refused too. Only a read that *landed* is stamped, so a page that failed stays stale. **A refresh the reader asked for always ends in a notice; one the app started by itself ends in one only when it failed.** Following's pull, Refresh in the menu of an event's sheet or a performer's or hall's page, the Me card's Refresh, Settings' venue refresh and a Try Again are the reader asking; opening a page for the first time, opening a stale one, coming back to the app and the Welcome screen's first import are the app keeping itself current, and an "Updated" over every page opened would be noise. Every caller goes through `RefreshNotices.report(_:byHand:)` — `RefreshNotices` is one `@Observable` in the environment, and the `RefreshNotice` constructors cover Following, an event sheet, the library, a performer's or hall's page and Settings' venue refresh. A refresh by hand that joins a read already running says what that read came to as its own would (the performer and venue pages keep the read's notice as its task's result, so each caller decides). It says "Updated" or "Update failed" and the reason, nothing more — what arrived is on the screen behind it. It is a Liquid Glass pill along the bottom, drawn by `.refreshNotices()` on each tab's own content (whose safe area already stops above the floating tab bar, so no bar height is hard-coded), again inside every sheet that can start a refresh (Settings, and the event sheet — which draws its own twice, `showing` one at a time: inside its stack at the root, so the notice stands above its action bar, and over the whole stack once something is pushed), because a sheet covers the tab, and again inside every page with a bar or a capsule along its foot (`aboveBar`: the event sheet's root, a performer's page, a hall's, and the Following tab, My Events and the full Favorite Events list under their capsules), since only the page's own safe area knows the bar is there. Only the frontmost draws, so one notice is never drawn twice: each overlay on screen stands in `RefreshNotices.standing` at a rank of how many sheets it is inside (`refreshNoticeDepth`, raised by `.refreshNoticesInSheet()` on each such sheet) and whether it has a bar, and the highest draws — a tab keeps quiet under a sheet or a performer's page, and the event sheet's stack-wide copy under a page pushed in it with a bar of its own. **A page read from the site is refreshed from Refresh in its ⋯ menu, and only the Following tab has a pull** (`RefreshMenuItem`, on an event's sheet and a performer's or a hall's page). An event's sheet is a sheet, and a pull down from its top is how a sheet is put away — a pull there that read the page took the gesture for something else; and the pages read themselves once their copy is stale, so reading one by hand is an occasional want, a menu's. The item cannot be chosen while a read runs. When the page was last read is the first sentence of the small print at its foot (`Footnote(_:updated:)`, redrawn by the minute) — "Updated 2 hours ago.", "Updated just now." inside the first minute — rather than under Refresh in the menu, where it could be read only by opening the menu; from `EventStore.lastRead(of:)` for an event (the later of this device's `PageReads` stamp and the copy's `readAt`; `readAt` alone moves only when a read finds something new, so a page just refreshed would still say days) and from the listing's own `readAt` for a performer or a hall. Following is a list, where a pull is expected and means nothing else, so it keeps one — **attached to the `List` itself, inside `.performerDestination()` and `.eventSheet`**: a `.refreshable` is carried down the environment into what is presented beneath it, and attached outside them it made a pull on an event's sheet opened from the tab re-read every followed listing (checked in the Simulator by reading `\.refresh` in the sheet: present with the old placement, nil with the new). The Event Passport deliberately has no refresh: it is the reader's own record read back. A pull on Following that lands while a read is already going joins that read and reports it (`FollowedDates.running`) rather than returning with nothing to say. A screen opened on a fresh copy reads nothing and posts nothing. **A read started from `.refreshable` runs in a `Task` of its own** (`FollowedDates.run`, `EventStore.reloadDetail`, `ListingCache.read`): SwiftUI cancels a refresh action when the screen under it changes mid-refresh, and a cancellation that reached URLSession ended the event sheet's pull, as it then was, in neither an answer nor an error — no notice at all. A new refresh anywhere should post one too. Images go through `ImageCache` (an actor; decoded copies in memory, bytes in Caches with the host's `ETag` beside them). The host files a flyer under the event's id, so a replaced flyer keeps its URL: a copy is drawn with no request for `Freshness.window` and then revalidated with `If-None-Match`. **A stale copy is still drawn at once** (`ImageCache.storedImage(for:)`) and revalidated behind it; the picture changes only when the host sends different bytes, and an unchanged answer hands back the very object already in memory so `CachedImage` leaves it alone. Waiting on the host first left every flyer a placeholder each time the window ran out, and for a whole timeout when offline. A screen refreshed by hand sets `EnvironmentValues.imagesCheckedSince`, and every `CachedImage` under it whose host was last asked before then asks again as it draws — so a refresh by hand resets the window on the flyers as well as the rows, once per flyer rather than once per scroll. **Stale is checked on the way back to the foreground as well as on the way in**: the Following tab, the Me card, an event sheet and a performer's or hall's page each re-run their stale check when `scenePhase` returns to `.active`, so a screen left open while the reader was away does not sit past the window. Settings' Clear Cache empties the listings, the page stamps, `ListingCache`, `ImageCache` and `VenueRegions`; `VenuePlaces` deliberately answers to it not at all — a hall's pin comes from Maps and two donated services rather than from Eventernote, a hall does not move, and rebuilding it is a run of hundreds of searches, which is what its own Refresh row under Location is for.
- Every accessor is failable by design: a changed template yields a missing field or a dropped row, never wrong data. The one place "missing" is not allowed to mean "none" is a listing's own block: the site prints no list at all where nothing matches, so `EventernotePages.events`/`performers` read a missing block as empty only on a page that closes with the smartphone template's `gb_foot_menu`, and throw `.unreadable` otherwise — a maintenance page, a captcha or the desktop template would otherwise read as a performer with no dates and be cached that way for the whole window. The footer is not enough on its own where the page also counts what it found (a positive total over no list is a renamed block), and a list that printed rows but gave up none of them throws too: one dropped row is a changed field, every row dropped is changed row markup.

## What the reader records

`Tracking` is the reader's private record for one event: whether the ticket is in hand — read from the lottery entries (`hasTicket`: a lottery won or a first-come round got), never asked on its own; the `ticket` field is what records from before entries said, folded into them as it is read (`foldLegacyTicket()`: the entry carried over from a count won, or a won entry of its own whose applications are not written down, so it moves no lottery figure — and the column emptied on the next write), where they sat (`seat`, one free line — a hall prints 1階 L列 23番, an arena a block and a number, a live house an entry number and no seat at all), the class the seat was sold as (read through `ticketClass`: the highest class among the rounds won or got — `classOfWins`, S above A above General (`SeatClass.order(of:)`) — and only where none names one the `seatClass` column, text, empty for "not written down", which nothing asks for any more and older records filled in by hand; `SeatClass` is only the classes offered, stored as the ticket prints them — S席, A席, 一般席 — and shown in the reader's language, S Seat / A Seat / General Seat in English, so a class chosen in one language reads back in another; anything else reads back as itself), what it cost (`cost`, a `Decimal` exactly as typed, in `currency`, an ISO 4217 code chosen beside it; nil is "not written down", which is not the same as free; read through `price`, a `Money`, which reads an empty `currency` as yen — every cost written before costs had currencies was whole yen), every lottery they applied to for the event (`lotteries`, a list of `LotteryEntry` — [Lottery.swift](Eventrail/Model/Lottery.swift)), and a note.

- **A lottery is an entry, not a count.** Each `LotteryEntry` is one round of a sale the reader tried for, as `Eventrail v4.dc.html` §7a draws it: the round (`round`, one of `LotteryRound`'s five, chosen from chips with no field to type in — 最速先行抽選, プレイガイド先行, プレイガイド二次先行, 一般発売, 見切れ席, the rounds MyGO!!!!! 9th LIVE's page on bang-dream.com runs its sale through, shown as 最速先行抽选 / 一轮抽选 / 二轮抽选 / 一般发售 / 见切发售 in Chinese — stored as the site prints them and shown in the reader's language, as `SeatClass` is; kept as text, so a round a later build adds reads back as itself, and empty on an entry carried over from a count; a new entry opens with nothing chosen — no round, its applications empty, and no result chip on, though it is pending until one is picked; a lottery saved with its applications still empty is saved as applied for once), how many times it was applied for (`applications`, up to 9999, 0 for "not written down", which counts nothing: one per 申込券 or serial code — a single's first pressing carries one, so a reader who bought five applied five times in the one 最速先行抽選), the day results come out (`day`, a `CalendarDay` kept as `2026-10-12`, no clock), the choices in order of preference (`LotteryChoice`: a seat class, empty where the lottery sold one kind of seat, and a ticket count, 1–8; at most three choices) and the result (`LotteryResult`: pending, won with a choice, lost) — only Pending while the results day written down is still ahead, and a day no later than today for a lottery already won or lost, which nothing could have drawn yet otherwise. **一般発売 and 見切れ席 are first come, first served, not lotteries** (`LotteryRound.isFirstCome`), and the reader writes one down only for a seat they got: their page asks no applications, no day and no result, and takes one seat with no rank (a day written while the entry was a lottery is kept, unshown, so moving it back gives it back), and the entry reads as got with that seat (`LotteryEntry.outcome`, `.won` with the first choice, whatever `result` holds — Got Tickets on its card). **Everything that reads how a round went reads `outcome`**, never `result`, which is only what the reader gave a lottery, and is kept while the round is first come so moving it back to a lottery gives it back. **The applications are what the old count meant**: `Tracking.lotteryApplications` adds them up over the lottery rounds alone, and the Passport's lottery figures and the watch's count are read from it; the count the builds before kept (`lotteryEntries`) reads back as one entry applied for that many times (`LotteryEntry.carriedOver(count:)`, with a fixed id so every read is the same list). **In the store each round is a record of its own** (`LibraryLottery` — see *Persistence and sync*), so two devices each adding a round while apart keep both; in an archive the list is still one answer, as the note is — an entry carries no date of its own — and `Tracking.Field.lotteries` keeps the raw value `lotteryEntries`, so an archive's edit date for the count dates the list. Ticket Details saves the list round by round (`Tracking.lotteries(_:changedFrom:to:)`): a round another device added while the sheet was open stays. **Entries are listed in the order the sale runs, whatever order they were added in** (`Tracking.lotteriesInOrder`: `LotteryRound`'s five in order, an entry with no round or one a later build names after them, two of one round as written), on Shawn's word — read in order and never rewritten, so an older record or a list synced in is ordered too and nothing is written for it. The ticket sheet lists them so, the Passport reads its rounds so (`lotteryRounds`) and the event sheet's tile takes the first win so (`wonLottery`). **A win is the ticket**: nothing marks one bought on top of it, and the seat and cost sections of the sheet appear once there is one. Taking the ticket away on the sheet — its last win taken out, or put back to Pending or Lost — with a seat or a cost still written asks on the checkmark whether to clear them too (`leavesSeatOrCostBehind`), since kept they would be kept out of sight; a record that had no ticket when the sheet opened is not asked again. Once there is one, Add Lottery Entry asks first ("You already have a ticket for this event"), since another round after a win is usually a slip but can be a second seat. Winning — or getting a first-come seat — decides the ticket's class and leaves the seat and price for the reader; the ticket sheet writes it into `seatClass` as it is saved (`Tracking.settleSeatClass(since:)`), and empties it when the last round that named it goes, but never empties a class no round ever named. Everything that shows or counts the class — the seat tile, the Passport, the watch — reads `ticketClass`, never the column. The event sheet's ticket tile reads from the entries: a pending one says when its results come out (or when a first-come round goes on sale), a win says what was won, and a win, being the ticket, is in the ticket's orange.

- **Interest and attendance are not fields; both are read off what is already recorded.** An event is in the library because the reader means to go. **Whether they went is whether they held a ticket once its day was over** (`EventStore.hasAttended(_:)`: `Tracking.hasTicket` — a lottery won or a first-come round got — and not `isUpcoming`), never whether the event is still kept: the library's past (`past`, [LibraryQueries.swift](Eventrail/Model/LibraryQueries.swift)) is every event the reader meant to go to, won or not, and an imported attendance history counts as attended only where a round says so. So nothing anywhere supposes a ticket for a past event — the ticket sheet asks the seat and cost of a past event only once a round says there was one, as it does of one ahead. What the reader says of a past event they went to without saying how the seat was got is `LotteryEntry.ticketHeld` (`Tracking.recordTicket()`): no round and no applications, so it moves no lottery figure — the same entry an older record's bought ticket is folded into, with a fixed id so two devices recording one event write the same list — given in bulk by My Events (the selection's ticket button, and `TicketReviewView` after an import). `EventStore.status(for:)` works the badge out from that — ticketed ahead and attended past with a ticket; planned ahead and No Ticket past (`unticketed`) for a kept event without one; untracked otherwise — and the event sheet's timeline says Attended only with a ticket (Ended without). Don't re-add a field for either.
- **In the store it is six columns on the event's `LibraryEntry`, and the lotteries a row each** — see *Persistence and sync*. The columns are one part of the entry with one date (`trackingChanged`), beside the membership's and the heart's. `Tracking` still carries `edits`, a date per field, for the archive: a backup, a restore and an older build's file are merged answer by answer. An entry has no per-field dates, so its tracking record goes into an archive with none (every answer as old as the part) — save the lotteries, dated by their newest row where that is newer or older than the part (`LibraryDatabase.stampedTracking(of:rows:)`). A field added here has to be named in `Tracking.Field` too; the switches in `sameAnswer(for:as:)` and `take(_:from:)` will not compile until it is. **The one exception is `currency`**, which rides with `.cost` as one answer: ¥9,900 and $99 are two answers, and settling the amount and the currency apart would make a third nobody gave. A currency is written only beside an amount — the ticket sheet holds one picked before any amount in its own `@State` — and goes when the amount is cleared. **So the cost is one column, `price`** — the amount as typed and its currency after a space ("9900 JPY", "49.99 USD"; the amount alone for yen from before currencies), empty for not written down (`LibraryEntry.priceText(of:in:)`) — on Shawn's word, October 2026: as two columns, CloudKit could settle them apart, and a device that changed only the currency and another only the amount left ¥9,900 read as NT$9,900. The two columns before it (`costHundredths`, `costCurrency`) and the whole-yen `cost` before those are read only where `price` is empty, and emptied when the cost next *changes* — not on every write: rewriting a cost the reader did not touch, to move it across, would race another device's change to it. **The lotteries are `LibraryLottery` rows**, one per round (on Shawn's word, October 2026): kept as one JSON column on the entry, two devices each adding a round while apart left whichever reached iCloud last. A row holds the round as JSON with its keys sorted (`LotteryEntry.rowText(of:)`), its place in the list as written (`position`, which orders two rounds of one kind) and when it was written; a round taken out is `isRemoved`, never a deleted row. Written through `LibraryDatabase.writeLotteries`, which touches only the rounds that move — so a change to the lotteries alone leaves the entry unwritten. The old column, `lotteries` (the list as JSON, `LotteryEntry.columnText(of:)`), the older `lotteryEntries` count and the `ticket` answer folded into them are read only for an event with no row yet, and never written again: the first change to such a list writes the whole of it into rows, each round left as it was dated when the entry last changed rather than now, so a device moving its copy across late cannot outrank a round another device has since changed or taken out, and a round already taken out written as a removed row. An entry folded into another carries those old columns across with its tracking part (`absorb`). **A round this build does not read back whole is written over only where the reader changed that round** (`LibraryLottery.write` compares what it reads back, as `understands(column:)` guards the old column): a round a later build wrote must not lose its new parts because another round beside it changed. **One it cannot read at all is in no list it reads, and is never taken for a round the reader took out** (`LibraryLottery.holdsUnreadableRound`): only a removal of the event and Delete All, which empty the whole record, take it out (`writeLotteries(…, clearing:)`). Each text is decoded once and kept (an `NSCache` keyed by the text).
- **`Tracking` decodes every key as optional, by hand.** The synthesized decoder treats a key an older record lacks as an error, and an error thrown there is not one record lost but the whole archive — a backup, or the library file an older build left to be moved in, reads as nothing. That is what the old lottery count did before the hand-written `init(from:)` in the extension existed. Encoding stays synthesized, and the init lives in an extension so the memberwise one survives. **Any field added here must be decoded with `decodeIfPresent`.** `LibraryArchive` says the same thing about its own new keys and answers it by making them optional.
- `MoneyAmount` and `EntryCount` (a round's applications, in [Lottery.swift](Eventrail/Model/Lottery.swift)) are `ParseableFormatStyle`s because no built-in style takes an optional and an emptied field has to read back as nil rather than 0 — which the applications field then writes as 0, "not written down". Both read the digits out of whatever was typed — `MoneyAmount` the locale's decimal point too, and as many decimals as the currency has (none for yen) — so the separators the style itself wrote survive an edit, and a full-width １２３４ from a Japanese keyboard is the same number as 1234. A price is printed through `Currencies.format`: with its cents where it has any and none where it has none (NT$3,800, $49.99), in the reader's locale's symbol (CNY is CN¥ in English and ¥ in Simplified Chinese, whose yen is then JP¥); a figure *worked out* — a conversion, an average — to the whole unit.

## Where a hall is

Eventernote publishes a hall's name and its address and no coordinate, and this app does not run the Google script behind the site's own `map_canvas`. So a placing is worked out here, in three tiers, all behind [VenuePlaces.swift](Eventrail/Services/VenuePlaces.swift) and keyed by the hall rather than the event — two events at the same hall are one question. The answers are kept per device, because a hall does not move — in a `KeptFile` in Application Support rather than Caches, since Clear Cache leaves them alone and rebuilding them is hundreds of searches. **An answer goes only once nothing has wanted it for a year** (`VenuePlaces.hasLapsed`), counted from the last time anything read it (`Answer.used`, noted at most once a month) — and every hall the library holds is read as the app launches (`timeZones(for:)`), so none of them ever goes. Counted from the asking, as it once was, every hall a first import placed would have lapsed on one day a year later, and the next refresh would have asked Maps about all of them at once.

1. **Apple Maps**, asked for the hall by name and judged by the address: a place is the hall when the address Maps publishes for it is the address Eventernote published. Nothing judges an answer by reading its name back, which is hopeless — Kアリーナ横浜 is "K-Arena Yokohama" on an English phone, and a search for メルセデス・ベンツアリーナ returns a Mercedes dealer in Nara. This is the only tier that yields an `MKMapItem.identifier`, so it is the only one that can open the hall's own card in Maps.
2. **[JapanAddresses.swift](Eventrail/Services/JapanAddresses.swift)** — the address search 国土地理院 publishes — where Maps answers nothing. That case is commoner than it sounds and often has nothing to do with the hall: MapKit's search is served by whichever provider covers wherever the *device* stands, and the one serving mainland China carries no Japanese venues, so a reader in Shanghai would otherwise have every hall in their library go unplaced. The register answers the same from anywhere, and grades its own match — only 7 and up (the block, the building number) is believed.
3. **[VenueBuildings.swift](Eventrail/Services/VenueBuildings.swift)** — OpenStreetMap, asked which building at the block the register placed carries the hall's name — is an upgrade rather than a rescue, and every candidate is held against a coordinate the register already vouched for (800 m). It is governed by the per-device `preciseVenuesEnabled` switch in Settings.

**On a phone whose Maps is the mainland-China provider, Maps is asked only about the mainland.** That provider has no Japanese venues and, asked about a hall in Seoul, offered a mainland place that merely shared the number 145 with the address — the address check compares numbers, and one shared number is all it takes. So `VenuePlaces` first asks Maps once per launch whether it can see Japan (`mapsSeesJapan()`: a search for 東京駅 that lands in Japan or does not), and where it cannot: a hall in Japan skips Maps and goes to the register (then OpenStreetMap under the switch, as ever); a hall whose address `VenueCountries.isMainlandChina` reads as the mainland is asked of Maps with no hint; every other hall abroad — Korea, Hong Kong, Macau, Taiwan and beyond — is asked of OpenStreetMap directly (`VenueBuildings.place(named:at:country:)`: the address as the anchor, then the named building within 2 km of it, or the name alone only inside a country the address plainly names). That search is governed by `preciseVenuesEnabled` like every other OpenStreetMap request — **the switch off means OpenStreetMap is never asked anything**, so on that phone a hall in Japan stays at the register's block and one abroad stays unplaced — and it keeps the rest of the OpenStreetMap rules: only from a sheet or the Settings refresh, never from an import. Both refusals are `Deferred`, which writes nothing down, so the first sheet or refresh after the switch goes on asks again. OpenStreetMap carries no zone, so such a hall is dated by its country where the country keeps one clock (`VenueCountries.timeZone(forCountry:)`) and left on its written clock otherwise. The mainland and country readings are text heuristics over the published address, and no API can replace them: the addresses that need them are the ones members wrote in Japanese kanji and katakana, which is exactly what OpenStreetMap fails to find. They cover every province-level division of Korea, Taiwan and the mainland and the districts of Hong Kong and Macau, in local script, kanji, katakana and English; a name Japan shares (台東, 大田, 桃園) is listed only with its suffix. A miss costs a fallback, never a wrong country. The mainland reading — a province or city *with* its 省/市 suffix, since Taipei's streets are named for mainland cities — and leans towards "not the mainland", which costs a slower answer rather than a wrong country. On any other provider nothing here changed. OpenStreetMap files Hong Kong and Macau under `cn`, so `countrycodes=hk` finds nothing: those two are searched inside a bounding box instead (`VenueCountries.searchScope(for:)`). **The one name-only search** is a fallback for a hall whose page published no address at all (歷山酒店-宴會廳): where the *event's title* names a city `VenueCountries.country(of:)` knows (香港, ソウル, 台北…), OpenStreetMap is asked for the name — then its shorter forms (`VenueBuildings.shortenings(of:)`) — inside that country or box only, on every provider, under the same switch and the same sheet-or-refresh rule. A title naming nowhere leaves the hall unplaced, as before. **That provider draws its tiles in GCJ-02**, and its own search answers come in GCJ-02 too, but an OpenStreetMap coordinate is WGS-84 and MapKit does not shift a pin it is handed. So `Answer.placing` shifts an OpenStreetMap answer through `MainlandOffset` wherever the answer came back in `cn` (the mainland, Hong Kong and Macau, as OpenStreetMap files them), `hk`, `mo` or `tw` — by the country the answer carries (`Answer.country`), not by the address reading, so a mainland hall the lists missed is shifted too; answers written before there was a country fall back to boxes round Hong Kong, Macau and Taiwan — while `VenuePlaces.mapsIsMainland` (the last probe, kept across launches) says the phone is on that provider — as it is drawn, never as it is stored, so the same answer lands right on another provider. The calendar mirror leaves an entry at either drawing alone (`Placing.otherDrawing`): an iCloud calendar is one entry for every device, and a device on each provider would otherwise put its own pin back on every mirror — and it never writes another answer over Apple Maps' (see *The calendar mirror*). All three were checked on a phone in Shanghai, and so were Korea and Japan — which that provider does **not** shift: don't add them. Korea once looked off, and it was a name, not a coordinate system — see the shortenings below. A name is shortened by what its break means: after a **space** the part after it is tried first (高麗大学校 化汀 体育館 → 化汀 体育館, since 高麗大学校 alone is the whole campus, 800 m from the arena), after a **dash** only the part before it (歷山酒店-宴會廳 → 歷山酒店, since 宴會廳 alone is any banquet hall in the city). **What a name carries in brackets is asked for last** (`VenuePlaces.inBrackets`, `VenueBuildings.queries(named:aliases:)`): every search drops the brackets, since in Japan they hold another name the hall goes by, but abroad members put the hall's own local name there — ドーセット・ツェンワン香港（香港荃灣帝盛酒店） — and the katakana finds nothing where 香港荃灣帝盛酒店 finds the hotel. So once the name and its shorter forms have found nothing, OpenStreetMap is asked for the bracketed name, before settling for the address alone; nothing found before it changes. A Korean address is often written in kanji and katakana rather than Hangul (畿道高陽市一山西区キンテックス路 is KINTEX), so `VenueCountries.country(of:)` also reads Korea's provinces and the suffixes only its cities carry (広域市, 特別市) — never a bare city name Japan shares, like 大田. Rulesets 9 to 12 re-ask only answers outside Japan (`japanRuleset`); 13, the brackets, re-asks only "no such place" (`foundRuleset`) — an answer due to be re-asked is passed over by the calendar mirror and the clocks until a sheet or a refresh reaches it, so a found one is never sent back for a fallback that runs only after a failure. Each threshold counts from its ruleset on, never at it alone (`VenuePlaces.stillStands(madeUnder:found:inJapan:)`): compared for equality, raising `ruleset` sent back every hall placed under the one before unless the thresholds were moved with it.

**Who is allowed to ask, and when, is the load-bearing part.** A hall is looked up when the reader opens an event at it — one question, asked because somebody is waiting. The calendar mirror reads what has been found and searches for nothing itself: a run of hundreds of searches is what got this app throttled into placing nothing at all. An import places the halls it brings in (`EventStore.placeArrivedVenues`), an event added by hand from Search is placed on the same terms through a one-at-a-time queue (`placeAdded`, which reads the event's own page first wherever the search row carried no address), and `VenuePlaces.refresh(_:)` from Settings is the one way to ask about everything — paced at 500 ms, and mirroring the calendar once at the end rather than per hall. Tier 3 is reached only when the reader asks: the sheet in front of them, and the Settings refresh they started. OpenStreetMap's policy allows one request a second across all of an app's users, discourages bulk geocoding, and tolerates a small one-off run from one device made one request at a time with the results kept — so `VenueBuildings` names itself with the app's repository in its User-Agent — the policy asks for a way to reach whoever makes the requests, and this once carried Eventernote's address — paces itself at 1.1 s, each hall is asked once for good (`Answer.triedBuilding`, carried across refreshes by `VenuePlaces.carrying(_:from:)`), a refusal stops the rest of the run's narrowing, and an import (`placeUnplaced`) **never** narrows. A block settled while narrowing was not allowed is narrowed the first time a sheet opens it (`VenuePlaces.narrowed(_:for:)`). Crediting 国土地理院 and OpenStreetMap is a condition of use and is done in [AboutView.swift](Eventrail/Views/AboutView.swift) — don't drop that footnote.

**A placing also settles which clock the hall keeps**, because Maps carries a zone with the place and the search is already being made. `VenuePlaces.timeZones(for:)` reads those back for the whole library without asking anything, the same way the calendar mirror reads placings, and `EventStore.retimeEvents()` applies them wherever a placing lands — an import, an event added by hand, a sheet, a refresh, a merge, a restore, and once at launch. Only a hall *outside* Japan is ever asked about: Japan is one zone, so a placed Japanese hall answers itself from its own coordinate, and the handful of halls a reader has abroad are re-asked exactly once (`Answer.needsZone`) rather than the whole cache being re-read. Maps answering with no zone at all leaves the hall on Tokyo time rather than guessing.

**The map under a hall says how its lookup came out** (`VenuePlaces.Lookup`, drawn by `VenueMap`), because one empty panel looked the same whether the answer was still on its way or had come back with nothing: "Finding the venue on the map…" under a spinner while it is asked; "Couldn't find this venue on the map" once every source this device may ask had nothing (a `Deferred` included — OpenStreetMap switched off); "Couldn't load the venue's location" with Try Again where the search did not get through, which writes nothing down; and a struck-through pin alone where there is no hall to ask about. An event sheet keeps each answer with the question it answered (`venueKey`), so an answer about a search row's hall — no address yet — reads as still looking while the page that brings the address is read, and as not loaded where that read failed.

`VenueRegions` is a different question with a similar name: not where a hall is, but which of the site's five areas it is in, for the Following tab's filter. It reads Eventernote's own pages rather than any map service.

## The Event Passport

[EventPassportView.swift](Eventrail/Views/EventPassportView.swift), reached from the Me tab, is the reader's own record of where they have been: a map of the country with every hall they have stood in, and what the library adds up to around it. [PassportStats.swift](Eventrail/Model/PassportStats.swift) is one pass over one slice of it.

- **Everything on it is read off the library's own `@Query`** (`LibraryEntry.library`, then `past`): what was attended in it (`EventStore.hasAttended(_:)`, a ticket and the day over) for every card but one, and the whole of the past for the Lottery Entries card (`PassportStats(events:lotteriesOf:)`), since a lottery lost on an event never attended is as much how the lotteries went as one won. With nothing attended the screen is its empty state — with Record Tickets, opening `TicketReviewView` on every past event with nothing written on its Ticket Details (`EventStore.awaitsTicket`), not only what has come since the last pass — and the lottery card under it where there are lotteries. Nothing here asks Eventernote anything, and nothing here is a second record the reader has to maintain — the same argument that keeps attendance from being a field.
- Computed on the screen rather than stored, and cheap enough to be: a handful of passes over a few hundred events. Storing it would mean keeping it in step with every note, every import and every merge; a `let` cannot go stale.
- `PassportScope` is all-time or one year, and a year the reader has nothing in is never offered — an event attended or a lottery round tried, since the lottery card is counted over every past event. A year of lotteries alone shows the empty state over the lottery card, its Record Tickets held to that year. It is deliberately not remembered between visits — a filter left on from a fortnight ago would have somebody reading one year and believing it was all of them.
- Every total says what it was counted over rather than implying it read every event: `timedEvents` beside `totalDuration`, because Eventernote publishes a finish time for a minority of dates — and an event timed past `PassportStats.longestEvent` (16 h) is not counted as timed at all, since a finish typed earlier than its start reads as the next morning and would top Longest at twenty-odd hours; Shortest and Longest Event each open every timed event behind their See All, from their own end, as Highest and Lowest Price open every ticket — the lottery card's win rate out of the rounds drawn, beside the count of events they were on, and Ticket Spending over the events a price was written on (`PassportStats.tickets`: a ¥0 seat counts, a blank one does not), broken down by the ticket's class (`ticketClass`), the three `SeatClass` chips keeping one colour each and an event naming no class going last as Unspecified.
- **The Lottery Entries card is how the reader's lotteries went**, as `Eventrail v4.dc.html` draws it: the win rate, a bar of won against lost, then Rounds, Entries (the applications) and Rounds to Win, then By Round, By Seat, Entries to Win and the events applied for hardest (`PassportStats.lotteryTally`, `lotteryRounds`, `lotterySeats`, `winTypes`, `topLotteries`), each event with a dot per choice tried (`PassportStats.choiceMarks(of:)`), drawn as the design draws its dots — filled 7 pt discs 3 pt apart in one row, in the legend's colours: grey for a choice lost, orange for the one won and nothing after it, so a seat won with the first choice is one orange dot, and faint where no result was written. Not hollow rings for the losses, nor a gap between rounds: both were tried and read worse. Counted over the lottery rounds alone (`LotteryEntry.isLottery`): not a first-come round, which is a seat got rather than a draw, and not the ticket an older record held (`foldLegacyTicket()`, no round and no applications), which would put a win into every rate. Every rate is out of the rounds whose result was written down; a round with none is No Result — the ticket sheet's word for a lottery pending once its event is over — counted and drawn apart, never as a loss. A class of seat's rate is the wins *in that class* out of the drawn rounds counted for it. A round won in another class it asked for is no win for this one, and which way that class lies decides the rest: won *higher* (S over A over General, `SeatClass.order(of:)`; for a class the chips do not offer, the order the round's choices were ranked in), the round is not counted for this class at all — it was never this class's to win; won *lower*, it is "other seat". So General, the lowest, is only ever won or lost, and Other seat is in the legend, and on a row's line, only where some class has one. A win naming no choice says nothing about any class and is left out of By Seat. By Seat badges and names each class as the spending card does, from one set of styles (`SeatStyle.styles(for:)`, the spending card's classes first so its spare colours never move): the same coloured letter, centred on what it heads (the name and the tally here; the name, the spread and the average on the spending card), and the name in the reader's language alone, not the ticket's own printing beside it. Rounds to Win is, over the events with a win, the rounds up to and including the first one won, in the order the sale ran them (`Tracking.lotteryRounds`). Entries to Win is the applications over those same rounds, filed under the class the first win got (`PassportStats.WinType`; a win naming none last, as Unspecified, and a win whose rounds have no applications written down left out), drawn as the spending card draws By Ticket Type and from the same parts — one bar split by wins per class, then each class's count, share, spread on one scale from the fewest to the most and average, the scale's ends under the last row — and a row opens that class's wins, most applications first, in the same sheet as By Seat's. A row of By Round or By Seat opens the events it counted (`PassportStats.roundEvents`, `seatEvents`) in the sheet Top Lottery Entries' See All opens (`PassportLotterySheet`), newest first, each with the applications and only the rounds that row counted — so an event whose S seat was won is not among A's or General's — dotted choice by choice: under By Round as on the card, and under By Seat every choice up to the one that asked for that class (`PassportStats.seatMarks(of:for:outcome:)`) — a class asked for second carries how the first went before it — the last in the colour of how it went for the class (won, other seat, lost), as the legend over it says.
- **Ticket Spending is added up in one currency**: the reader's Default Currency as the screen opens, or any other picked from the capsule in the card's corner, for that visit only (not remembered, for the reason `PassportScope` is not). A ticket paid in another currency is converted at today's rates (`ExchangeRates`, the one thing on the screen read from anywhere; `CurrencyRates` through the euro). Where every ticket was paid in one other currency (`PassportStats.paidCurrency`), the total prints what it was there beside it, and the Avg. Price, Highest and Lowest readings and each class's range carry an ⓘ that opens it in a popover (`PassportPaidPopover`: the figure as paid and nothing else); paid in several, there is no such figure, so none is offered, and the day of the rates is the card's caption instead. **The card is the same height in every currency**: anything a conversion adds goes beside a figure or into a popover, never on a line of its own — a line that came and went with the menu moved everything under it. That is why the rate day is a caption only where the tickets were paid in several currencies (every choice converts, so the line never goes), and why each ⓘ sits on its text's baseline (centred, it hung below the line and grew its row). Checked by screenshotting the card in both currencies and comparing where each row of text starts. A ticket the rates cannot convert — none held yet, or a currency they do not carry — is left out and counted (`unconvertedTickets`), never read as yen. A library kept in the currency it is read in needs no rates at all, and the screen asks for none. Under the classes come the dearest and the cheapest ticket, over seat type chips kept to one line (`ViewThatFits`: headed "Seat Type" where that fits, the chips alone where it does not, scrolling sideways past that — wrapped, one chip sat alone on a second line), each with a See All listing every ticket under the chips from its own end: dearest first behind Highest Price, cheapest first behind Lowest Price, titled for that end. A row under By Ticket Type opens the same sheet on every ticket of its class, dearest first, whatever the chips are set to, titled with the class's name.
- **An event is not always at a hall.** Eventernote files streams, undisclosed rooms and "somewhere abroad" under placeholder venues whose names open with `!_` (`!_国内外各所 (ライブビューイング等)`, `!_東京都内某所`). `Event.isAtHall` is false for those and for an empty venue: the event still counts, but adds no hall, no prefecture and no pin, and `VenuePlaces.Venue` refuses to look one up by the same test (`Event.namesHall`), save that a hall with no name and a published address is still asked about.
- `PassportStats` takes `tracking` as a closure rather than the store, which is what keeps the whole type `nonisolated` and testable with no `EventStore` behind it.

## The ticket stub

`Eventrail v4.dc.html` §9a: the reader's ticket as a keepsake image. ## Persistence and sync

The library is a SwiftData store, `Library.store` in Application Support, opened by [LibraryDatabase.swift](Eventrail/Services/LibraryDatabase.swift), and **synced by SwiftData with nothing on top**: a record another device wrote lands as CloudKit settled it — the copy that reached the server last, whole — and nothing here merges, reconciles or writes it back — save where two rows turn out to be about one thing (below). The builds before this one put an archive-based merge after every import (a snapshot before, per-field reconcile after, stamps compared to the millisecond, a fold that merged twins, a prune that rewrote rows, a mirror of each record onto the event's row for older builds). Every one of those was a write the app made on the reader's behalf, and between them they undid removals, hid kept events and kept devices busy trading copies. **Don't bring that layer back.** Make the rows such that CloudKit's rule is the right answer instead.

So the rows are cut by *who writes them*, in six models ([LibraryModels.swift](Eventrail/Model/LibraryModels.swift)):

- **`LibraryEntry`** — everything the reader owns about one event: `inLibrary`, `isFavorite`, and the tracking answers, with a date for each of those three parts (`inLibraryChanged`, `favoriteChanged`, `trackingChanged`, read through `changed(_:)`) and one `modified` for the whole. Each write dates only the parts it gives (`LibraryEntry.give(_:dated:)`): an import adding the event dates the membership and says nothing about a heart or a note. An entry an older build wrote carries no part dates, and every part of it reads as of `modified`. Written only when one of those changes (`EventStore.edit(_:keepingFacts:_:)`, which writes nothing where the answers are unchanged) — by the reader, or by an import of their account adding the event (`adopt`). Never by a read of the event's page. A removal is `inLibrary` false, never a deleted row, so it travels; Delete All empties every entry the same way. It also carries `kept`, a JSON copy of the event as it stood when the reader last wrote there, **because CloudKit sends an entry and the facts beside it as two records in whichever order it likes**: seen in two devices' store history, an add's entry-equivalent reached the other device 17 s before its facts, and My Events, drawing only from the facts, left out an event every other screen called kept. `EventStore.events(of:where:)` draws from the facts where they have arrived and from `kept` where they have not.
- **`LibraryEvent`** — Eventernote's facts about one event, flattened into columns: a copy of its page. Anything may rewrite it (an import, a read of the page, a hall's clock once known), so it holds nothing the reader decided, and a copy sent by a device that was behind costs at most an older copy of a public page. **It is never emptied or deleted when the event leaves the library**: a row emptied on one device lands empty on every other. The getter `facts` reads any row whose columns hold a title, because the builds before entries dropped facts by clearing `hasFacts` and left the columns.
- **`LibraryLottery`** — one lottery round the reader entered for an event, keyed by the event and the round's id (a round carried over from before entries has the same id in every event). Its own record so two devices each adding a round while apart keep both; the same round changed on both is settled by which reached iCloud last. A round taken out is `isRemoved` rather than a deleted row. See *What the reader records*.
- **`FollowingReadMark`** — whether one Following date was read. Its own record because it is written as a row is opened, on whichever device is in the reader's hand. Deleted by `LibraryDatabase.pruneReads(in:asOf:)` once its event is three days gone — by the event, so every device drops the same marks.
- **`FollowedPerformer`** (the follow and who they are) and **`LibrarySettings`** (the linked account, recent searches and the import dates — one row).
- **`LibraryMembership`** is read once and never written: see the migration below.

The screens read it with `@Query`, through the descriptors in [LibraryQueries.swift](Eventrail/Model/LibraryQueries.swift) (`LibraryEntry.library`, `LibraryEntry.favorites`, `FollowedPerformer.followed`), so "the library" means the same rows everywhere. **A screen turns its entries into events through `EventStore.events(of:where:)`, never by reading the rows itself**: it answers each entry through the one kept for its event (so two entries for one event list it once, as the newer says), passes the flag the query asked for (`\.inLibrary` or `\.isFavorite`), and keeps each event's copy until a write touches it (`save()` names the events it wrote; `reindex()`, after anything landing from elsewhere, forgets them all), because reading nine hundred rows' forty columns took some 17 ms a time, several times a redraw, on every tab at once. **The reader's record goes the same way**: `tracking(for:)` keeps each event's `Tracking` (`records`), forgotten as the event is written (`edit`, `save()`) and all at once on `reindex()` — the Passport and every badged row ask for it several times a redraw, and reading an entry's columns each time cost the Passport some 35 ms a redraw on nine hundred ticketed events. `EventStore` is where every write is made; it keeps no copy of the library, only an index of rows by id — the row `deduplicate` will keep, where there are two (`LibraryDatabase.index(_:by:preferring:)`) — which is how anything holding an event, kept or not, reads that event's entry and facts. `RootView` hands the store and the container down together with `.library(store)`, which the previews use too.

- **Two rows for one thing are expected, and one is kept** (`LibraryDatabase.deduplicate(in:)`, Apple's own answer to CloudKit having no unique constraint). After every import from iCloud and every open, each set of rows sharing an event id or actor id — or, for lottery rounds, an event id and a round id — keeps the one its model's `isPreferred` picks — the entry, round, mark or follow written last, the facts read latest from the page — with the lower `uid` breaking a tie, so every device keeps the same row and none deletes the one another kept; the rest are deleted. **Two entries are folded first** (`LibraryEntry.absorb(_:)`): the kept one takes every part another gave later. Two entries for one event were written by two devices that had not seen each other's, so the one written last is not the reader's word on the parts it never gave. Kept whole, it lost data on the most ordinary path there is: a device set up afresh, linking the account and turning sync on together on the Welcome screen, imported the account before iCloud had brought it the reader's entries. Its own entries said only "in the library", were the newer, and the fold deleted every note, ticket, seat, cost and heart on every device. Part by part, the same way on every device, every device ends on the same answers, with one write. The settings are folded too, since each device writes its own row the first time the reader searches: field by field (`LibrarySettings.absorb(_:)`), so neither the link nor the searches is lost.
- **Every import from iCloud is followed by `LibraryDatabase.settle(in:)` — taking in what an older build left, then the fold — and then a reindex, whatever it brought** (`LibraryDatabase.finished`) — even a failed one may have landed part of what it read. An earlier build skipped the reindex when it judged an import had brought nothing new, judged it from a snapshot taken on the main queue after the import had already landed, and left My Events on a stale index.
- **A tombstone answers for the reader's devices, not for Eventernote** — the premise at the top of *The Eventernote import*. An import (`EventStore.adopt`, `adoptFollows`) raises what the linked account still lists, tombstone or not, and re-adding by hand always has.
- **iCloud sync is SwiftData's own.** With the switch on, the same store is opened with `cloudKitDatabase: .private("iCloud.moe.shawn.Eventrail")` and Core Data mirrors it into the private database's `com.apple.coredata.cloudkit.zone` as `CD_` records. **Nothing is `.allowsCloudEncryption`, on purpose.** The CKSyncEngine build kept its whole payload in `encryptedValues`; this one keeps every column as a plain CloudKit field in the reader's private database — encrypted at rest by iCloud, readable by no one but the reader's devices and Apple, never by the developer. The records are a seat, a price, a count and a note beside a public event, and end-to-end encryption would cost field renames (Production already holds these fields plain, and a field's encryption cannot be changed once it exists), values the Console cannot show when sync goes wrong, and a failure mode of its own when the reader resets their iCloud Keychain. Encrypting any of them later means a new field name. Every column has a default and nothing is `.unique`, because CloudKit allows neither; the configuration names `.none` outright when the switch is off, since left alone SwiftData picks `.automatic` and syncs whenever the entitlement is there. **CloudKit settles two devices' edits to one record by which reached it last, not by when they were made**, and that is accepted. The window is not a few seconds: it runs until the other device has fetched the change, which is minutes at best and days for a device that was offline. Core Data looks to send only the columns a save changed (its serializer has a `fullyMaterializeRecords` switch, and its exporter reads the changed properties out of persistent history), and `update(_:to:)` dirties only the columns that move, so two devices answering *different* parts of one entry should both stand. Apple does not document this. Until it has been seen on two devices, one offline, treat a heart given on one device and a note on the other as possibly lost to whichever reached iCloud last.
- **What the builds before entries kept is taken in wherever nothing answers for it yet** (`LibraryDatabase.adoptLegacyRecords(in:)`), every time the store opens and after every import (`settle(in:)`): whatever the store holds in `LibraryMembership` and in `LibraryEvent`'s old columns (`inLibrary`/`inLibraryChanged`, the heart, the tracking answers, the read) becomes an entry or a mark for any event that has neither, newest copy winning. Not once per device: a device reinstalled or newly set up opens its store empty and only then hears from iCloud what an older build left there, and a flag set on that first empty open (`libraryEntriesAdopted`, as a build once did) meant it was never taken in. Never over an entry or a mark already there, so after the first run it usually finds nothing. Each device takes in its own copy, and the entries two of them make for one event meet in the fold. What an older build writes about an event this build already has an entry for is not listened to: **every device has to run this build**, and a tester on an older one will not see changes from a newer one or be seen by it. The old columns and `LibraryMembership` stay in the schema because CloudKit's schema only ever grows.
- `LibraryArchive` is no longer how the library is kept or synced, but it is still the backup file's format, the format older builds wrote to `library.json` and the legacy iCloud zone, and the merge those are taken in by. `LibraryDatabase.archive(in:)` turns the store into one (each of an entry's three records dated by its own part, and a part never given as `.distantPast`) and `apply(_:to:)` writes one back — **additively**, touching only rows whose answer moves and deleting nothing, since every caller hands in the library already merged with what it is taking in. Each part written there takes its own record's date — a new entry every record the archive holds, a removal included — and the entry the newest of them, so a restore raised as of now outranks every device's older copy. **A part whose answer stays but whose record is newer is dated again too**: that date is what a second entry for the event is folded against, and left at the older one a copy given in between would outrank the answer just taken in. Lottery rounds left as they were are dated again only where the archive raises the event's list past its newest row, as a restore does: the store's own archive dates each list by that row, and merged back as it stands it once carried every older round up to it and sent it again.
- Event facts from two copies of the archive are settled by `Event.readAt`, when that copy's page was read (`LibraryArchive.settle`): the later read's answers stand, gaps included — a start time or a 概要 missing from a read of the page (at a `detailFormat` no older than the copy it lands on) was taken off the page, and `Event.merging` clears it; only a listing row, or a read by a build that looked for fewer fields, has its gaps filled from the other copy. The hall's address and capacity always fill gaps, since they come from a second page whose failure an import shrugs off.
- **Only what moved is written.** Every row written is a record CloudKit sends again, so model columns are assigned through `update(_:to:)`, which skips an equal value. **A read of an event's page that finds nothing new is not written at all** (`Event.isSameRead(as:)`, everything but `readAt` compared, `editedAt` by the day), and for the same reason `editedAt` is dated to the start of the day on the site's clock (`Event.siteDay(of:)`); counted back from the moment of reading, every read carried its own hour and read as an edit. Saves are coalesced 400 ms behind an edit — a note field writes on every keystroke — and flushed as the app leaves the foreground (`saveNow()`); the rows change at once, so every screen shows an edit before it is saved. **A save that fails is said** (`EventStore.saveFailure`, under Export Backup in Settings, since a backup is written from the rows saved or not) and tried again on coming back to the app; the edits stay in the context meanwhile and go with the next save. **So is a backup that could not be written** — on the same row, with a tap to try again — and a store that cannot be read throws rather than standing in an empty library, which would export a backup of nothing, or let a restore write the file's older copies over this device's newer ones.
- **A field added to `Event`, `Tracking`, `FollowingRead` or `PerformerProfile` needs a column** on its model, with a default, and a line in the accessor that builds the value (`LibraryEvent.facts`/`write(_:)`, `LibraryEntry.tracking`, `FollowingReadMark.read`, `profile`). SwiftData migrates an added column by itself and CloudKit's schema only ever grows; a removed or renamed one is neither. `LibraryDatabaseTests.anArchiveComesBackOutSayingWhatItSaid` catches a field left out.
- **The store is made once per process, by `Launch.shared`** ([RootView.swift](Eventrail/Views/RootView.swift)), with `FollowedDates` and `VenueRegions` beside it — never in a view's initializer. SwiftUI makes a view value as often as it likes and keeps only the first `@State`; every other `EventStore` a `RootView()` made opened the library again, and with iCloud Sync on that was a second CloudKit mirror of the same file, which Core Data refuses (`NSCocoaErrorDomain` 134422, "another instance of this persistent store actively syncing with CloudKit in this process") and keeps retrying — the app stuttered for as long as syncing was on. `LibraryDatabase` also refuses to mirror a file another database in the process is already mirroring (`syncingFiles`).
- **Turning sync on or off opens the store again** (`LibraryDatabase.setSyncing(_:)`): a container's CloudKit setting is fixed when it is made. **The store is never opened with CloudKit before the iCloud user has been checked** — not at launch either, where the switch alone used to open it that way: an account changed while the app was not running would have had the last user's library sent into the new one's database before any check answered. So every launch opens the store without CloudKit and `checkAccount()` opens it again with CloudKit (`startSyncing()`) once the user is the one written down; a check that cannot answer (offline) leaves it unsynced, asks again in a minute and on coming back to the app (`resumeSyncing()`). SwiftData keeps persistent history with CloudKit off too, so what was written meanwhile is sent once it starts. **A swap never drops an edit:** where the old context will not save, what it holds is folded into the new container by the archive's merge, and stays there unsaved until a later save succeeds. The old container is held for a second, so a screen still drawing one of its rows is not left holding a row whose store has gone, and then let go: a CloudKit container kept alive goes on importing pushes and exporting what the new one writes to the same file, so holding it until the next swap meant the off switch did not keep the library out of iCloud. **This process's claim on the file (`syncingFiles`) goes with that container**, not with the switch (`letGoOfRetired()`): released at the switch, a reader turning sync off and on again within the second had a second mirror opened beside the one still being let go. Turned on again inside the hold, syncing waits for it (`startsWhenLetGo`). `EventStore` reindexes at once, and every `@Query` follows the new container through `.library(store)`.
- **How sync stands** comes from `NSPersistentCloudKitContainer.eventChangedNotification` (SwiftData is built on it) and `CKContainer.accountStatus()`, as `LibraryDatabase.SyncStatus` — worked out by `SyncOutcomes`, which keeps the last setup, import and export apart, so an import from the other device does not clear iCloud Full on this one's exports, nor an export an import that failed; only offline and unavailable pass with any success — and `lastFetched` — what Settings shows under the switch, "Fetched from iCloud …" — is the end of the last **import** that succeeded, kept per device across launches (`iCloudLastFetched`, cleared whenever the switch moves). Not an export: every launch and every return to the app sends whatever is waiting, usually nothing, and a time that moved with those read "synced just now" on a device that had not fetched the other one's changes for minutes. When a device fetches is Core Data's call: it imports on a push from iCloud, which is best-effort and held back shortly after a fetch, not on a return to the app and not reliably on a launch — seen in the store histories as changes that waited from 5 s to nearly 6 min, by how recently the receiving device had fetched and not by what the change was. There is no public API to fetch now; don't build one by reopening the container. **A change of iCloud account turns sync off** (`SyncStatus.accountChanged`, said under the switch while it is off). The user record the library first synced with is kept per device (`iCloudSyncAccount`, cleared whenever the switch moves), and it is checked as syncing starts and on every `CKAccountChanged`: a sign-out, or a different user, stops syncing until the reader turns it on again, so one person's library is never uploaded into the next person's private database. **So does deleting Eventrail's data from iCloud** (Settings › iCloud › Manage Storage): CloudKit answers `userDeletedZone`, often inside a partial failure, and `status(for:)` reads it as `SyncStatus.cloudDataDeleted` and stops syncing, since SwiftData left running would make the zone again and send the whole library back into it. An account status that cannot be read, or reads `.couldNotDetermine`, is said as a status rather than left blank, because blank under the switch reads as syncing fine. That is what the CKSyncEngine build did. Core Data also reacts to the change on its own and may purge the rows it mirrored from the account that left; check what it does on a device before telling anyone it is safe.
- `iCloudSyncEnabled` is a **per-device** preference in `UserDefaults` and deliberately does not sync — turning it off on a phone must not turn it off on the iPad. It is **off until the reader turns it on**, like `calendarSyncEnabled`: copying what they have written into their iCloud is theirs to say yes to, and a switch found already on is not an answer anybody gave. So a fresh install reaches iCloud for the first time when the Welcome screen's switch or Settings' says to.
- **A store that will not open is never written over.** It is created with the system's default protection, so before a device's first unlock it will not open at all. The library is then held in memory instead (`LibraryDatabase.isBlocked`), where the reader can go on using it, and `reopen()` — tried as the app comes back to the foreground — folds whatever was written there into the file by the ordinary merge once it opens. Settings says so meanwhile (`EventStore.libraryFileIsBlocked`).
- **The JSON library older builds kept is moved in, not dropped.** `LibraryDatabase.moveIn(from:)` runs every launch: the first time it merges `library.json` into the store, moves it aside as `library.pre-swiftdata.json`, and deletes the CloudKit engine's old `cloudkit.json`; after that there is no file, and it only folds back a copy an older build set aside unread (`library.unreadable-<stamp>.json`, see `LibraryFile.load()`), which Settings counts until it can be read. `LibraryFile` survives to read, with `LegacyArchive` for files from before records carried timestamps; nothing but the tests writes the JSON file any more.
- **What the CKSyncEngine builds wrote to iCloud is read, never written.** SwiftData mirrors into Core Data's zone, so nothing in their `Library` zone reaches the store by itself — a device reinstalled since would start empty, and a device still on one of those builds would never be heard from. So every time syncing starts, `LegacyCloudZone` reads what changed there since this device last read (a change token per device, `iCloudLegacyZoneToken`, cleared with the account) and it is merged in by the archive's rules, like the library file. Each `LibraryRecord` carries its slice as zlib-compressed JSON in `encryptedValues["payload"]`, and one in a `format` newer than 1 is left alone. Nothing is written back, so a device still on an old build hears nothing from upgraded ones.

**What a device finds out for itself is a file, not a preference.** `UserDefaults` holds the per-device switches and nothing that grows. `VenuePlaces`, `VenueRegions` and `PageReads` each keep one dictionary in a [KeptFile](Eventrail/Services/KeptFile.swift) — read once, held in memory, written 400 ms after the last change and off the main actor, writes and removals reaching the disk in the order they were made — as `FollowedDates` and `ListingCache` keep theirs. Placings go in Application Support and the other two in Caches. What a build that kept them in `UserDefaults` left there is moved across on the first read. Like the library file, a kept file that is there and will not open is never written over: the launch starts empty beside it, and each write tries it again and folds what it holds in beneath what the launch found. Nor is one that opens and will not decode — a later build's shape, or one a change got wrong: it is read as empty but moved aside first, as `<name>.unreadable` (the latest copy only), and folded back in beneath the file by a build that can read it. Written over, one wrong change of `VenuePlaces.Answer` would have cost every hall the reader had placed.

`LibraryBackup` is the other copy: one file the reader exports and keeps themselves, with no size ceiling. Sync and backup are deliberately different answers — sync keeps devices agreeing, so a removal travels; a file is the one copy nothing done in the app afterwards can reach.

The file is the app's own format, `.eventrail`: the eight bytes `EVNTRAIL`, a version byte, then the archive as zlib-compressed JSON. The signature makes a wrong file wrong before anything is decoded, and the extension keeps a backup from looking like a document any app may open and edit. It is a container, not encryption. The type is declared in [Info.plist](Info.plist) and reached in code as `UTType.eventrailBackup`; the importer also accepts `.json` so the app's own `library.json`, lifted off a device, can still be read. Three things follow:

- **A new field means a new version byte.** `LibraryBackup.currentFormat` is 10 today. It guards only the container; `LibraryArchive` still decodes its own older files, and a file whose version byte is higher than this build's is refused rather than read with its unknown fields dropped.
- **Opening a backup from Files is a second entry point, not a second implementation.** `CFBundleDocumentTypes` in [Info.plist](Info.plist) claims the type (`LSHandlerRank` `Owner`), `INFOPLIST_KEY_LSSupportsOpeningDocumentsInPlace` has it read where it sits rather than copied into an Inbox folder the app would then have to tidy up after, `RootView` receives it with `onOpenURL`, and both it and Settings hand the file to the same `restoringBackup(_:asking:)` modifier — which asks first only for a file that arrived from outside the app. The type conforms to `public.data` **and not `public.archive`**: conforming to the latter handed the file to the Files app's own archive handling, which failed to unpack it and refused with "inappropriate file type or format" instead of passing it on.
- **Export goes through the share sheet, not `fileExporter`.** Not for want of a permission — iOS lets any app save a file where the reader points it, and the share sheet offers Save to Files anyway — but for the preview. Settings writes the backup into the temporary directory and hands `ShareLink` that URL, rewriting it whenever `EventStore.revision` changes. A `Transferable` would write it more lazily, but handing the share sheet a file that exists is what makes the system compose its own preview — name, kind and icon — instead of leaving a screen to draw a picture of a file.
- **Restoring is `LibraryArchive.restoring(_:)`, not `merging(_:)`.** A plain merge would lose to a tombstone, so a backup restored after "Delete All Events" would bring back nothing. A restore raises the backup's *positive* records over this device's no — the same licence an import has — and only those: a note this device still holds keeps whichever copy was typed later, and nothing the file lacks is dropped. A restore adds; it never erases. The restored archive is written to the rows through `LibraryDatabase.apply(_:to:)`, which touches only the rows whose record changed.

`EventStore.removeAllEvents` empties every `LibraryEntry` — out of the library, unhearted, every tracking answer cleared — rather than deleting it, unfollows everyone (tombstones, like a removal), unlinks the Eventernote account so the next refresh does not import it all straight back — the app's settings stay — and turns every Following date back to unread, writing a `FollowingRead` with no fingerprint rather than deleting the mark, for the same reason a removal is `inLibrary` false and not a deleted row. **Every removal empties the event's record too** (`EventStore.remove`, which the event sheet's button reaches through `toggleLibraryMembership`): its lotteries, ticket, seat, cost and note, on every device, the heart left alone — so an event the linked account brings back comes back with nothing written on it. **So every way out of the library asks first and says so**: the selection trash, My Events' swipe, the event sheet's button and menu, and the checkmark on a search result or a followed date (`LibraryToggle`), all through `confirmingRemoval(isPresented:remove:)` and `EventRemoval`'s words, in [Panels.swift](Eventrail/Views/Components/Panels.swift). A way out added later goes through it too.

**Capability:** sync needs the iCloud (CloudKit) and Push Notifications entitlements in [Eventrail.entitlements](Eventrail.entitlements) at the repo root (outside the synchronized group, so it is not bundled as a resource), wired via `CODE_SIGN_ENTITLEMENTS` in both configurations: `icloud-services` CloudKit, the container `iCloud.moe.shawn.Eventrail`, and `aps-environment` for the silent pushes the engine relies on — with `UIBackgroundModes` `remote-notification` in [Info.plist](Info.plist), since it has no build setting. Simulator builds sign locally and work as-is; a **device build needs iCloud (with the container) and Push Notifications enabled on the App ID in the developer portal**, otherwise signing fails. The Live Activity adds an App Group, `group.moe.shawn.Eventrail`, to both the app and the `EventrailWidgets` extension ([EventrailWidgets.entitlements](EventrailWidgets.entitlements), beside the app's): `REGISTER_APP_GROUPS` has automatic signing register it, but a signing that cannot — Xcode Cloud among them — needs the group and the extension's App ID (`moe.shawn.Eventrail.Widgets`) to exist in the portal first; one device build from Xcode registers both. The watch app's App ID (`moe.shawn.Eventrail.watchkitapp`) is the same: registered by the first device build of the app from Xcode, needed before Xcode Cloud can sign it. It has no entitlements of its own. **The schema is created in the Development environment by the first save and must be deployed to Production in the CloudKit Console before a TestFlight build can sync** — TestFlight and the App Store talk to Production only. Since the move to SwiftData that schema is Core Data's `CD_LibraryEntry`, `CD_LibraryEvent`, `CD_LibraryLottery`, `CD_FollowingReadMark`, `CD_FollowedPerformer`, `CD_LibrarySettings` and the read-once `CD_LibraryMembership` in `com.apple.coredata.cloudkit.zone`; the `LibraryRecord` type the CKSyncEngine builds created is no longer used. A model column added later is a new field there, and has to be deployed again.

## The Live Activity

`Eventrail v3.dc.html` draws one for an upcoming event the reader holds a ticket for: on the Lock Screen and in the Dynamic Island from when the reader turns it on — no earlier than eight hours before the show is over — until it is. [EventActivities.swift](Eventrail/Services/EventActivities.swift) asks for it, keeps it up and ends it; [EventLiveActivity.swift](EventrailWidgets/EventLiveActivity.swift) draws it.

- **Started from the sheet, at once, and never scheduled.** iOS 26 can schedule one (`Activity.request(…, alertConfiguration:, start:)`), and this app did, two hours before the doors — but **iOS ends every activity an app has, scheduled ones included, when the app is updated**: `liveactivitiesd` logs "Stopping uninstalled activity" for each as the new build is installed, seen in the Simulator for a running and a scheduled one alike (October 2026). One scheduled weeks ahead was usually gone by the day of the event, every TestFlight build and every install from Xcode taking it. **And the system ends an activity eight hours after it starts** (Apple's *Displaying live data with Live Activities*), taking it out of the Dynamic Island, so one turned on at ten for a show ending at eight would go at six, as the show began. So the sheet starts one only from `EventActivities.earliestStart` — eight hours (`EventActivities.longest`) before what the event runs to, the published end or the assumed length after the start — and before then refuses (`EventActivities.refusal(for:at:in:)`). The button and the menu item stay on every day the activity is offered; a tap too early is turned down in passing — the refresh notice's pill with an ✕, and its error haptic (`RefreshNotice.refused`), as Apple Music says "Added to Library" — rather than an alert the reader has to dismiss: "Available from 12:30" where the earliest start is later today, on the clock the sheet prints its times on, and "Available on the day of the event" where it is not. Nothing reminds the reader at that time; they come back and tap again. One scheduled ahead by an older build (or the debug bench, which still schedules, for watching a stage come on by itself) shows as scheduled and can be turned off. Offered only for a kept event the reader holds a ticket for (`Tracking.hasTicket`: a lottery won or a first-come round got), whose page has published a start, and that is not over — plus, whatever changed since, for one already asked for, so it can always be turned off from where it was turned on. Not on an iPad, and not where the reader turned Live Activities off (`ActivityAuthorizationInfo`): the button is not there rather than there and refused. Where the system refuses one anyway (its limit on running activities), the sheet says the system's reason in an alert.
- **It moves on through the event by itself, though nothing can send it anything.** It is an archived picture, drawn again only when the app sends it something or its stale date passes — there is no server, and none is wanted — and a stale date is one redraw, not one per stage: the first build spent it on the next stage, and with the app not running an activity went on to "Doors open" and then sat at "Show in 0:00" through the show. So the extension draws **every stage still to come at once** (`ContentState.phases(at:)`: each stage with the moment it comes on and the moment it gives way) and shows each only inside its own stretch — `Stretch` masks each copy with a `Gate`, the system's own timer bar (`ProgressView(timerInterval:)`, filling over a second from the moment) stretched over the whole copy, since that bar is the one thing an activity draws that changes by itself at a set time. Three things about the gate were found out by looking: the bar's empty track is not clear, and used as it was it left every hidden stage faintly behind the one shown, so the bar is drawn white on black and put through `.contrast(4)` and `.luminanceToAlpha()` before it masks, which makes the track clear and the fill solid; the fill's rounded end stays put however little is filled, so the bar runs 60 pt past the view at both ends rather than being scaled past it, or the compact status kept a sliver of the stage before; and the gate going off is turned round, so the old stage wipes out as the new one wipes in rather than both showing mid-wipe. **The track is a different grey on every renderer.** The Smart Stack on a paired Apple Watch and the Mac's menu bar (iPhone Mirroring) draw the same archive; masks, alpha and the filters all hold there, and the bars run, but the Mac draws the track as an opaque grey about 0.66 of white (measured off its swatches), which a mask lets through whole and `contrast(4)` around the midpoint left 90 % solid — so every stage showed at once, "Doors in" over "That's a wrap". The fill is white everywhere. So `Gate` cuts at 0.85 instead (`brightness(-0.35)`, then `contrast(16)`), which only the fill reaches. **The watch does not honour the gates at all**: it drew every stage over the others before that cut and after it, text over text (seen on a real watch, October 2026). So the watch's own card is drawn for one stage, not through `eachStage` — see below. Checking any of it takes a real device: the paired watch Simulator is sent no Live Activity at all (its ChronoKit logs `0 activity descriptors`), so it takes a real iPhone, its watch or the Mac it mirrors to, and an event inside its window. Only what changes with the stage is drawn per stage — the words, the seat's colour, the two times and the fill, the compact status — never the flyer. Everything within a stage is a view the system runs too: the countdowns are `Text(timerInterval:countsDown:)`, the fill a `ProgressView(timerInterval:)` over the doors→start or start→end stretch. The island's outline (`keylineTint`) takes one colour, so it keeps the stage it was drawn in. Any redraw starts from where the event stands (`phases(at: .now)`), and the stale date is the next change (`nextChange`), so the redraw there catches up anything the stretches missed. The app still brings it up to date whenever it runs — on launch, on coming back to the foreground, while the sheet is open (a seat written, a door time published), a second after every write and every change of Settings › Time Zone while one is up (`EventActivities.refreshSoon(from:)` — a seat written on the ticket sheet opened from the Lotteries list or a reminder, or a clock changed, reached it only at the next of the others), at each change of stage while it is up, and in a background refresh (`BGAppRefreshTaskRequest`, `EventActivities.refreshTask`) asked for at the next one, which the system grants when it sees fit. An activity whose event has left the library is ended; one over is ended with "That's a wrap", left for half an hour. **The stretches were checked in the app's own drawing of the card, not in the system's**: the Simulator's screenshots leave the island out, and it cannot be locked or sent a button press from the command line.
- **The compact island counts down only through the last hour.** Before that its status is the time it counts to — the doors', or the start's — with the AM or PM left off ("18:00", "6:00"), and a `Gate` turns it into the countdown at 59:59 (`EventMoment.glanceStatus(sizedFor:)`). The island's width is fixed as it is drawn, whatever the timer in it reads afterwards: sized for the longest reading still to come, an activity drawn at 1:59:59 stayed that wide through 59:29 and on, and the one redraw the stale date buys cannot fix it for every event — every stage is drawn at once and the island takes the widest, so doors ninety minutes before the start kept it wide until the last hour of those. A time and "59:59" are one width. It is laid over a hidden template of its longest reading ("00:00", "0:00") because a timer takes all the width it is offered. Its timer's interval is the last hour alone, not from now: one running from more than an hour off was set for "1:00:59", shrunk to fit, and stayed a size smaller than a countdown started inside the hour. The mark at the top of the watch face, the watch's alerts and the Mac's menu bar are these same compact views; the Smart Stack has a card of its own (below). **Where even that does not fit, the minimal island's reading stands in** (`EventMoment.narrowStatus`, the second choice of a `ViewThatFits`): the iPhone 18 Pro's island is narrower, and beside another activity (Now Playing) it sets the poster and the status side by side to the left of the camera with room for about three characters, where "47:17" was cut to "4…". It reads "47m", "1h" or "40s" — in **every language**, on Shawn's word: "47分" and "1小时" are a full character wider, and there is no room for one (`minimalStatus(latinUnits:)`; the minimal island itself keeps the reader's units) — at the largest size from 13 pt down to 9 that fits, sized by a hidden "00m" so a longer word ("已结束", a time) shrinks rather than widening it. Chosen by fitting, so every island the clock fits draws what it always drew. iOS 27's `isDynamicIslandLimitedInWidth` is not read: it is documented for landscape, and whether the 18 Pro sets it for the shared island has not been seen.
- **The minimal island shows only the largest unit left, rounded down** — "1h" with an hour and twenty minutes to go, "40m" with forty minutes and forty seconds, "40s" in the last minute (`EventMoment.minimalStatus`) — because the smallest view, the one the island falls back to beside another app's activity, has room for three characters, not "47:17". No format the system runs prints that (see the next point), so each reading is drawn once and gated to its own stretch of the time left. The hours are words of their own, one per hour. The minutes and seconds are the system's timer laid over a hidden template ("00:00", "0:00") as the compact one is, with a slot as wide as the digits kept set against the template's leading edge (minutes) or trailing edge (seconds) and everything outside it clipped, so "40:40" reads "40m" and still counts by itself. That makes four readings a stage — two digits and one for each unit, switched at 10:00, 1:00 and 0:10 so a lone digit never leaves a gap beside it. Each timer's window begins at the longest reading its slot holds (59:59, 9:59, 0:59, 0:09), since a timer set for more is shrunk. More than `EventMoment.minimalHours` (12) hours off, which only an activity drawn long before its window sees, it shows the time instead. The masking was checked as drawn on the Mac (`ImageRenderer`). The island itself only shows on a device.
- **The countdowns are timers ("1:27:13"), not the sheet's "1h 27m".** Checked on iOS 27: `Text(.dateRange(endingAt:), format: Date.ComponentsFormatStyle…)` prints "1h 27m" but the extension logs "Misconfigured Text(_:format:) … The Text will not update"; `Text(.durationOffset(to:), format: .units…)` counts *negative* on the way to the moment; the `.offset` and minute-precision `.timer` styles spell the time out in words; and a custom `DiscreteFormatStyle` fails to decode in the system's renderer and draws blank (Apple forums, FB16521246). The timer holds at 0:00 once it runs out, which is what a stage nobody has updated should read. Don't swap it back without watching the extension's log.
- **Both the Lock Screen card and the expanded island stop at 160 points tall**, and the design's run to about 185. The system fits a taller one by eating its margins: on a device the card's content ended up against its edges and the island's was cut off in its corners. So on the Lock Screen the times carry their labels beside them rather than under them and the type is a size smaller; the card measures under 150 pt, in English and in Japanese. **The island follows the design's own split: only its top row — the time counted from and the time counted to, a small capital label over each — sits either side of the camera, in the `.leading` and `.trailing` regions; the flyer with the title and hall, and the stage beside the seat, sit below it in `.bottom`.** It has no fill, and none of the design's rule between those two rows: at the ceiling, the rule's 5 pt were what the seat capsule was cut off by. Its gaps are a little tighter than the design's, which adds up to about 179 pt. **Leave its content margins as the system sets them.** Taken in to 10 at the top (`contentMargins(.top, …, for: .expanded)`), the two times rose into the top corners and were cut off there on a device, and the bottom region started no higher for it — about 68 pt down either way; set to 14 at the bottom, the seat capsule's rounded bottom was still cut flat along the region's lower edge. The bottom region is cut off at its own frame, whatever margin the island leaves below it, so it carries 6 pt of padding of its own under the stage and the seat, for that cut to fall on. The height is found in its content instead: the flyer 22 × 31, the gap between its two rows 6, the seat capsule 24 tall and the labels over the two times 10 pt. Two earlier layouts showed what not to do: the `.center` region stays centred at its own width whether or not anything is beside it (a title there was cut to a few characters, a seat floated mid-island), and whatever sits in the top corners or along the bottom edge near the corners is cut into by their rounding — so the regions' content is kept 6 pt further in from the sides. Keep both under 160 with room to spare, and check the island on a device: the Simulator's screenshots leave it out.
- **The seat is a capsule in the stage's colour**, "SEAT" small beside it, in black — on the Lock Screen at the top right, in the island beside the stage, on the watch's card under the headline.
- **A paired Apple Watch's Smart Stack draws a card of its own**, as `Eventrail Watch.dc.html` draws it (`SmartStackView`, the `.small` family — `supplementalActivityFamilies([.small])`, read back through `\.activityFamily` in `ActivityCard`; CarPlay draws the same family). Three lines: the headline beside the flyer, the seat capsule — or the hall where no seat was written — and the two times with the fill between them. The title is left on the phone; the flyer says which event it is. The card is the stage's colour washed over `#1C1C1F` (`SmartStackView.base`, its `activityBackgroundTint`). **It is drawn for the stage the event is at, and no other** — no `Gate`, no copy per stage. Drawn through `eachStage` as the phone's are, the watch drew every stage at once, text over text. The countdown and the fill still run by themselves; the card moves on to the next stage when it is next drawn — at the stale date, or when the app brings it up to date. No size for the card is published, so it is laid out for whatever it is given: the design's is a 46 mm watch's (194 × 89 pt), and the three lines are spread with spacers that close up on a smaller one. The times row is a `ViewThatFits` — a size down on a 42 mm watch, whose "16:18 Doors … Start 16:33" leaves the fill a couple of points short at the design's 13 pt, then without the labels for a twelve-hour clock — so the fill's frame carries an `idealWidth` of 15, the design's least. Its layout was checked as drawn on the Mac (`ImageRenderer`, in English and Japanese, at 194 × 89 and 176 × 80), with the gates and the fill stood in for, since neither renders there; on a real watch the wash reaches the card's edges, and the gates do not hold (above). Tapping it opens the watch app on that event's Countdown, as the design says: the watch app names `EventActivityAttributes` under `WKSupportsLiveActivityLaunchAttributeTypes` (an empty list, which Apple's page says means every type, is reported not to work), and reads the activity's `widgetURL` with `onOpenURL` as the phone does. Not yet seen on a real watch — the watch Simulator is sent no activity.
- **No knob on the end of the fill**, as the design has: the fill is the system's timer bar, and nothing the activity can draw stays on the end of it between updates.
- **The flyer goes through the App Group** (`group.moe.shawn.Eventrail`, `EventActivityAttributes.posterFile(for:)`): the extension cannot download anything as it draws, so the app leaves a 108 × 150 px copy — the largest place it is drawn, at 3× — before asking, and throws copies away once the system no longer holds their activity.
- **The times are printed on Settings' clock** — the hall's, or the reader's under Settings › Time Zone, never the sheet's switch, which lasts only as long as the sheet — carried in the content (`ContentState.timeZone`). The labels beside them are the sheet's Doors / Start / End rather than the design's "Doors open / Show / Started / Ends", so the two read the same.
- **Tapping it opens the event's sheet**: its `widgetURL` is the Eventernote page, which `RootView`'s `onOpenURL` reads as an event id rather than a backup. **Opened over whatever sheet is up** (`OutsideOpens`, in [OutsideOpens.swift](Eventrail/Views/Components/OutsideOpens.swift)): a sheet presented from the root while another is up is one SwiftUI does not present at all, so the root and the root of every view shown as a sheet carry `.opensFromOutside()`, each standing at the depth it was presented at, and the frontmost takes the request — ranked as `RefreshNotices` ranks its overlays. **A view newly shown as a sheet carries `.opensFromOutside()` at the root of its body**, or a Live Activity or a reminder tapped while it is up opens nothing. Checked in the Simulator with a temporary hook: a second event's sheet opened over a first. **A request stands until its sheet appears**, not only until a presenter asks for it: a presenter knows the sheets in front of it and nothing else, and SwiftUI presents no sheet over an alert, a popover, Quick Look, a share sheet or the Welcome screen replayed from Settings — so the frontmost presenter asks again each second until the sheet's own `onAppear` says it is up, and one presenter at a time (`OutsideOpens.claimant`), or the sheet's own presenter, standing in front as it appears, would open it twice. Checked in the Simulator behind an alert: the build before opened nothing once the alert went, this one opens the sheet.

## Handoff

An event's sheet open on one device is offered to the reader's others through Handoff ([EventHandoff.swift](Eventrail/Views/Components/EventHandoff.swift)): one `NSUserActivity` of type `moe.shawn.Eventrail.event`, claimed under `NSUserActivityTypes` in [Info.plist](Info.plist) (it has no build setting), with the event's Eventernote page as its `webpageURL`. **That URL is the whole fallback**: a device without Eventrail, and a Mac, continues the activity in the browser on the page the event was read from, and nothing in the app decides it. A device with the app opens the event's sheet over whatever it has up, through `OutsideOpens`, as a Live Activity tapped does.

- **Advertised once per window, from `RootView`, never by each sheet.** An event's sheet can stand over another's (a billed performer pushed in it, one of their dates opened from there), and two views in a scene advertising one type leave it to SwiftUI which is heard. So each event sheet stands in `EventHandoff` at the depth it was presented at (`.advertisesHandoff(of:)`, outside its `.opensFromOutside()`), as `RefreshNotices` ranks its overlays, and the root advertises the frontmost through `userActivity(_:element:_:)` — nil, and nothing offered, once no event's sheet is up. A screen that shows an event some other way and should be handed off stands there too — an event beside its list stands one shallower (`advertisesHandoff(of:beneathSheets:)`), since the list stands at the depth of the sheets presented over it, and an event opened over it from outside the app tied with it, the fixed rule picking either. SwiftUI fills the activity lazily: a change of event marks it for saving and the update closure runs when the system saves it — on backgrounding, and before it is sent to another device — not at once. Checked in the Simulator with a temporary hook: a second event's sheet over a first was the one filled in.
- **The activity carries the event as a listing row would** (`EventHandoff.payload(for:)`, about a kilobyte): 概要, the links, the hashtags and the edit history stay behind, since Handoff asks for a payload of a few kilobytes and 概要 alone can be that, and so do `detailFormat` and `readAt`, so the sheet that opens on the copy reads the page for the rest (`isFullyDetailed`) — and a copy added to the library before that read lands is read again the next time it is opened. The sheet answers with the receiving device's own copy wherever it holds one. The phone and the iPad are updated apart: a copy this build cannot decode falls back to the event this device holds under the page's id, and with none, `RootView` opens the page in the browser.
- Handoff needs both devices on one Apple Account with Handoff on and Bluetooth near, and the two apps signed by one team; no entitlement. It cannot be seen in the Simulator — check it on two devices.

## Spotlight, Siri and Shortcuts

[SpotlightIndex.swift](Eventrail/Services/SpotlightIndex.swift) puts into Spotlight every event in the library, ahead and past, every followed performer's date the library does not hold, the performers followed and the halls the library is held at. [Eventrail/Intents/](Eventrail/Intents/) makes the same three things App Intents entities, so Siri and Shortcuts open them too.

- **Public facts only, never the reader's record** (on Shawn's word, October 2026): the title, the day, the hall and its address, the bill and the hashtags — no ticket, seat, cost, lottery round or note. Whatever is indexed is offered wherever the system searches. Don't add a tracking field to `EventEntity`.
- **Following dates are indexed too**, in a domain of their own (`following`), each expiring once its day is over everywhere (`dayEndsEverywhere`), as the Following tab lets it go — so one goes even if the app never runs again. A kept event never expires. Only the followed are indexed as performers, not everyone billed: an event is found by every name on its bill already. A followed performer's kana reading goes in as printed, in the other kana and in romaji (`PerformerEntity.soundings(of:)`), on their own item and on every event they are billed on; the name itself is never transliterated, since the system reads kanji as Mandarin. Titles and halls are found only as Eventernote wrote them: 横滨 does not find 横浜.
- **Written the way `WidgetLink` writes**: from `RootView`, a second after every write that can move what it holds (`EventStore.factsRevision`: what is in the library, an event's facts, who is followed, a hall placed, and whatever lands from iCloud — not a note, a ticket, a lottery, a heart or a read, which are never in it), every Time Zone change, as the app opens and comes back (for the flyers cached meanwhile), and by itself whenever `FollowedDates.dates` changes (observation tracking — no write to the library marks a listing read). Each item carries a fingerprint, a digest of its entity encoded and of whether its flyer is held; what was written is kept in `Caches/Eventrail/Spotlight.json`, and the index's client state (at most 250 bytes, so a digest of that file) says whether the file still describes the index. Where both agree a pass writes only what changed; where they do not — a first launch, an index the system emptied, Caches cleared — it empties the app's four domains and writes them whole, marking the state empty first so a pass cut short is redone whole. `SpotlightIndex.format` forces that once where an item changes in a way a fingerprint cannot see. Items go to the index a hundred at a time, since each event's carries its flyer. **Every call to the index is made from `SpotlightWriter`, an actor of its own, and the rebuild empties by domain, never with `deleteAllSearchableItems`**: in the Simulator that took six and a half minutes to come back, with work on the main actor waiting behind it, where emptying by domain took 50 ms and the whole rebuild of 122 items 0.7 s. Building the items stays on the main actor (it reads the store): some 30 ms for nine hundred events in the Simulator, unplaced and without flyers — which is why it follows `factsRevision` rather than `revision`, which every note typed and every Following row opened moves.
- **Flyers come only from `ImageCache`'s copy** (`storedData(for:)`, read without filling its memory), made 180 px thumbnails off the main actor. Nothing is downloaded for Spotlight; a flyer cached later reaches the index on the next pass.
- **A result tapped** comes back as `CSSearchableItemActionType` with the item's identifier (`event/<id>`, `performer/<actor id>`, `venue/<hall name>`), which `SpotlightIndex.opening(_:in:)` turns into an `IntentOpen` for `RootView` to open over whatever is up through `OutsideOpens` — an event's sheet, and a performer's or a hall's page as a sheet with a stack of its own (`OutsidePage`). An event this device no longer holds opens its Eventernote page in the browser. Every item is associated with its entity (`associateAppEntity`), so the system may run the matching `OpenIntent` instead; both arrive at the same place.
- **Search in App**, under Spotlight's results (`CoreSpotlightContinuation` in Info.plist, `CSQueryContinuationActionType`), and `SearchEventernoteIntent` open the Search tab with the term typed in and searched (`SearchView`'s `request`), remembered as a submitted search, and back at the tab's root (its `path` emptied — a page left pushed over the results once stood in front of them) — under a sheet, if one is up, which is the reader's to put away.
- **The intents** are `OpenEventIntent`, `OpenPerformerIntent` and `OpenVenueIntent` (`OpenIntent`s on the three entities), `OpenNextEventIntent` (the library's soonest event still to come, the one the Next Event widget and the watch count down to, ticket or not) and `SearchEventernoteIntent` (a `ShowInAppSearchResultsIntent`). Each writes its request into `IntentOpens.shared`, and the root of the window in front takes it, as a results-day reminder is taken (`openReminder()`). `EventrailShortcuts` gives Siri three of them with nothing set up; their phrases are translated in [AppShortcuts.xcstrings](Eventrail/AppShortcuts.xcstrings), each a `stringSet`, which `xcodebuild` does not add to — a phrase added in code is added there by hand. The entity type names are keyed (`entity.event`, `entity.performer`, `entity.venue`, each with an English default), because the catalog's "Venue" is the clock switch's 現地.
- **The entities are `nonisolated` structs**, `Codable` for their fingerprint and built on the main actor from the store; their queries hop there through `Launch.shared`, since Shortcuts may ask for a parameter with the app in the background.
- No permission, entitlement or host: Spotlight and App Intents need none. The index is this device's and is not synced; each device indexes the library as iCloud brings it there. Spotlight and Siri can only be looked at by hand, but the index can be read back from a temporary hook with `CSSearchQuery`.

## The watch app

[EventrailWatch/](EventrailWatch/) is `Eventrail Watch.dc.html` section 1a: My Events, then each event in three pages turned with the Crown — the countdown, the seat, the times. A `NavigationSplitView` rather than a stack, because the pages are the app and the list is where an event is loaded into them: the system draws the list button at the top left of every page, as the design does. The pages are a `.verticalPage` `TabView`, each washed in the stage's colour (`containerBackground(for: .tabView)`), and laid out on the whole screen from the design's 46 mm measurements (208 × 248 pt) scaled to the watch it is on (`DesignCanvas`), since the gauge and the times below it are placed against the screen rather than against the bar.

- **The phone and the watch app are updated apart**, a TestFlight build often leaving the watch a build behind, so `WatchLibrary` and `WatchEvent` are decoded a key at a time — only an event's id, title, link and day are insisted on — and an event the watch cannot read is left out rather than the whole copy. A field added to either is decoded with `decodeIfPresent`.
- **It keeps no store and reads nothing but what the phone sends.** `WatchLink` on the phone builds a `WatchLibrary` — the library's events still to come (`EventStore.upcoming`, at most 60), each with the ticket, seat, seat class, cost and its currency, how many times the lotteries were applied for and where they stand (`LotteryStanding`: won, pending or lost — sent as text, so a standing a later phone sends reads as none rather than failing the copy), and whether Settings › Time Zone is on Local Time — and sends it as WatchConnectivity's application context, which keeps only the latest and hands it to the watch app whenever that next runs. Within `WatchLink.budget` (60,000 bytes, `WatchLink.payload(for:within:)`): the context is refused somewhere past 64 KB, sixty events with long titles come to some 51 KB, and a refused copy left the watch on its last one with nothing but a log line — so the events furthest off are left out where it would not fit, and the links' slashes go unescaped. It is sent on launch, on every `EventStore.revision` and Time Zone change (a second after the last, and only where it differs from what was sent, so a note typed on the phone sends nothing), on coming back to the app, and when a watch or the watch app appears (`sessionWatchStateDidChange`). The watch keeps the last copy in a file (`WatchLibraryStore`) and drops an event whose day is over by its own clock. **The watch never asks the phone for anything**: a message from the watch would wake the iPhone app in the background just to open the library. No SwiftData, no iCloud, no Eventernote page on the watch — so nothing on it can write to the library either.
- **An event is read by the Live Activity's rules** (`EventActivityStage.at`, its tints, `Event.inOrder`'s order, `Event.assumedLength`), so the app and the Smart Stack card never disagree. Before its day it is "coming up", in the design's blue. The gauge is two thirds of a ring, open at the foot, filled as the event sheet fills its line — half by the start, which a dot marks at the top.
- **The countdowns are the system's timers** (`Text(timerInterval:)`), which count by themselves in Always On; `StageSchedule` redraws the rest every second (every minute in the list and with the wrist down) and at the exact moment each stage gives way.
- **Flyers come from the flyer host, fetched by the watch itself** (`FlyerCache`): downsized to 120 px, kept per event in Caches, fetched again after a week, and thrown away with the event. Nothing else goes over the network from the watch.
- **Checking it in the Simulator takes the paired pair** (iPhone 18 Pro with the Series 12 42 mm). `simctl install` straight onto the watch leaves the phone's `isWatchAppInstalled` false — the phone's registry was never told — so install the iPhone app, launch it, *then* install the watch app while it runs: the phone hears of it through `sessionWatchStateDidChange` and sends. A context sent in the same second as an install can be lost; relaunching the iPhone app sends again. Any other watch Simulator can show the screens from a temporary `#if DEBUG` hook that hands `WatchLibraryStore` `WatchLibrary.preview` (the design's events, the first an hour and a half before its doors).

## The widgets

The design canvas's Widgets row (`WidgetNext.dc.html`, `WidgetLottery.dc.html` and `WidgetOnThisDay.dc.html`, with `WidgetsHome.dc.html` and `WidgetsLock.dc.html` setting them side by side) draws three, and the extension carries them beside the Live Activity: **Next Event** (small and medium; circular, rectangular and inline on the Lock Screen), **Lotteries** (small and medium; circular and rectangular) and **On This Day** (small and medium; circular, rectangular and inline). Static configurations, with nothing to choose.

- **The extension reads a copy, never the store.** `WidgetLink` writes a `WidgetLibrary` to `Widgets/library.json` in the App Group's container the way `WatchLink` sends the watch its copy — from `RootView`, a second after every write, on a Time Zone change, a launch and a return — holding the next ten events still to come, every lottery round awaiting a result for an event still ahead (`LotteryList.next`'s order, at most 60), and every event gone to (`EventStore.attended`, with the first line of its note). It writes only where the copy changed, and asks the system to draw again only the widgets whose part changed (`WidgetKind`): a reload asked for from the background costs the widget's daily allowance. Decoded an element at a time (`Readable`), as the watch's copy is, since after an update the extension reads what the last build left until the app runs; a field added there is an optional.
- **Everything that moves with the clock is worked out as a timeline is made**, from the days and times in the copy, so a copy days old still draws today right: the days left are `Event.daysAway`'s (the day the hall says, against the reader's today — `WidgetEvent.day`), a round is out once its day has come (`WidgetRound.isOut`), a memory comes round by `CalendarDay.comesRound(on:)` — the rule `OnThisDay` reads by, leap day and all — and the next event is the first whose show has not run (`WidgetEvent.leaves`: its published end or the assumed length after its start, or with no start the end of its day). Next Event has an entry at each midnight and at each doors, start, end and leaving over two days; Lotteries at each of the week's midnights; On This Day at midnight, and each hour where the day has several memories — chosen by the hour of the day, so a timeline made again mid-hour shows the same one. Days and times are printed on Settings › Time Zone's clock, as the Live Activity prints them (`shownDay`, `timeZone`).
- **Next is the soonest kept event, not only a ticketed one**, as My Events counts down to every event the reader keeps; the medium says Ticketed or Planning. On its day the small and the medium count down to the doors, then the start, then the end — the Live Activity's stages (`EventActivityStage`) and its timers (`Text(timerInterval:)`, held at zero) — over a wash warmed amber. The round Lock Screen widget's ring fills over the last week before the day: the design draws a part-filled ring and does not say what it measures, so that is a reading of it, not the design's word.
- **On This Day's round widget is the design's two at once**: "2y AGO" with one memory, as the Lock Screen board draws it, and "2 MEMORIES" with several, as the On This Day board does.
- **Won and Lost are given on the medium Lotteries widget and written down by the app.** The buttons run `GiveLotteryResult` in the extension, which must not write the store: it leaves the answer as a file of its own in `Widgets/Answers/` (`WidgetAnswer`, one per round), takes the round's results-day reminder back, and the widget leaves the round out from then on. The app takes every answer in as it launches and comes back (`WidgetLink.takeAnswers(into:)`) — only where the round is still a lottery waiting with its day come, so a result written since, on another device or in the app, stands; and from waiting a result can only give a ticket, never take one, so there is no seat or cost to ask about. A win goes to the choice named or the round's only one; where the round applied with several, Won is a link to the round's page in the app instead, where the reader says which, as the list's swipe asks. Until the app runs, the result is on this device's widget alone. Not a `LiveActivityIntent`, which would have the system run it in the app's process: deliberately, so the extension never writes the store and nothing turns on which process the system picked. **Not yet seen end to end on a device** — the Simulator cannot be driven from the command line to put a widget on the Home Screen and tap it — and nor has whether `UNUserNotificationCenter` in the extension reaches the app's pending reminders; where it does not, the app's next schedule takes the reminder back, and until then it may still come at eight.
- **Links.** A widget opens an event with its Eventernote page, the Live Activity's route. A round is opened with the same page naming the round in its query (`RoundLink`, `?round=`), which `RootView.onOpenURL` opens on the ticket sheet's round page as a results-day reminder does: the small Lotteries widget where the round's results are out, and the medium's Won where the round applied with several choices. Everything else opens the event.
- **Flyers are fetched by the extension** (`WidgetFlyers`) as a timeline is made — never as a widget draws, which cannot wait — downsized to 540 px on the longest side, since a widget whose images are far larger than it is is not drawn; kept in the extension's Caches, fetched again after a week and dropped after a month unasked for.
- **The faces take their family as a parameter** (`NextEventFace`, `LotteriesFace`, `OnThisDayFace`) rather than reading it from the environment, so one preview can draw every family. That is how they were checked: compiled into the app for a while, drawn at the design's sizes in the Simulator in light and dark, and compared with the boards.
- **The extension's catalogs are its own.** Strings: `xcodebuild` does not add a new key to a catalog, so a key built only from the command line is added by hand with its translations — and the catalog refuses a plural that leaves the number out, so DAY and DAYS, drawn beside a count, are two keys. Colours: copies of the app's palette colorsets the widgets draw with, and four of their own (`TicketInk`, `WashAmber`, `MemoryPaper`, `StageLive`). Behind white type the design's orange and green stay at full strength in dark mode (`Color.solidTicket`, `solidWon`): the palette's lighten there, and white on them did not read.

## The calendar mirror

[CalendarSync.swift](Eventrail/Services/CalendarSync.swift) writes the library into one calendar Eventrail creates and owns. A calendar the reader made is never touched, so turning the mirror off is a single deletion rather than a hunt through a diary the app does not own. Past events are mirrored as well as upcoming ones — a calendar is a diary as much as a plan — **whether or not a ticket was recorded**, though only a ticket says the reader went: kept on Shawn's word (October 2026), so an entry never disappears the day after for want of a ticket not yet written down.

- **Off by default, and off is quiet.** Until `calendarSyncEnabled` is on, the app never reaches EventKit at all: only `mirror(_:)` and `stop()` ask for permission, and the second returns before asking unless a calendar of the app's own was actually made. So the system's permission sheet is the answer to that one switch and to nothing else. **A save mirrors only where it moved something an entry is made of** — an event into or out of the library, or an event's facts (`EventStore.owesMirror`): a note, a ticket, a heart, a Following date read or a search set off a pass that reads the whole calendar back, on the main actor, and opening a row of Following did. **`CalendarSync` is an actor**, so a pass runs off the main actor; it is handed plain values (`CalendarSync.Place`, the placing less its map item, which is built again there) and the calendar's colour. It is a per-device preference, like `iCloudSyncEnabled`, and so is the calendar identifier it remembers — an identifier belongs to this device's calendar database and means nothing on another one, so it is deliberately not part of the synced library.
- **The identifier is a cache, not the answer, and `calendar()` adopts before it makes.** The calendar usually lands on the reader's iCloud account, which *does* sync: a device with nothing in `UserDefaults` that goes straight to making one produces a second "Eventrail" beside the one already synced to it, each device mirroring the whole library into its own — every event twice, under one name. The same gap opens on a single device whenever the identifier stops resolving (a restore, iCloud handing the calendar back under a new one), and there the entries already written are not even reachable to be corrected, because every search is scoped to the calendar it was handed. So `adoptableCalendar()` takes an existing one when it is named as this app names its own, is writable, and holds **nothing but entries whose URL points at Eventernote**. That last test is load-bearing: the mirror removes every entry that does not point at an Eventernote event page, so adopting a calendar of the reader's own that happened to share the name would empty it. Don't relax it to a title match. Adopting stops a second one from being made; `discardDuplicates(of:)` removes the ones already made, by that same test, so a pair written before this existed converges — the other device's identifier stops resolving and its next mirror adopts the survivor.
- One consequence, accepted on purpose: an iCloud calendar is one object rather than one per device, so turning the mirror off on the phone takes it off the iPad until that device's next mirror makes it again. A flap that settles itself beats two calendars of one name.
- The entry carries the event's own zone, which is the hall's — see *The Eventernote import* on why an event abroad is re-read rather than re-imported. So a Taipei date sits at the Taipei hour in the reader's diary wherever they are reading it from.
- Entries are matched by the Eventernote page URL rather than by title: a title can be re-published, and an entry the reader dragged elsewhere is still the same event.
- **An entry the library lacks goes only where this device knows its event left** (`CalendarSync.goes(_:library:departed:)`, `EventStore.departedEvents`): a removal written down as one — `inLibrary` false with its membership dated, which every removal and Delete All leave and sync — or a second entry for an event already written. The entry of an event this device has never held stays, because the calendar is shared: it is the reader's iCloud account's, every device that mirrors writes to it, and each holds the library as it has it. Taking out whatever this device's library lacked, as the mirror once did, had a device set up afresh — its library not yet arrived from iCloud — empty the calendar on every device the moment Calendar Sync was turned on, and two devices mirroring without iCloud Sync take each other's entries out on every pass. The cost is an entry left behind by a device that removed its event and has not synced that since; turning the mirror off and on again rebuilds the calendar.
- **The sweep for entries is fixed (30 years back, 10 ahead), not measured from the library.** The entries worth finding are the ones whose events have *left* it, and nothing in the library can point at those: a range starting at the earliest event still held would never reach the event just removed from in front of it, and emptying the library would collapse the range to ±4 years and strand everything older in the reader's diary forever. The library's own span still widens the sweep where it falls outside. EventKit refuses a window longer than four years, so it is read in chunks of that size — ten predicates against one calendar the app owns. **Once per device the same sweep is read again 2018 years on and 543 back** (`strays(in:)`, `calendarStraysSwept`), for the all-day entries the builds before every day was Gregorian wrote on a phone set to the Japanese or the Buddhist calendar — in 4044 or 1483, outside the sweep, so never found and written afresh by every mirror after; anything of ours there is taken out.
- **Every entry carries one alert, at the door time**, wherever Eventernote published one — past events included, so the diary records the hour the reader had to be there. No switch governs it: the door time is the event's own fact rather than a preference, and Calendar's per-entry alert remains the reader's to change. (There is no travel-time field in EventKit to write instead.)
- **An event with no published start is an all-day entry, written floating** (`CalendarSync.floatingDay(of:in:)`): its hall's day at this device's midnight, no zone, and compared by the day rather than the instant. Handed `Event.date` as it stands — midnight on the hall's clock — it would land on the evening before on a phone west of the hall, and an all-day entry reads its zone back as nil, so the old comparison found it moved on every mirror.
- Where a start time was published and a finish was not, the entry is given `Event.assumedLength` (3 h) so it has a length at all; the event sheet's timeline runs to the same length, but no screen prints an end time made from it. EventKit refuses a search window longer than four years, so a wider range is read in chunks of that size.
- A placing is read from `VenuePlaces`, never searched for here — see *Where a hall is*. An entry gets a structured location where the hall has been placed and the hall's name as text where it has not, and `EventStore` re-mirrors once after a run of placings rather than once per hall.
- **Apple Maps' placing always wins** (`CalendarSync.keepsLocation(_:over:found:)`, on Shawn's word, October 2026). A phone on the mainland provider cannot ask Maps about a hall in Japan or abroad and places it by the register or OpenStreetMap, while the reader's other device placed the same hall by Maps — and the iCloud calendar is one entry for both, which each put its own back on every mirror. So a device holding Maps' answer writes it over anything; a device without one (placed otherwise, or not at all) leaves an entry holding Maps' placing of the same hall alone. Told apart by the entry's radius, the one thing a structured location could say it with: Maps' is zero and every other answer's at least a metre (`Place.notMapsRadius`). An entry an older build wrote for an OpenStreetMap building carries zero too and is taken for Maps' — a building either way. Coordinates are compared to about a metre.

## The results-day reminder

[LotteryReminders.swift](Eventrail/Services/LotteryReminders.swift) puts a local notification at **20:00 on the results day** of every lottery round still awaiting a result (`LotteryList`, `LotteryEntry.isPending` — not a first-come round, not a round with no day): "Lottery results are out", the event's title under it, and the round with "Tap to record whether you won." Tapped, it opens `TicketDetailsView` on that round's page (`opening:`), over whatever sheet is up as the Live Activity's tap opens the event (`OutsideOpens`) — or the event's sheet where the round has gone since — in the window in front (`RootView.openReminder()`): on an iPad each window has its own root, and the reminder is one for the app.

- **On the reader's clock, floating.** A results day is a `CalendarDay` with no clock, and the trigger's components carry no zone, so it comes at eight wherever the phone is that evening. They are written in the phone's own calendar, era and all (`LotteryReminder.components(of:in:)`), since the system matches a trigger with no calendar against it: the Gregorian year as it stands was Reiwa 2026 on a phone set to the Japanese calendar, and never came. Results are out by mid-afternoon in Japan, so eight anywhere east of Hawaii is after them.
- **Scheduled from the library as it stands**, as `WatchLink` sends: on launch, a second after every `EventStore.revision`, and on coming back to the app (notifications may have been turned on or off meanwhile) — each run waiting on the last. It adds only what differs from what is pending (`LotteryReminder.isScheduled(as:)`: the evening and the words, which change with the title or the app's language), takes back what no longer waits (a result written, a day moved, the event removed or over), and takes a delivered one out of Notification Center once its round has a result. iOS keeps an app's 64 soonest and drops the rest, so the 60 soonest are scheduled (`LotteryReminder.limit`) and the rest follow as the app next opens.
- **Each device schedules its own.** Nothing goes through iCloud or a server; a phone and an iPad holding the same library both ring, and a result written on one before eight takes the other's back only once that one opens.
- **Lottery Reminders under Settings › General is on by default** (`lotteryRemindersEnabled`, per device), unlike iCloud Sync and Calendar Sync: the system's prompt is the consent, and it is asked at the moment a results day is written down — on the ticket sheet's checkmark, for a round added there or given a new day (`askIfNeeded(for:)`), not on the round's own page, whose day a sheet put away with its X throws away. The row speaks only when the switch is on and the system says no, with Open Settings to the app's notification page. Off, every pending reminder is taken back.
- The delegate is set as `MyApp` is made (`LotteryReminders.shared`), since one tapped to open the app is otherwise never heard; a reminder that arrives with the app open is shown as a banner anyway.

## The iPhone Duo

The Duo (`iPhone19,4`, in the simulator from Xcode 27.1 with the iOS 27.1 runtime) is two screens: the outer one, 466 × 678 points, used closed, and the inner one, 669 × 951 — 951 × 669 opened on its side — with the fold down its middle. The canvas's iPhone Duo page draws six boards (`DuoClosedEvents`, `DuoClosedEvent`, `DuoOpenEvents`, `DuoTurnedMe`, `DuoBookPassport`, `DuoPassportSheet`). Every API below is iOS 27.1, behind `#available` — the app still deploys to 26.0 — and nothing here knows the Duo's dimensions: an iPhone publishes no fold and lays out as it always has. An iPad publishes none either, and is parted at its middle instead wherever a screen is held on its side (below), by the same code.

- **The rail down the side is the system's, not ours.** In landscape and closed, iOS 27.1 draws a *vertical bar* on the trailing edge: the status bar, a screen's `.primaryAction` items at its head, a `.bottomBar` group at its foot, and the tab bar and Search between — every board's rail, for free. Nothing in the app draws one; read the edge as `EnvironmentValues.verticalBarEdge` (`toolbarVerticalEdge`, which iOS 26 lacks). Upright and open there is none: the tab bar is horizontal again. Closed, the app keeps the iPhone's portrait whichever way the Duo is held — turned upright and then folded, it reads sideways — on Shawn's word, as on every iPhone.
- **The event sheet's close button joins the rail** (`EventDetailView.closeItem`): a bottom-bar item of its own above the actions, a capsule apart, as `DuoClosedEvent` draws it — floating over the page it stood beside the rail rather than in it. The rail keeps a bar's items at its foot where the board draws them at its head; that is the system's to place. A sheet on the open screen gets no vertical bar and is a form sheet the system centres — across the crease; no board covers an event's, so it is left as the system draws it (the Passport's drawers have a board, below).
- **The fold is read, never assumed** (`Fold.crossing`, [Fold.swift](Eventrail/Views/Components/Fold.swift)): the `division` reserved region iOS 27.1 publishes for "where content should split", inactive regions included — the boards part the screen at the fold whether the Duo is flat or half open. A fold parts a view only where it runs from edge to edge and leaves 240 points either side (`Fold.leastHalf`), so a sheet or a card it happens to cross is left whole. `FoldSplitLayout` puts two views either side of it, keeping the last in place when there is none, so a list keeps its state as the Duo opens and folds.
- **One bar over two scroll views follows the last laid out.** On the rail the title over the screen shrinks away as the scroll view the bar follows scrolls, and everything under the bar moves up with it: with the event laid out after its list, scrolling the event moved the list. Nothing in SwiftUI names the scroll view a bar follows; the order does. So `FoldSplitLayout` lays out the half before the fold — the one the title stands over — last, and the half after keeps clear of the bar (`standingAfterTheFold()`): on the rail it ignores the top safe area and starts 16 points from the top of the screen, level with the title as the boards draw it, with the bar's soft edge hidden, since that edge is as tall as the bar and lay over the half's head. So nothing a list puts in the bar may reach over the half after: Search's scope bar, which the system centres across the whole screen and nothing moves, ran over the event. Beside the fold (`opensEventsBeside`, set on the list by `eventPane`) the system is handed no scopes and the results carry the same Events/Performers choice in a `safeAreaBar` of their own, shown while the search is up as the system's is (`SearchScopes`, `BesideFoldScopes`); the scopes are emptied rather than taken off, so nothing is rebuilt as the Duo opens and folds. Each half then scrolls without moving the other — seen by scrolling one from a temporary hook and screenshotting before and after. A scroll made from a hook skips hit-testing, so it cannot show that a half takes touches at all: ask the window (`window.hitTest(_:with:)` at a point in each half, from a temporary hook) which view a touch lands on — each half's own scroll view or list, never the hosting view.
- **Every list of events opens its event beside itself** where the fold runs down the screen (`View.eventPane(_:)`, [EventPane.swift](Eventrail/Views/Components/EventPane.swift)), as `DuoOpenEvents` draws My Events: the list in the half before the fold, `EventDetailView(presentation: .pane)` in the half after, and a sheet as ever everywhere else. My Events, Following, Search, Favorites, Lotteries, On This Day, a performer's and a hall's pages and their See Alls, and the site's own lists all use it; the Me tab and the Passport part themselves (below), and a sheet over them stays a sheet. One binding drives both, so the event in front stays in front as the Duo folds (the half becomes a sheet), opens (the sheet becomes the half) and turns — handed across with no animation (`readingFold` sets the fold with animations off): the screen changing is the system's to animate, and a sheet seen sliding away on the opened screen read as the event being closed and opened again. **The sheet's item is a state of its own** (`sheetEvent`): SwiftUI says a sheet has gone by writing nil through the binding it was presented with, however it went and up to a second later, and a sheet put away for the half emptied the half that had just taken its event over. So a nil written where no sheet is up is ignored, and only the reader putting away a sheet that is up closes the event; the Passport's drawers keep theirs apart for the same reason. **And a sheet the screen put away is brought back only once that nil has come** (`awaitsReceipt`), or 1.5 s without it: an iPad turned and turned back, or a Duo folded and opened, inside that second had the late nil land on the sheet just brought back, and close the event. The drawers wait the same way. **Nothing moves while the event's page has a sheet of its own up** (`EventSheetsHold`): a sheet goes with the view that presented it, so turning an iPad, widening a Stage Manager window or opening, folding or turning a Duo with Ticket Details open put Ticket Details away — and it writes nothing until its checkmark, so every answer changed on it went, with no word. So the page says while Ticket Details or the stub is up (`EventDetailView.holdsSheet`), and the list holds the event where it stood: a sheet stays a sheet over a screen that has parted, the list laid out whole under it; a half stays in place over a screen gone whole, at no size, out of sight and putting nothing in the bar (`isTucked`). The event moves once the last of them has *gone* — in the sheet's `onDismiss`, not as its state changes: let go of as Ticket Details began to go, the list put the event's sheet away in the same moment, which SwiftUI does not do while another dismissal is under way, and the sheet stayed up with nothing presenting it. A list inside an event's sheet (a performer pushed there) holds the screen under that sheet for as long as its own event's sheet is up, and the Passport holds its drawers beside the fold the same way (`heldBeside`, the panel tucked). Checked in the iPad simulator with temporary hooks faking the fold either way under an open Ticket Details. **Picking closes the event beside the list** (My Events, Following, Favorites, on Shawn's word): its buttons stood in the bar beside the picking's, and an event picked and removed stayed up beside it. **Opening from closed, the sheet goes as the hinge moves** (`readingDuoOpening`, on `onHingeChange`): the opened screen's fold is published well over a second after the hinge leaves closed (1.4 s in the simulator), and a sheet still up by then was drawn as a form sheet in the middle of the opened screen and put away there. So the sheet is put away as the Duo starts to open, and comes back where it opens onto no half — upright, closed again, or no fold within three seconds. **And only from a list on screen** (`isShown`, off `onAppear`/`onDisappear`): every tab stays alive behind the one in front, a sheet presented from one out of sight is drawn over the tab in front, and a list there is told nothing of the fold — My Events, its event left open beside it, put the event up as a sheet over the Passport three seconds after the Duo was folded and opened again. Out of sight, or under a page pushed over it, the event waits and comes up as the list's sheet once the list is back. The Passport holds its drawers' sheets the same way, opening and out of sight alike (`holdsPassportSheets`). **Until a row is chosen the half is empty** (No Event Selected), and a close button heading the rail empties it again — not the list's first event, as the board draws it, on Shawn's word: shown there unchosen it looked open, and folding, which carries over only what was chosen, put it away. Its row wears the board's tinted ring (`marksEventBeside`, before the row's panel). My Events re-reads the event leaving the half as it re-reads one whose sheet closes.
- **The page beside a list has no stack of its own.** What it pushes — a billed performer, the hall — goes on the list's stack, so every stack that holds an event list registers `venueDestination()` at its root (the Passport and On This Day no longer register halls themselves, Me's root does). ## The look

The UI comes from the Claude Design canvas "Eventernote Mobile App Design" (`Eventrail.dc.html`), which specifies a Liquid Glass treatment in light and dark. **Pages are not drawn in glass** (on Shawn's word, October 2026: the glass is not essential, and one page in glass beside another without read as inconsistent): every card, row, pill and chip on a page, and every round button set in one, draws the glass's look without it — a veil of white over the wash and a hairline, `PanelFill` and `PanelRim` — through `panel(cornerRadius:tint:)`, `capsulePanel()` and `circlePanel()` in [WashBackground.swift](Eventrail/Views/Components/WashBackground.swift), and a button on a page is `.bordered` or `.borderedProminent` rather than `.glass` or `.glassProminent`. Glass is kept for what floats over a page, as the system's own bars do: the capsule at the foot of a list (`ListMenu`), the Passport's year chips in their bar, the refresh notice, and the close and back buttons (`glassCapsule`, `glassCircle`, `glassBackground(in:interactive:tint:)` — the last also holds a `#if os(visionOS)` material fallback, kept from when the target still built for visionOS). Palette colours are colorsets in `Assets.xcassets` generated from the design's oklch values, with light and dark variants. `PanelFill` and `PanelRim` carry High Contrast variants as well — a firmer veil and a darker rim — since the glass they stand in for strengthened its own edge under Increase Contrast and a flat panel does not. The widget extension carries copies of the ones it draws with in a catalog of its own, so a changed colour is changed in both.

It began with My Events, whose list dropped frames on an iPad scrolling beside an open event: glass is drawn afresh in every frame it moves in, and a row is never still while its list scrolls. Measured in the iPad simulator with seven hundred events, by a temporary bench that scrolled the list from a `CADisplayLink` and counted late frames and the main thread's CPU time: glass rows dropped about one frame in six and kept the main thread a fifth busier, and either glass alone (the panel, or the status pill on it) cost nearly all of that; a blur (`.regularMaterial`) or a soft shadow under the row cost nearly as much as the glass; flat colour dropped almost none. App code — date formatting, the read state, grouping — was under 1 % of the main thread. Don't put glass, a material or a shadow back on a panel; the fill and the rim were sampled off the glass itself, in light and in dark, so the two read alike over the wash.

Every screen sits on `washBackground()` — most as a `ScrollView` of cards, the library and the half-lists as a plain `List` with `scrollContentBackground(.hidden)` so the same wash shows through. The app icon is an Icon Composer document at `Eventrail/AppIcon.icon`. `AppIconBadge` in [AboutView.swift](Eventrail/Views/AboutView.swift) draws it from a separate `AppIconArt` image set, because the catalog holds an Icon Composer icon as a layer stack rather than a picture — `UIImage(named: "AppIcon")` throws on one, and the flattened PNGs iOS writes beside it top out at 120 pt. A changed icon means re-exporting that image set and `Design/AppIcon.png` too, and copying the document over `EventrailWatch/AppIcon.icon`: the watch app is its own bundle, so it carries a copy.

**The text that is read follows the reader's text size; the rest keeps the design's points** (on Shawn's word, October 2026). A list's rows and their empty notes (My Events, Following, Search, Favorites, Lotteries, On This Day, followed performers, a performer's and a hall's pages, the Me cards' rows), an event sheet's body, Ticket Details and a round's page, and Settings (with About) set their type with `scalingFont(size:weight:design:)` ([Typography.swift](Eventrail/Views/Components/Typography.swift)) — the system font at the design's size, grown through `@ScaledMetric` along the curve of the text style nearest that size — as do `SectionLabel`, `CardHeader` and `Footnote`. Everything else is `.font(.system(size:))` and stays put: the Passport, the ticket stub (a picture), every capsule, chip, pill and tile (the ticket and seat tiles, a round's calendar tile, the list group headers), the timeline's stops (drawn as the Live Activity draws them), icon buttons in fixed frames, the Welcome screen and the account sheet — and the Live Activity, the widgets and the watch, which are their own targets. **The whole app stops at xxxLarge** (`dynamicTypeSize(...DynamicTypeSize.xxxLarge)` on `RootView`, which sheets inherit), the largest size short of the accessibility sizes: past it, rows laid out side by side would have to stack. Text added to a reading screen uses `scalingFont`; text in a control or a tile does not.

## Build and run

```bash
# Build for the simulator
xcodebuild -scheme Eventrail -destination 'platform=iOS Simulator,name=iPhone 18 Pro' build

# Clean build folder when the project file or build settings change
xcodebuild -scheme Eventrail clean
```

**Xcode 27 ships no `Simulator.app`.** The bundled simulator UI is now
`DeviceHub.app` (bundle id `com.apple.dt.Devices`), and the whole
`Xcode.app/Contents/Developer/Applications/` directory is gone — Instruments,
Create ML, FileMerge and the rest moved up to `Xcode.app/Contents/Applications/`.
So `open -a Simulator` fails with "Unable to find application named 'Simulator'";
launch the UI as `open -b com.apple.dt.Devices` instead. Any tool that hardcodes
the old name breaks here — SweetPad's "Launch" task was the one this repo hit, and
a shell script under `.vscode/` stood in for it until SweetPad was fixed. SweetPad's
own build and launch tasks work now, so [.vscode/](.vscode/) holds nothing but its
settings; don't re-add a launch task or a runner script without a reason.

`xcrun simctl` is **unchanged** — boot, install, launch and `--console-pty` all
still work exactly as before. Only the app that draws the window was renamed, so
prefer `simctl` for anything scriptable and treat DeviceHub as just the window.

Don't hardcode a device name without checking `xcodebuild -scheme Eventrail
-showdestinations` first. The installed runtimes are iOS 27.0 and 27.1 (Xcode
27.1), and the simulators are iPhone 18 Pro, iPhone Air, iPhone Duo (27.1 only —
see *The iPhone Duo*) and the iPads; the `iPhone 17` this file used to name no
longer resolves, and a missing name fails the build rather than falling back to
another device.

# Run one suite or one test

The shared `Eventrail` scheme in `xcshareddata/xcschemes/` is what puts it under the Test action. The tests cover the pure logic — the widgets' copy and the lottery results given on them, the Eventernote page readers (against hand-written pages carrying the template's markers, never a fetched page), `HTMLCursor`, `Event`'s merge and re-timing, `Tracking`'s decoding and per-answer merge, `LibraryArchive`'s merge, prune and restore, `LibraryDatabase`'s rows, fold, migration and move-in (on a store held in memory, never the app's own), how `EventStore` writes and lists entries, the backup container, `Region`, `PassportStats`, `EventProgress` and the Live Activity's stages, where an iPhone Duo's fold, or an iPad on its side, parts a screen (`Fold`), and what goes into Spotlight and what a pass writes — and nothing that touches the network, iCloud, EventKit or MapKit. `Fixtures.event(...)` builds an `Event` naming only the fields a test is about. `#expect` cannot wrap a mutating call (an `HTMLCursor` advance, say); take the result into a `let` first.

## Branches and releases

**Every change goes on `main`. `release` is what testers run, and it is only ever advanced by a pull request, on Shawn's word.** Work and commit on `main` directly — a fix does not need a branch of its own. Xcode Cloud starts on branch changes to **`release`**, so nothing reaches TestFlight until that pull request is merged:

```bash
# ordinary work — this is all of it
git switch main
# edit, build, commit
git push

# only when Shawn says a build should go out
gh pr create --base release --head main --title "release: <what is in this build>"
# merged on his word; Xcode Cloud builds and distributes from release
```

**Don't open that pull request unasked, and never push to `release` directly.** Deciding that a batch of work is ready for testers is his call, not something to infer from the work looking finished; the PR is where he sees what the build would contain before it goes.

- **Keep `main` buildable anyway.** Nothing else watches it, so a broken `main` is only found when a release PR is opened. Build before pushing.
- **A hotfix branches off `release`**, not `main`, whenever `main` is carrying unfinished work: `git switch -c fix/<summary> release`, open its PR against `release` to ship, and merge it into `main` too so the fix is not lost at the next release.
- **A pull request into `main` is still welcome for anything worth reviewing** — a large feature, or a change whose diff wants reading. It is not required for ordinary work. Where one is opened, name the branch for the commit type it carries (`feat/`, `fix/`, `docs/`, `test/`, `refactor/`, `chore/`).
- **Pull requests are written in English** — title and description alike, whichever language the conversation that opened them was in, the same as commit messages.
- **Xcode Cloud builds what the repository holds**, so a change that only exists in local Xcode state — a scheme, a build setting, a file Xcode has not written into the project — fails there while it builds here. Its own record of what to build is `Eventrail.xcodeproj/xcshareddata/xcodecloud/manifest.json`, and `xcshareddata/` is tracked for that reason; `xcuserdata/` is the ignored one.

## Project structure conventions

- The `Eventrail` group is a **PBXFileSystemSynchronizedRootGroup** (`objectVersion = 90`). New `.swift` files dropped anywhere under [Eventrail/](Eventrail/) are picked up automatically — do **not** hand-edit `project.pbxproj` to register sources. Only build settings, targets, and capabilities need project-file edits. [EventrailWidgets/](EventrailWidgets/), [EventrailWatch/](EventrailWatch/) and [Shared/](Shared/) are synchronized the same way — `Shared` listed under the app, the extension and the watch app, so a file dropped there is compiled into all three. The exceptions are `EventActivity.swift` and `WidgetLibrary.swift`, kept out of the watch target by a `PBXFileSystemSynchronizedBuildFileExceptionSet`. The app embeds the watch app through an "Embed Watch Content" copy phase (`dstSubfolder = Product`, `$(CONTENTS_FOLDER_PATH)/Watch`) and a target dependency, so building the `Eventrail` scheme builds the watch app too, and Xcode Cloud archives it with no scheme of its own.
- [Info.plist](Info.plist) at the repo root holds the keys that cannot be expressed as build settings: `UTExportedTypeDeclarations` and `CFBundleDocumentTypes`, both for the `.eventrail` backup type, `UIBackgroundModes` (`remote-notification` for sync, `fetch` for the Live Activity's background refresh), `BGTaskSchedulerPermittedIdentifiers`, which names that refresh, `NSUserActivityTypes`, the Handoff activity the app takes (see *Handoff*), and `CoreSpotlightContinuation`, which offers Search in App under Spotlight's results (see *Spotlight, Siri and Shortcuts*). `NSSupportsLiveActivities` is a build setting. The extension's own, [EventrailWidgets-Info.plist](EventrailWidgets-Info.plist), holds only the `NSExtension` point, for the same reasons and in the same place. `GENERATE_INFOPLIST_FILE` stays `YES` and `INFOPLIST_FILE` points at it — Xcode merges every `INFOPLIST_KEY_*` setting into that file rather than replacing it, so the usage strings, the scene manifest and `LSSupportsOpeningDocumentsInPlace` still come from build settings. Anything that *can* be a build setting should be one: opening the target's Info.plist in Xcode rewrites the file in its own canonical form and **strips every XML comment**, so a reason written in there does not survive the next editor visit — it belongs in this file. It sits at the root beside the entitlements, outside the synchronized group, so it is not also bundled as a resource.
- `INFOPLIST_KEY_ITSAppUsesNonExemptEncryption = NO` answers App Store Connect's export-compliance question for every upload ("None of the algorithms mentioned above"). It is true because the only encryption is the system's own HTTPS through `URLSession`; `CryptoKit` is used for SHA-256 cache file names, which is hashing, and a backup is compressed rather than encrypted. **Adding encryption of the app's own — encrypting a backup, say — means revisiting this.**

## Platform and language constraints

- `SUPPORTED_PLATFORMS = iphoneos iphonesimulator` with `SDKROOT = auto`, `SUPPORTS_MACCATALYST = NO`, and `TARGETED_DEVICE_FAMILY = 1,2` (iPhone, iPad). macOS and visionOS were dropped deliberately; `platform=macOS` and visionOS destinations will not resolve. The watch app alone is `SDKROOT = watchos`, `TARGETED_DEVICE_FAMILY = 4`, watchOS **26.0**, with the same concurrency settings.
- Deployment target is iOS **26.0** at both the project and target level, so recent SwiftUI APIs are available without availability checks.
- Some `#if os(visionOS)` branches survive from when the target built for visionOS (`glassBackground` in [WashBackground.swift](Eventrail/Views/Components/WashBackground.swift), `tabViewSearchActivation` in [RootView.swift](Eventrail/Views/RootView.swift)). They are unreachable now but make re-adding the platform cheap — remove them only on purpose.
- `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` — types are `@MainActor` by default. Mark work that must leave the main actor explicitly (`nonisolated`, `@concurrent`, actors). `SWIFT_APPROACHABLE_CONCURRENCY = YES`, Swift language mode 6 in both targets, so a data race is a compile error rather than a warning. Under approachable concurrency a plain `nonisolated async` function runs on its caller's actor and its non-`Sendable` parameters stay in the caller's region; a value a framework hands over that is not `Sendable` (`TranslationSession` is the one here) has to be used from a `@concurrent` closure or function from the moment it arrives, with only `Sendable` results crossing back.
- **Every year, month and day the app counts, keeps or compares is Gregorian** — `Calendar.gregorian(in:)` and `asGregorian` in [Shared/Gregorian.swift](Shared/Gregorian.swift) — **never `Calendar.current`**, which may be the Japanese calendar (2026 is Reiwa 8, and `dateComponents([.year…])` carries no era) or the Buddhist one (2569). A year read off one calendar and handed to another landed an untimed calendar entry in 4044 (written again by every mirror), took every unclocked date off Following (its day's end in the year 8), put an eight-thousand-day countdown on Heisei events in My Events' past, kept a results day as `0008-10-12` for every other device to read as the year 8, and counted the Passport's years by era. The reader's own calendar is for naming days, and the months of a date it names whole, on screen — but a month *counted* Gregorian is named from the Gregorian calendar in the reader's language (`PassportStats.monthSymbols(in:)`): the Chinese and Hebrew calendars' own month names are other months, and the Passport's January read 正月 or Tishri. A `calendar` parameter on `CalendarDay`, `CalendarSync.floatingDay`/`isDate` and `LotteryReminder.evening` is read for its clock alone. `CalendarDay` reads a year kept as Reiwa's (under 100) or the Buddhist Era's (2400 and up) back as Gregorian. `GregorianTests` hands those a Japanese, a Buddhist, a Chinese, a Hebrew, an Islamic and a Persian calendar, and the whole suite passes with the Simulator set to any of them — `xcrun simctl spawn <dev> defaults write -g AppleLocale en_US@calendar=japanese`, then back to `en_US`; a test that builds its dates with `Calendar.current` fails there, so tests build them on `Calendar.gregorian()` too.
- `LOCALIZATION_PREFERS_STRING_CATALOGS` / `SWIFT_EMIT_LOC_STRINGS` are on and known regions are en, ja, zh-Hans, zh-Hant — user-facing strings should be localizable `LocalizedStringKey`s, not raw `String`s.

## Permissions and hosts

iOS sandboxes every app by itself, and no build setting here widens or narrows that. The `ENABLE_APP_SANDBOX`, `ENABLE_RESOURCE_ACCESS_*` and `ENABLE_USER_SELECTED_FILES` settings the target once carried are the **macOS** App Sandbox, left from when it built for macOS: an iOS build signed with them carried none of it — its entitlements are the four in [Eventrail.entitlements](Eventrail.entitlements) and nothing else — so they were removed. Don't re-add them. On iOS a protected resource is gated by its usage string (an `INFOPLIST_KEY_NS…UsageDescription` build setting, in both configurations) and the system's own prompt; iCloud, push and the App Group by the entitlements files and the App IDs.

- **Calendars** is the one protected resource the app reads: `NSCalendarsFullAccessUsageDescription`, asked for by the mirror alone — see *The calendar mirror*. Full access rather than write-only, because the mirror reads back its own entries and adopts a calendar another device made.
- **Notifications** (alert and sound, no usage string — a notification prompt carries none), asked for by `LotteryReminders` alone: the first time the ticket sheet is saved with a lottery round added or given a results day whose evening is still to come, or when the Lottery Reminders switch is turned back on with nothing asked yet — never on a launch, and never for rounds synced in from another device. Only local notifications; the `aps-environment` entitlement is CloudKit's silent pushes, not this. See *The results-day reminder*.
- **Photos, add-only** (`NSPhotoLibraryAddUsageDescription`, `PHPhotoLibrary.requestAuthorization(for: .addOnly)`), asked for the first time the reader saves an event's flyer — from the flyer's long-press menu, or Save Image in a share sheet, which needs the string too or the app is killed — or a ticket stub, from its own Save Image (`PhotoSaving`); the string names both. Nothing reads the photo library.
- **A file the reader picks** needs no permission: the importer reads the one file picked, and export's share sheet is a choice made for its preview (see *Persistence and sync*).
- **Nothing asks for the reader's location** — there is no `CLLocationManager` in the app and no `NSLocationWhenInUseUsageDescription` — the maps draw halls, not the reader. The same goes for the camera, microphone, contacts, Bluetooth and the rest: none has a usage string. A feature that needs one means adding it, and a new system prompt in front of the reader — flag it.

The app fetches from five places and no others: `www.eventernote.com`, the flyer host its pages point at (`eventernote.s3.amazonaws.com`, loaded through `ImageCache` by `CachedImage` — never `AsyncImage`, whose shared URL cache the host's missing `Cache-Control` defeats; the watch app and the widget extension read their flyers from there too, and nothing else), `msearch.gsi.go.jp`, `nominatim.openstreetmap.org` and `api.frankfurter.dev` — exchange rates, free and keyless, the reference rates of a hundred-odd central banks, read by `ExchangeRates` only when a screen has a ticket to convert, one GET of `/v2/rates?base=EUR` for every currency at once, kept in Caches and not asked again for twelve hours. Its **v2** API: v1 (`api.frankfurter.app`, the URL most examples give) carries only the ECB's thirty currencies, with no Taiwan dollar or pataca. Apple Maps goes through MapKit. Everything else — the source repository, a hall's official site, a hashtag, directions — is handed to the system as a link and opened outside the app. Another host means a new dependency on somebody else's service, and should be argued for first.

## Playgrounds

[RootView.swift](Eventrail/Views/RootView.swift) imports `Playgrounds` and defines a `#Playground` block alongside the `#Preview`. These are inline-execution scratch areas for Xcode; they are not tests and are not run by `xcodebuild`.
